직접 만든 세 가지 교육 사례를 호스트에서 빌드하고 실행했습니다. 기존 제품에서 발견한 결함, 실제 보드 계측, MCU 인터럽트 실행과 구분합니다. 프레임의 잘못된 길이 승인, 살아 있는 수신 버퍼의 내용 변경, 명시적으로 열거한 공개 순서를 관측했습니다.

최종 실행은 3개 소스의 빌드와 3개 실행이 모두 종료 코드 0이었습니다. 컴파일 경고는 없었습니다. 종료 코드만으로 판정하지 않고 아래 출력과 활성화된 `assert`의 조건을 함께 확인했습니다. 러너는 새 출력 폴더에 빌드 입력 복사본·소스 SHA-256·인수·로그·실행 결과 JSON을 남깁니다. 저장소에는 해당 실행 파일이나 사용자 컴퓨터의 전체 경로를 담은 로그를 올리지 않습니다.

## 1. C 프레임의 길이와 바이트 순서

```text
valid_count=2 sample0=4660 sample1=43981
wrapped_count=2147483648 faulty_accept=1 safe_accept=0
wrong_endian_sample0=13330 expected=4660
length_count_combinations=16496
frame contract checks passed
```

헤더 `00 00 00 80`이 원소 수 2,147,483,648을 나타낼 때 32비트로 좁힌 길이 식은 실제 4바이트 입력을 승인했습니다. 수정 파서는 거부했습니다. 잘못 승인한 경로로 본문을 읽지는 않았습니다. 원소 수 8종과 길이 0~2,061의 2,062종으로 16,496개 반환값을 비교했습니다. 별도로 잘린 헤더·잘린 샘플·빈 프레임·남는 바이트·알려진 little-endian 샘플을 검사했습니다.

## 2. C++의 복사·뷰·핸들

```text
borrowed=ERROR owned=READY
lost_bound=PASS,FAULT kept_bound=PASS
stale_handle=rejected rebound=37
ownership contract checks passed
```

버퍼를 재사용한 뒤 뷰와 소유 복사본의 값이 달라졌습니다. NUL 종료 포인터만 전달한 문자열 생성에서는 필드 길이가 사라졌고, 뷰를 전달한 생성에서는 길이 4가 유지됐습니다. `vector`의 재할당 후에는 세대 번호가 지난 핸들을 거부하고 새 핸들로 값 37을 읽었습니다. 무효 포인터를 역참조하거나 AddressSanitizer를 실행하지 않았습니다.

## 3. 공개 순서와 SPSC 큐

```text
schedule=PPCC faulty_stale_read=0 corrected_stale_read=0
schedule=PCPC faulty_stale_read=0 corrected_stale_read=0
schedule=PCCP faulty_stale_read=1 corrected_stale_read=0
schedule=CPPC faulty_stale_read=0 corrected_stale_read=0
schedule=CPCP faulty_stale_read=0 corrected_stale_read=0
schedule=CCPP faulty_stale_read=0 corrected_stale_read=0
shared_counter_observed=0 expected=1
spsc_capacity=7 wrap_pairs=10000 head_lock_free=1
schedules=6 faulty_stale_reads=1 corrected_stale_reads=0
ring publication model checks passed
```

두 생산 사건과 두 소비 사건의 순서를 유지하는 여섯 배치를 열거했습니다. 조기 공개 경로의 `PCCP`에서 오래된 값 0을 읽었으며 기록 후 공개 경로에서는 같은 문제가 없었습니다. 별도의 공유 카운터 읽기·쓰기 순서에서 기대값 1 대신 0을 얻었습니다. C11 SPSC 코드는 빈 큐·full 거부·FIFO·10,000 push/pop 쌍을 순차적으로 검사했습니다. 호스트의 `head` 원자 객체가 잠금 없는지도 확인했으나 실제 MCU의 결과로 일반화하지 않습니다.

## 초기 빌드 문제와 검사 활성화

첫 빌드에서는 최적화 경로에서 `assert`가 비활성화되어 그 안에서만 참조하는 변수에 미사용 경고가 발생했습니다. `-Werror` 때문에 빌드가 실패했고 그 실행을 통과 결과에 포함하지 않았습니다. 현재 러너는 `-UNDEBUG`를 명시합니다. 또한 세 소스 모두 `NDEBUG`가 정의된 채라면 `#error`로 빌드를 거부합니다.

이 장치를 확인하려고 각 소스에 `-DNDEBUG -fsyntax-only`를 지정한 별도 음성 대조 빌드를 실행했습니다. 세 빌드 모두 `requires active assertions` 오류로 거부되었습니다. 이는 런타임 검사를 끄고도 성공하는 경로를 방지하는 빌드 조건 검사이며, MCU의 고장을 재현한 결과는 아닙니다.

## 범위와 한계

이 검사는 코드가 다루는 입력과 계약을 확인합니다. 전송 계층, CRC, 시퀀스 번호, 모든 32비트 입력, 할당 실패, 세대 번호 순환, 실제 두 스레드의 경쟁, CPU 약한 메모리 순서, MCU ISR·DMA·캐시·지연은 시험하지 않았습니다. SPSC의 순차 실행과 사건 모델을 각각 읽어야 하며 두 결과를 합쳐 현장 동시성 검증 완료라고 부르지 않습니다. 기존 단일 실행 흐름 예제와 프로젝트의 과거 결과 파일은 변경하지 않았습니다.

## English

Three native fixtures built and exited successfully with assertions enabled. A separate NDEBUG control rejected all three sources at compile time. The observations distinguish deliberate contract failures from corrected paths. The evidence covers host execution and a finite event model, not device measurement, sanitizers, interrupt execution, or concurrent stress.
