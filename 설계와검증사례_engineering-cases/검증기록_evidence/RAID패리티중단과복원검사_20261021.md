## 실행 환경과 범위

2026-10-21에 Python 3.12.14, Windows-11-10.0.26200-SP0에서 실행했습니다. 데이터 두 개와 패리티 한 개를 각각 4바이트 호스트 파일로 기록했습니다. 선택한 기록 경계에서 동기화 뒤 정상 반환하고, 새 Python 프로세스가 그 파일을 다시 읽었습니다. 물리 RAID·Linux md·mdadm·전원 제거·OS crash·fsync 도중 kill·sector tearing·4바이트 쓰기 원자성·성능은 시험하지 않았습니다.

원시 명령·stdout·stderr·종료값·각 비교·환경은 비공개 `tmp/backup-raid-retry-20261021/raid/verification.json`과 `final-*/results.json`에 보존했습니다. 초기 실행 기록도 남겼으며, 아래 수치는 세대 상한 검사를 반영한 최종 소스의 결과입니다.

## 실제 명령과 종료값

예제 폴더 기준의 명령입니다. `python`은 위 환경의 Python 실행 파일, `OUT`은 매번 새로 지정한 비공개 결과 루트입니다. 실제 절대 인자 목록은 원시 JSON에 있습니다.

```powershell
python -X utf8 -B verify.py --output OUT/final-normal-none --mutation none
python -X utf8 -B -O verify.py --output OUT/final-optimized-none --mutation none
python -X utf8 -B verify.py --output OUT/final-normal-trust-dirty --mutation trust-dirty
python -X utf8 -B -O verify.py --output OUT/final-optimized-trust-dirty --mutation trust-dirty
```

나머지 `replay-incomplete`·`accept-two-missing`·`skip-generation`도 각각 기본과 `-O`에서 실행했습니다.

| 실행 | 횟수 | 기대 종료값 | 실제 결과 |
| --- | ---: | ---: | --- |
| 정상 기본·최적화 | 2 | 0 | 각각 PASS·832개 검사·146개 입력 사본·298개 자식 호출입니다. |
| 네 변이 × 두 모드 | 8 | 1 | 모두 ERROR로 기대 계약과의 차이를 검출했습니다. |
| 기존 정상 출력 경로 재사용 | 1 | 2 | OUTPUT_EXISTS이며 기존 results.json의 해시가 같습니다. |

정상 stdout은 다음과 같았습니다.

```text
{"status": "PASS", "error": null, "mutation": "none", "checks_count": 832, "cases": 146, "child_calls": 298}
```

`cases`는 seed 원본을 복사해 만든 입력 폴더 수입니다. `checks_count`에는 종료값·사유·내용·원본 보존 등의 비교가 함께 포함되며 832개의 물리 고장을 시험했다는 뜻이 아닙니다. 모델 자식의 의도한 거부는 종료 3이고, 검증기는 해당 사유까지 비교합니다.

## 실제 관측

| 대상 | 관측과 기대 비교 |
| --- | --- |
| 정상 이전 stripe의 D0·D1·P 각각 단일 결손 | 세 경우 모두 `[10111213,a0a1a2a3,b0b0b0b0]`으로 사본 재구성했습니다. |
| D0만 새 값 | `[20212223,a0a1a2a3,b0b0b0b0]`, 패리티 불일치입니다. |
| P만 새 값 | `[10111213,a0a1a2a3,80808080]`, 패리티 불일치입니다. |
| 혼합 상태의 계산 D1 | 두 순서 모두 `90919293`이며 독립 원본 `a0a1a2a3`와 다릅니다. |
| dirty·로그 없음 | 모든 멤버가 있어도 NEEDS_RECOVERY_DATA로 거부했습니다. |
| dirty·유효한 세대 8 full redo | 멤버 갱신 이전·한쪽만 갱신·양쪽 갱신 뒤 모두 새 사본의 세 값이 고정 새 리터럴과 같았습니다. |
| 56바이트 로그 prefix 0~55 | 모두 REDO_LENGTH로 거부하고 목적지를 만들지 않았습니다. |
| 한 바이트 바뀐 로그 | REDO_DIGEST입니다. |
| 온전한 세대 6 로그 | REDO_GENERATION입니다. |
| 다른 stripe·정합성 없는 payload | REDO_IDENTITY·REDO_PARITY입니다. |
| 두 개·세 개 멤버 결손 | TOO_MANY_MISSING이며 dirty·full redo의 두 결손도 거부했습니다. |
| 멤버 길이 0·3·5바이트 | MEMBER_LENGTH입니다. |
| 최대 세대 경계 | clean 65534·dirty 65533→65534는 허용하고 dirty 65534→65535는 거부했습니다. |
| 기존 사본 출력·원본 보존 | KEEP 파일과 기존 보고서가 유지되며 원본의 파일명·해시도 같습니다. |
| 복원 사본 재복원 | 이전·새 stripe 모두 다시 만든 파일의 해시가 같은 멱등성을 확인했습니다. |

두 갱신 순서·세 로그 상태·다섯 경계·D1 결손 유무를 조합한 60개 입력 사본과 별도 prefix·손상·자료형·상한 검사를 실행했습니다. 다섯 경계는 dirty 표시 직후, 로그 단계, 첫 멤버, 둘째 멤버, clean 표시 뒤입니다. 로그 없는 경로의 `log`는 추가 기록이 없는 동일 상태이며, 이 중복을 서로 다른 물리 손상으로 세지 않습니다.

## 패리티만으로 놓치는 동시 손상

D0를 `11111213`, P를 `b1b0b0b0`으로 함께 바꾼 사본은 parity_matches=True였지만 원본 리터럴과의 비교는 False였습니다. clean의 자체 XOR 복원 경로는 이 바이트들을 그대로 복사했습니다. 검증기는 이를 알려진 한계의 양성 반례로 기록했고 원본 복구라고 표시하지 않았습니다. 멱등성·패리티 정합성만으로 원본 정체성을 확정할 수 없습니다.

## 의도적 변이에서 발견한 차이

| 변이 | 기본·최적화 공통 관측 |
| --- | --- |
| `trust-dirty` | dirty·로그 없음이 거부되어야 하는데 복원 종료 0을 반환하여 `child_11_exit: 0 != 3`입니다. |
| `replay-incomplete` | digest 없는 24바이트 header를 받아들여 `child_37_exit: 0 != 3`입니다. |
| `accept-two-missing` | 두 결손 중 하나를 0으로 채워 복원 성공 처리하여 `child_276_exit: 0 != 3`입니다. |
| `skip-generation` | 세대 6의 온전한 옛 로그를 받아들여 `child_269_exit: 0 != 3`입니다. |

검증기는 최초 차이에서 종료하고 그 자식의 실제 JSON stdout을 남겼습니다. 위 오류는 의도적으로 틀리게 만든 코드의 관측이며 정상 구현에서 실패했다는 뜻이 아닙니다. `require`와 검증기의 명시적 `raise`는 `-O`에서도 유지됩니다.

## 출처와 자체 전제

Linux 6.12 [RAID cache](https://docs.kernel.org/6.12/driver-api/md/raid5-cache.html)·[PPL](https://docs.kernel.org/6.12/driver-api/md/raid5-ppl.html) 문서 전체와 [md 관리자 문서](https://docs.kernel.org/6.12/admin-guide/md.html)의 dirty/degraded·bitmap·consistency_policy 절을 2026-10-21에 읽었습니다. 공식 파일 형식·성능 수치를 이 모델의 결과로 쓰지 않았습니다. 자체 56바이트 redo, clean metadata의 신뢰, 세대 상한, 한 멤버 결손 지원 범위는 이 예제의 선택입니다. SHA-256은 서명이 아니며 metadata와 로그를 함께 바꾸는 공격자에 대한 인증·rollback 방지는 없습니다.

## English

Normal and optimized runs each passed 832 comparisons across 146 input copies and 298 fresh child calls. Four implementation mutations failed in both modes; reusing the existing output returned exit 2 without changing its report. Mixed updates reconstruct the wrong D1 as 90919293, whereas valid generation-bound full-stripe redo yields the new fixed literals. Every proper record prefix is refused. Repeated copy recovery preserves source hashes. A positive consistent-corruption example separately shows parity agreement without original content identity. These are bounded host-file experiments, not Linux md or physical power-loss tests.
