# 워치독 진행 상태와 리셋 검사 / Watchdog health and reset checks, 2026-10-21

표준 라이브러리 Python으로 직접 구성한 task 진행·feed 창·원인 기록·부팅 정책 모형을 실행했습니다. MCU·하드웨어 watchdog·실제 reset·RTOS·retention 저장장치를 실행하지 않았습니다. 의도한 오류를 정상 경로와 비교한 교육용 자료이며 현장에서 발견한 제품 결함이나 안전 인증 시험이 아닙니다.

[사례](../작업진행을확인하는워치독과리셋기록_watchdog-health-reset.md), [실행 방법](../../예제_examples/실무검증_practical-validation/watchdog_reset/README.md), [models.py](../../예제_examples/실무검증_practical-validation/watchdog_reset/models.py), [verify.py](../../예제_examples/실무검증_practical-validation/watchdog_reset/verify.py), [입력과 literal 기대값](../../예제_examples/실무검증_practical-validation/watchdog_reset/fixtures.json)을 연결했습니다.

## 실제 환경과 명령

2026-10-21 Windows 11 `10.0.26200`, AMD64, CPython `3.12.14`, MSC v.1944에서 실행했습니다. 외부 Python 패키지는 필요하지 않습니다. 실제 JSON에는 UTC 시각·Python 실행파일·전체 명령 인수·최적화 수준·소스/입력 SHA-256이 있습니다.

코드 폴더에서 다음 형태로 실행했습니다. 출력 경로는 매번 새 폴더로 지정합니다. `-O`는 Python의 최적화 모드이며 이 검사에서는 `assert`에 의존하지 않습니다.

```powershell
python -X utf8 -B verify.py --output C:/temp/watchdog-run-new
python -X utf8 -B -O verify.py --output C:/temp/watchdog-optimized-new
python -X utf8 -B verify.py --inject periodic-feed --output C:/temp/watchdog-periodic-new
python -X utf8 -B verify.py --inject raw-deadline --output C:/temp/watchdog-wrap-new
python -X utf8 -B verify.py --inject clear-before-capture --output C:/temp/watchdog-clear-new
python -X utf8 -B verify.py --inject always-restart --output C:/temp/watchdog-boot-new
```

각 mutation에도 `-O`를 붙인 별도 실행을 했습니다. 로컬 산출물은 `run-1`, `run-optimized-1`, `mutant-...-1`, `optimized-mutant-...-1`이라는 다른 폴더에 보존했습니다. private 경로가 없어도 공개된 소스와 입력으로 같은 검사를 새로 실행할 수 있습니다.

## 정상 결과와 기대값의 근거

| 항목 | 별도로 정한 기대값 | 실제 관측 |
| --- | --- | --- |
| 진행 gate | feed `[254]`, reset poll 266 | 기대값과 같습니다. |
| 주기 feed 대조 | `[254,258,262,266,270]`, 구간 내 reset 없음 | 멈춘 acquire를 가립니다. |
| 창 경계 | 시작250, 현재253/254/5/6 → early/feed/feed/late | 다섯 literal 입력과 같습니다. 마지막에는 feed 요청 없음도 포함합니다. |
| freshness | 나이10 허용, 나이11 거부 | 경계를 구분합니다. |
| epoch | 이전 feed에서 소비한 보고 거부, 두 task의 새 보고 허용 | 두 조건을 구분합니다. |
| 원인 snapshot | watchdog+power → raw5·두 원인, 소거 뒤 raw0 | 순서대로 관측했습니다. |
| 부팅 정책 | 실패값 `[1,2,3,0,1,0,1]` | mode는 normal/normal/recovery/normal/normal/stable/normal입니다. |

reset_at=266은 입력이 deadline에 poll하도록 구성됐기 때문에 얻은 값입니다. `monitor()`는 progress 사건에서 timeout을 검사하지 않고 poll에서만 평가합니다. 늦거나 사라진 poll 사이에 하드웨어가 정확한 시각에 reset을 일으키는 비동기 타이머를 구현하지 않았습니다.

tick sweep는 256개 시작값에서 현재값을 한 칸씩 전진시켜 경과 0~127을 만듭니다. 그 독립 경과 번호를 모형의 `%256` 차이와 비교하고 feed 창의 세 구간도 비교했습니다. 총 32,768조합이 일치했습니다. 실제 시간 차이 128 미만이라는 외부 전제가 필요하며 여러 바퀴의 모호함을 복원한 검사가 아닙니다.

기대 feed·리셋 시각·창·부팅 결과는 fixture의 literal 값입니다. 결과가 스스로 보고한 deadline·횟수를 기대값으로 다시 사용하지 않습니다. 내부 오류 대조 6개, 잘못된 tick·빈/중복 task·미등록 task·잘못된 window 등 입력 거부 7개도 통과했습니다. 같은 실행의 여러 대조를 독립 fault coverage로 합산하지 않습니다.

정상 프로세스가 끝났다는 사실만 확인한 것이 아닙니다. 의도한 네 결함으로 정상 계약을 바꾸면 종료 1이 되며 실패 이유가 결과 JSON에 있습니다. 정상 실행 안에 잘못된 경로를 설명용으로 관측한 것과, 오류 주입으로 전체 검사가 실패한 것을 구분합니다.

같은 `run-1` 경로로 재실행한 대조는 종료 2와 `output already exists`였습니다. 기존 결과 SHA-256은 전후 모두 `8741c45ff145121474da3aaa512239aad98710da1a14632af696ae495979e87c`였습니다. 정상/O 결과는 시각·명령·최적화 수준이 달라 파일 전체 hash는 다르지만 checks와 소스/입력 해시는 같습니다.

## 공식 자료와 실제 읽은 범위

열람일은 2026-10-21입니다. [ST RM0368 Rev 6, 2025-01](https://www.st.com/resource/en/reference_manual/rm0368-stm32f401xbc-and-stm32f401xde-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)의 표지·§6.3.18(131~132쪽), §15.1(422쪽), §16.1~16.6(427~432쪽), §23.16.4(832쪽)의 해당 내용을 웹 원문으로 읽었습니다. RCC_CSR 원인 플래그와 RMVF, IWDG와 WWDG의 클록 차이, window·만료·debug freeze를 대조했습니다. 특정 MCU의 예시이며 모든 Cortex-M의 동일한 주변장치 규격이라는 뜻은 아닙니다.

[ST F4 HAL driver v1.8.3 RCC header](https://github.com/STMicroelectronics/stm32f4xx-hal-driver/blob/v1.8.3/Inc/stm32f4xx_hal_rcc.h)의 reset flag 조회와 clear 매크로도 직접 읽었습니다. 실제 MCU에서 매크로를 실행한 기록은 아닙니다. 모델의 8비트 증가 tick·4/12 창·세 번의 실패 한도·checkpoint 정의는 직접 정한 계약이며 해당 문서의 레지스터 설정값이 아닙니다.

boot ledger는 정상적으로 보존된다고 가정한 Python 객체입니다. 실제 장치의 retention·초기화·CRC·원자적 갱신·flash 마모·전원 상실을 시험하지 않았습니다. recovery는 정책 표시이며 부팅 이미지 선택·안전 출력·보안 검증·시간 backoff를 실행하지 않습니다. 제품에서는 이 부분과 clock tolerance·startup·저전력·debug 없는 동작을 추가 검증해야 합니다.

## English

The suite passed 32,768 bounded tick/window cases, literal scenario expectations, freshness/epoch boundaries, six internal fault controls and seven invalid-input controls. Both normal and optimized runs returned 0; four injected faults returned 1 in both modes. Existing output reuse returned 2 with an unchanged result hash. The record covers scripted host observations and source reading, not asynchronous hardware reset timing or retained storage.
