## 추가 대조를 재현하는 SQL 순서

각 시나리오마다 새로운 로컬 DB 파일을 만들고 Python `sqlite3.connect(path, isolation_level=None)`으로 A와 B를 각각 엽니다. 자동 커밋 구성에서 두 조회를 먼저 마친 뒤 두 갱신을 순서대로 실행합니다. 동시 스레드의 타이밍 경쟁을 측정하지 않습니다.

```sql
-- 연결 A에서 새 파일 초기화
PRAGMA journal_mode=WAL;
CREATE TABLE counter(id INTEGER PRIMARY KEY, value INTEGER, version INTEGER);
INSERT INTO counter VALUES(1, 0, 0);
-- A와 B가 각각 아래 조회를 실행: 둘 다 (0, 0)
SELECT value, version FROM counter WHERE id=1;
```

| 별도 새 DB에 적용한 순서 | A의 변경 행 수 | B의 변경 행 수 | 마지막 조회 |
| --- | --- | --- | --- |
| A: `UPDATE counter SET value=1 WHERE id=1;` → B: 같은 문장 | 1 | 1 | `(1, 0)` |
| A: `UPDATE counter SET value=value+1 WHERE id=1;` → B: 같은 문장 | 1 | 1 | `(2, 0)` |
| A: `UPDATE counter SET value=value+1,version=version+1 WHERE id=1 AND version=0;` → B: 같은 문장 | 1 | 0 | `(1, 1)` |

Python 커서의 `rowcount`를 각 SQL 직후 저장했습니다. 마지막 조회는 `SELECT value, version FROM counter WHERE id=1`입니다. 첫 두 시나리오에는 버전 증가를 넣지 않았습니다. 세 번째 시나리오는 충돌 검출까지만 확인했으며 B를 자동 재시도하지 않았습니다.
