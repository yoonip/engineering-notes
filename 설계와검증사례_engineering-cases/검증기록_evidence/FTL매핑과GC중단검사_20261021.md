# FTL 매핑과 GC 중단 검사 / FTL mapping and GC interruption checks, 2026-10-21

실제 호스트의 두 append 파일을 새 Python 프로세스에서 읽어 LPN→PPN 상태를 재구성했습니다. 선택 prefix를 flush·fsync한 뒤 자식만 종료했습니다. 실제 NAND·SSD firmware·NVMe 명령·OS crash·전원 차단 장비를 실행한 기록은 아닙니다.

[코드와 입력](../../예제_examples/실무검증_practical-validation/ftl_mapping/README.md) · [매핑 게시 사례](../FTL의매핑게시와전원중단_ftl-map-publication.md) · [GC·TRIM 사례](../FTL의GC와폐기된주소재사용_ftl-gc-trim-reuse.md)

## 환경과 실제 실행

Windows 11 build 10.0.26200·AMD64·CPython 3.12.14·MSC v.1944 64 bit와 표준 라이브러리에서 실행했습니다. 소스·fixture를 UTF-8/LF로 고정한 뒤 기본과 `-O`를 새 결과 폴더에 실행했습니다. 비공개 `ftl/verification.json`과 각 results.json에 실제 실행 파일·전체 명령·환경·stdout·stderr·exit·소스와 결과 SHA-256이 있습니다.

코드 폴더에서 아래 인수를 사용하며 C:/temp는 독자가 선택할 새 경로의 예입니다.

```powershell
python -X utf8 -B verify.py --output C:/temp/ftl-normal-new
python -X utf8 -B -O verify.py --output C:/temp/ftl-optimized-new
python -X utf8 -B -O verify.py --mutation publish-first --output C:/temp/ftl-map-first-new
python -X utf8 -B -O verify.py --mutation erase-old-first --output C:/temp/ftl-erase-first-new
python -X utf8 -B -O verify.py --mutation wrong-page-identity --output C:/temp/ftl-identity-new
python -X utf8 -B -O verify.py --mutation stale-gc --output C:/temp/ftl-stale-gc-new
python -X utf8 -B -O verify.py --mutation ignore-trim --output C:/temp/ftl-trim-new
```

변이 5종도 기본 모드로 각각 실행했습니다. 최종 정상 2회·변이 10회이며 first-run과 다른 새 경로입니다. 명시적 예외를 사용하므로 `-O`에서도 기대값 검사가 남습니다.

## 정상 결과와 중단 행렬

기본/-O 정상 실행은 PASS·종료 0이며 checks·cuts·bad_controls·workload가 같았습니다. 각각 검사 241개·cut 98개·새 자식 409개·오류 경로 대조 5종·부하 요약 1개입니다. 비교 횟수와 prefix 수를 서로 독립인 실물 시험 수로 합산하지 않습니다.

| 행렬 | 선택한 prefix | 기대값과 관측 |
| --- | --- | --- |
| write DATA 32바이트 | 0~32, 33개 | 모두 이전 값·PPN0이며 full DATA만 남으면 stale 사본 1개입니다. |
| write map 48바이트 | 0~48, 49개 | 48에서만 새 aaaa0001·PPN1·version 2입니다. |
| GC DATA/MOVE/ERASE | 각각 0·1·N−1·N, 12개 | 현재 live 값은 보존하며 완성된 MOVE에서 참조가 이동합니다. |
| TRIM map | 0·1·47·48, 4개 | full 48에서만 None·version 2입니다. |

자식 종료값은 정상 288개·의도한 거부 3이 20개·명시 중단 23이 101개입니다. 마지막 수는 행렬 98개, 잘못된 게시/선행 erase 대조 2개, 미해결 꼬리 대조 1개입니다. 자식의 예상 종료 3/23과 검증기 자체의 ERROR·종료 1을 구분합니다.

## 매핑·GC·주소 재사용

| 대조 | 실제 관측 |
| --- | --- |
| 새 DATA 확인 뒤 매핑 게시 | LPN0은 PPN0·incarnation 1·version 1에서 PPN1·incarnation 4·version 2로 바뀝니다. |
| 매핑 선행 뒤 DATA 0바이트 중단 | MAPPED_PAGE_MISSING입니다. |
| 이전 block ERASE 선행 뒤 DATA 0바이트 중단 | 기존 매핑도 MAPPED_PAGE_MISSING입니다. |
| 다른 LPN을 넣은 DATA | WRITE_READBACK_IDENTITY로 게시를 차단하고 이전 값·stale 사본을 유지합니다. |
| GC snapshot 뒤 같은 LPN 새 쓰기 | STALE_GC_SNAPSHOT이며 두 파일의 SHA가 같습니다. |
| GC snapshot 뒤 victim에 다른 LPN live 추가 | 일부 MOVE 뒤 ERASE_LIVE_BLOCK입니다. 값은 유지되지만 전체 GC rollback은 아닙니다. |
| TRIM→stale-only erase→다른 LPN 쓰기 | PPN0은 LPN1·incarnation 5가 되고 LPN0은 None입니다. 옛 GC는 거부합니다. |
| TRIM을 무시한 복구기 | 옛 11111111이 다시 보입니다. 같은 파일의 정상 복구기는 None을 유지합니다. |

stale-gc 오류 대조는 writer와 MOVE 재생의 token 검사를 둘 다 생략합니다. 새 aaaa0001 대신 11111111·version 1이 노출됐으며 정상 reader는 그 잘못된 저널을 MAP_BASE_CHANGED로 거부했습니다.

## 부하·공간 계산

고정 trace는 host 자료 쓰기 6회 뒤 valid 3·stale 6·free 3입니다. GC live 복사 1회와 block 3페이지 ERASE 뒤 valid 3·stale 4·free 5가 됩니다. 자료 24바이트에 복사 4바이트가 더해진 비율은 28/24=7/6입니다. seed·metadata·ERASE 사건·ECC·장치 내부 기록을 제외한 자체 계산이며 실제 WAF 측정이 아닙니다.

같은 trace에서 TRIM·회수 후 PPN0을 LPN2·incarnation 13으로 재사용했습니다. LPN0은 None·version 4입니다. 별도 부하는 free PPN11 하나가 victim block3 안에 있어 NO_GC_TEMP_SPACE를 확인하고, stale-only block0을 회수해 free 4를 얻었습니다. host reserve 1페이지가 모든 victim의 처리를 보장하지 않는 반례입니다.

## 손상·경계와 결과 보존

다른 LPN·다른 논리 version·다른 incarnation·이전 token 불일치·물리/매핑 CRC·할당된 PPN 재기록·물리 사건 순번·live erase의 9종을 기대 이유로 거부하고 결과에 values가 없는지도 확인했습니다. bool·음수·LPN 3·잘못된 hex·PPN 12·version 0·incarnation 65,536·파일 header·65,536바이트 초과 등 직접 입력 13종과 최대 필드의 32바이트 부호화를 확인했습니다.

inspect는 부족한 마지막 고정 기록을 보류합니다. writer는 TAIL_NEEDS_REPAIR로 멈추며 파일 SHA가 유지됐습니다. 자동 truncation·수리·GC 전체 원자성·자동 재시작 진척은 구현하지 않습니다.

기존 정상 출력 폴더를 다시 지정한 검증기는 종료 2였습니다. 이전 results.json의 전후 SHA는 모두 `809931af9c1a534cac0868a6b696e4b711e5bab024d6254b782029e11b251adf`입니다. 결과 환경·시각·경로가 포함된 해시이므로 독자의 다른 실행과 같아야 하는 값이 아닙니다.

## 읽은 출처와 실행의 경계

2026-10-21에 KIOXIA L2P, November 2023 Rev.1.0 pp.1–3와 GC, April 2023 Rev.1.1a pp.1–3를 읽었습니다. NVMe Base 1.4c의 표지 날짜 2021-03-09, Figure249 DLFEAT와 §6.7/§6.7.1.1도 읽었습니다. URL과 의미는 두 사례 본문에 있으며 비공개 source-review.md·sources.json에는 읽은 범위·접근 제한·보관 원문 SHA가 있습니다.

ERASE는 append 이력의 상태 사건이며 실제 파일의 옛 bytes도 지우지 않습니다. None은 자체 unmapped 정책이고 실제 TRIM read-zero·secure erase가 아닙니다. flush·fsync 성공 뒤 명시적 자식 종료만 실행했으며, OS crash·directory fsync·sector/page tearing·장치 cache·NAND wear/ECC/bad block·실물 전원 시험은 수행하지 않았습니다.
