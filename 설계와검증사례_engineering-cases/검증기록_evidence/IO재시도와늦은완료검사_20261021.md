## 명령과 종료 상태

실행 파일은 위 표의 Python 3.12.14 인터프리터였습니다. 작업 경로는 예제의 `io_retry` 폴더였습니다. 아래 `python` 표기는 해당 실행 파일이며 `OUT`은 위 비공개 결과 경로입니다. 실제 절대 인자 목록과 stderr는 비공개 `verification.json`에 보존했습니다.

```powershell
python -X utf8 -B verify.py --out OUT/normal
python -X utf8 -B -O verify.py --out OUT/optimized
python -X utf8 -B verify.py --mutation callback-filter-only --out OUT/normal-callback-filter-only
python -X utf8 -B -O verify.py --mutation callback-filter-only --out OUT/optimized-callback-filter-only
```

같은 방식으로 나머지 세 변이도 기본·`-O`에서 각각 실행했습니다.

| 실행 | 횟수 | 기대 exit | 실제 결과 |
| --- | ---: | ---: | --- |
| 정상 기본·최적화 | 2 | 0 | 모두 PASS, 각각 82개 검사·45개 계약 거부입니다. |
| 네 변이 × 두 모드 | 8 | 1 | 모두 ERROR이며 의도한 차이를 검사했습니다. |
| 기존 normal·optimized 출력 경로 재사용 | 2 | 2 | 모두 `output already exists`이며 기존 JSON 바이트가 같습니다. |
| LBA 수가 2인 잘못된 fixture | 1 | 2 | `only one four-byte LBA is supported`이며 결과 폴더를 만들지 않았습니다. |

정상 두 실행의 stdout은 다음과 같았습니다.

```text
{"status": "PASS", "checks": 82, "rejections": 45, "issues": []}
```

## 실제 관측값

| 흐름 | 관측값 |
| --- | --- |
| callback만 거르는 경로 | B 완료·C 완료 뒤 `42424242`였으나 옛 A 적용 후 최종 `41414141`입니다. |
| callback만 거르는 경로의 완료 목록 | `["R1", "R2"]`이며 최종 데이터 오류가 남습니다. |
| 장벽과 정지 증거를 사용한 경로 | 최종 `42424242`, R1·R2 모두 SUCCESS, 각각 한 번의 응용 완료입니다. |
| 미해결 A가 남은 때 | retry B·새 R2·실패 포기를 거부했습니다. |
| A 정지 증거 이후 | 옛 A 적용을 거부하고, R1이 성공하기 전 R2도 거부했습니다. |
| 이미 적용한 A 뒤 timeout·정지 | `41414141`을 유지하며 rollback하지 않습니다. |
| 읽기 retry | 옛 slot a·새 slot b를 따로 보유하고 응용 완료는 Q 한 번입니다. |
| 두 번째 시도까지 실패한 뒤 | 정지 확인 후 세 번째 시도를 거부하고 R1 FAILED·R2 SUCCESS를 각각 한 번 알렸습니다. |

## 오류 변이가 실패한 지점

아래 실패는 정상 구현의 결함 보고가 아니라 의도적으로 틀리게 만든 경로의 관측입니다. 두 실행 모드에서 같은 차이를 확인했습니다.

| 변이 | 실제 실패 |
| --- | --- |
| `callback-filter-only` | `retry blocked: invalid event was accepted`입니다. |
| `release-buffer-on-timeout` | `timeout retains slot: {} != {'a': 'A'}`이며 읽기 retry가 옛 slot을 재사용하는 검사도 실패합니다. |
| `unbounded-retry` | `bounded attempt budget: invalid event was accepted`입니다. |
| `accept-stale-callback` | 완료 ID가 `['R1', 'R2', 'R1']`이 되어 리터럴 두 개와 다릅니다. |

완료가 timeout 전·후인 순서, duplicate·wrong ID·wrong generation, 조기 성공 통지, 시도 ID 재사용, 범위를 벗어난 한도·payload·식별자도 검사했습니다. 명시적 `raise AssertionError`와 `ContractError`를 사용하므로 `-O`가 검사를 제거하지 않습니다.

## 출처의 적용 범위

[Linux 6.12 blk-mq 문서](https://docs.kernel.org/6.12/block/blk-mq.html)의 Operation·Tag-based completion, timeout enum, `blk_mq_ops.timeout`, `blk_mq_quiesce_queue`, `blk_mq_start_request` 설명을 읽었습니다. [v6.12 헤더](https://github.com/torvalds/linux/blob/v6.12/include/linux/blk-mq.h)의 timeout enum 주석과 선언도 대조했습니다. 원문 파일과 읽은 범위는 비공개 `sources/`와 `source-review.md`에 있습니다. 자체 `stopped=True` 증거와 상태 `QUIESCED`는 별도 모델 전제이며 커널 queue quiesce의 보장이라고 쓰지 않습니다.

## English

Normal and optimized Python runs each passed 82 checks, including 45 rejected contract violations. Four implementation mutations failed in both modes. Reused output paths and an unsupported fixture were rejected without replacing prior evidence. The callback-only trace ends in `AAAA` despite one completion per application request; the guarded trace ends in `BBBB`. These are deterministic decoded host events, not block-driver, DMA, timing, persistence, or hardware tests.
