# NAND 블록과 교란 모델 검사 / NAND block and read-management checks, 2026-10-21

Python 표준 라이브러리의 결정적 합성 모델을 실행했습니다. raw NAND 명령·MTD·ECC codec·셀 전압·물리 오류율·실물 보드·전원 차단을 실행하거나 측정하지 않았습니다. 6블록×2페이지×4바이트 geometry와 임계값은 자체 학습 계약입니다.

## 환경과 재현 명령

Windows 11 build 10.0.26200·AMD64, Python 3.12.14, MSC v.1944 64 bit에서 실행했습니다. UTF-8/LF를 확인한 소스·fixture로 2026-10-21 05:21:40 UTC에 최종 일반 실행을 시작했습니다. 전체 실행 파일 경로·명령·stdout·stderr·결과 JSON은 비공개 `nand/verification.json`과 각각의 새 출력 폴더에 보존했습니다.

아래는 코드 폴더에서 사용할 재현 명령입니다. C:/temp는 독자가 정할 새 경로의 예입니다.

```powershell
python -X utf8 -B runner.py --out C:/temp/nand-normal-new
python -X utf8 -B -O runner.py --out C:/temp/nand-optimized-new
python -X utf8 -B runner.py --mutation nand-zero-to-one --out C:/temp/nand-bits-fault-new
python -X utf8 -B runner.py --mutation reuse-bad --out C:/temp/nand-pool-fault-new
python -X utf8 -B runner.py --mutation early-remap --out C:/temp/nand-map-fault-new
python -X utf8 -B runner.py --mutation publish-ue --out C:/temp/nand-ue-fault-new
python -X utf8 -B runner.py --mutation skip-scrub --out C:/temp/nand-scrub-fault-new
```

변이는 모두 `-O`로도 새 폴더에서 실행했습니다. 정상 2회와 오류 변이 10회를 구분했습니다. `require()`는 명시적으로 AssertionError를 발생시키며 `-O`에서 사라지는 assert 구문에 의존하지 않습니다. `-B`는 bytecode 파일 생성을 막습니다. 실제 실행 출력도 UTF-8로 처리했습니다.

## 마모와 자료량의 리터럴 결과

factory bad는 블록 5입니다. 정상 블록 0~4의 초기 소거 이력은 `[0,4,4,4,4]`로 입력했습니다. cold=블록 0, hot=블록 1의 초기 자료를 준비한 뒤 카운터를 재설정해 hot 갱신 네 번을 비교했습니다. 이 초기 이력은 실제 장치의 사용 로그가 아닙니다.

| 항목 | 동적 선택 | 정적 이동 1회 후 동적 선택 |
|---|---|---|
| 추가 정적 이동 | 없습니다. | cold 0→2, 원래 0의 erase가 1입니다. |
| hot 목적지 | 2, 3, 4, 1입니다. | 0, 3, 0, 4입니다. |
| 최종 논리→물리 매핑 | 0→0, 1→1입니다. | 0→2, 1→4입니다. |
| 최종 정상 블록 소거 이력 | `[0,5,5,5,5]`입니다. | `[3,5,4,5,4]`입니다. |
| 소거 이력의 최대−최소 | 5입니다. | 2입니다. |
| host_bytes | 32입니다. | 32입니다. |
| move_bytes | 0입니다. | 8입니다. |
| program_attempt_bytes | 32입니다. | 40입니다. |
| erase_attempts | 4입니다. | 5입니다. |
| program/host 비율 | 1.0입니다. | 1.25입니다. |

cold 자료 `10203040`·`50607080`, 마지막 hot 자료 `44444444`·`dddddddd`가 두 정책 모두 일치했습니다. 성공 비교 창의 계산은 32/32와 40/32입니다. program 시도량은 실패도 세지만 위 창에는 실패가 없습니다. 초기 seed·metadata·ECC/OOB를 제외하므로 제품 전체 WAF 측정값으로 쓰지 않습니다.

| 경로 | 실제 관측 |

읽기 횟수는 호스트·원본 복사·목적지 검증의 물리 페이지 읽기 경로를 합쳐 셉니다. 실제 NAND의 행별 노출이나 오류율을 계산하지는 않습니다. CE/UE는 입력한 telemetry입니다. UE에서 원본 배열·매핑을 유지한 사실과 그 자료의 복구 가능성은 구분합니다. 모델은 UE 자료를 공개하지 않습니다.

## 경계·결과 보존·별도 대조

33개 입력·상태 거부를 기대한 ContractError 이유와 비교했습니다. 범위 밖/boolean 주소, 잘못된 페이지 자료, 중복 seed, 페이지 순서, 재프로그램, bad block 접근, 범위 밖 CE, UE와 확정 정정 개수의 충돌, 잘못된 fault, 여유 공간 없음 등을 포함합니다. 잘못된 telemetry가 읽기 계수나 매핑을 바꾸지 않는지도 대조했습니다.

별도 `factory_bad=[]` 구성에서 바이트 0~255를 물리 블록 5의 페이지 0·1에 프로그램하고 소거해 256경계를 확인했습니다. program 뒤 바이트와 erase 뒤 FF를 각각 검사했습니다. 본래 factory bad 5를 되살린 것이 아니라 다른 시험 구성입니다.

기존 정상 결과 폴더 재사용은 exit 2였고 이전 result.json 바이트가 유지됐습니다. `{"schema":1}`만 있는 fixture도 exit 2로 거부되었고 출력 폴더가 생기지 않았습니다.

공개 runner 외에 다른 입력으로 API를 직접 대조했습니다. 초기 이력 `[1,6,5,4,3,0]`의 정적 목적지 2·후속 동적 목적지 0, 다른 payload 보존, CE 한계 3의 직전/경계, 목적지 검증 실패 후 다른 후보로 재이동, UE 후속 비공개, bit 0→1 거부 등을 리터럴로 확인했습니다. 실행 종료·LF·해시·결과 보존과 이 별도 대조를 합친 private 검증은 64건·실패 0건입니다. 공개 runner의 바이트 256개와 중복 합산한 장치 적합성 수치로 쓰지 않습니다.
