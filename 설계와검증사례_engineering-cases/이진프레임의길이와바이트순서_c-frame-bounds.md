# 이진 프레임의 길이와 바이트 순서 / Binary frame bounds and byte order in C

길이 필드가 들어 있는 프레임을 받았다고 해서 그 필드가 말하는 양만큼 데이터가 도착한 것은 아닙니다. 이 사례는 C로 작성한 파서에서 길이 계산, 정수의 표현 범위, 바이트 순서를 각각 검사하는 방법을 다룹니다. 교육용 결함을 직접 넣어 비교했으며, 기존 프로젝트에서 발견한 장애나 실제 보드의 통신 오류로 소개하지 않습니다.

[실행 코드](../예제_examples/실무검증_practical-validation/native_firmware/frame_bounds.c), [공통 실행 방법](../예제_examples/실무검증_practical-validation/native_firmware/README.md), [2026-10-21 실행 기록](검증기록_evidence/C펌웨어경계검사_20261021.md)을 함께 볼 수 있습니다.

## 1. 먼저 프레임 계약을 정합니다

자체 예제는 처음 4바이트에 원소 수 `count`를 넣고, 그 뒤에 원소당 2바이트인 부호 없는 샘플을 넣습니다. 두 필드 모두 작은 자릿수 바이트를 먼저 보내는 little-endian입니다. 예를 들어 정수 `0x1234`는 `34 12`로 전송합니다. CPU 자체의 바이트 순서와 독립된 통신 규칙입니다.

| 항목 | 이 예제의 계약 |
| --- | --- |
| 헤더 | 원소 수를 나타내는 32비트 부호 없는 정수, 4바이트 |
| 본문 | 원소마다 16비트 부호 없는 샘플, 2바이트 |
| 입력 단위 | 한 프레임 전체이며 뒤에 다른 프레임을 붙이지 않습니다. |
| 원소 수 | 0부터 1,024까지 허용합니다. |
| 성공 조건 | 실제 길이가 `4 + count × 2`와 정확히 같습니다. |
| 실패 시 | 본문을 읽지 않으며 출력 원소 수를 변경하지 않습니다. |

이 계약에서는 빈 프레임도 4바이트입니다. 길이 3인 입력은 헤더조차 부족합니다. 길이 5이고 원소 수가 0인 입력도 남는 1바이트 때문에 거부합니다. TCP 스트림처럼 여러 프레임을 이어 받는 프로그램이라면 소비한 바이트 수를 돌려주는 별도 조립 계층이 필요합니다. 현재 파서의 정확한 길이 비교를 스트림 전체 길이 비교로 옮기면 정상적인 다음 프레임까지 오류로 오인할 수 있습니다.

## 2. 길이의 곱셈부터 하면 생기는 문제

잘못된 경로는 필요한 길이를 넓은 정수로 계산한 뒤 `uint32_t`로 좁힙니다. `uint32_t`는 이 환경에서 정확히 32비트인 부호 없는 정수형입니다. 값이 이 형의 범위를 벗어나면 변환 결과에는 나머지만 남습니다. 이 사례는 정의되지 않은 signed overflow를 실행하지 않습니다. unsigned 변환의 규칙은 [C11 초안 N1570의 6.3.1.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)에 근거합니다.

```c
uint32_t required = (uint32_t)((uint64_t)4 + (uint64_t)count * 2);
// uint64_t로 계산해도 마지막 uint32_t 변환에서 상위 비트를 버립니다.
return required == available;
// ==는 같음 비교입니다. 이미 잘린 길이를 비교하면 잘못 승인할 수 있습니다.
```

헤더가 `00 00 00 80`이면 little-endian 원소 수는 2,147,483,648입니다. 수학적인 길이는 `4 + 2,147,483,648 × 2 = 4,294,967,300`바이트입니다. 이를 32비트 부호 없는 값으로 좁히면 4가 됩니다. 실제로 4바이트만 받은 입력이 길이 검사에서 통과합니다. 프로그램이 곧바로 그 원소 수만큼 읽는다면 범위 밖 접근으로 이어질 수 있으므로, 예제는 승인 여부까지만 비교하고 잘못 승인된 본문은 읽지 않습니다.

실무에서 `size_t`로 바꾸는 것만으로 끝내기 어려운 이유도 같습니다. `size_t`는 객체 크기를 표현하는 형이지만 무한히 큰 정수가 아닙니다. 다른 플랫폼이나 다른 원소 크기에서는 그 형의 곱셈도 표현 범위를 넘을 수 있습니다. 계산 전에 곱셈의 상한을 정하는 것이 핵심입니다.

## 3. 실제 남은 공간으로 먼저 제한합니다

```c
if (available < HEADER) return false; // if는 조건 분기이며 뺄셈 전에 헤더 길이를 확인합니다.
uint32_t count = read_u32_le(p); // 바이트 배열을 통신 규칙에 맞게 정수로 조립합니다.
size_t room = (available - HEADER) / ITEM; // /는 정수 나눗셈이며 들어갈 수 있는 원소 수를 구합니다.
if ((uintmax_t)count > (uintmax_t)room) return false; // 넓은 부호 없는 형에서 개수와 공간을 비교합니다.
if (count > MAX_ITEMS) return false; // 메모리에 들어가더라도 서비스의 개수 상한을 적용합니다.
size_t required = HEADER + (size_t)count * ITEM; // 공간 검사 뒤에 곱셈하므로 available을 넘지 않습니다.
if (required != available) return false; // !=는 다름 비교이며 남는 바이트도 거부합니다.
*count_out = count; // *는 포인터가 가리키는 출력 변수에 값을 기록합니다.
return true; // 앞의 계약을 만족한 경우에만 성공합니다.
```

순서가 중요합니다. 헤더가 4바이트 이상인지 먼저 확인해야 `available - 4`가 0 아래로 내려가는 unsigned 뺄셈을 피할 수 있습니다. 그다음 `(available - 4) / 2`보다 큰 원소 수를 거부합니다. 이 검사를 통과하면 `count × 2`가 남은 공간 안에 들어간다는 근거가 생깁니다. 1,024개 정책은 그 후에 적용하며, 계산 안전성과 업무 정책을 서로 다른 조건으로 남깁니다.

이 함수는 `p`가 `available`바이트의 실제 메모리를 가리킨다는 호출자 계약을 전제로 합니다. 숫자 길이만 전달한다고 포인터의 실제 할당 크기를 알아낼 수는 없습니다. DMA 완료 길이, 드라이버 수신 길이, 버퍼 할당 크기의 관계는 호출 계층에서도 확인해야 합니다.

## 4. 바이트 순서를 명시적으로 읽습니다

```c
return (uint32_t)p[0] | ((uint32_t)p[1] << 8) |
       ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24);
// []는 배열 원소 접근, <<는 왼쪽 비트 이동, |는 각 비트의 OR 연산입니다.
// 이동 전에 uint32_t로 바꾸어 상위 바이트를 원하는 32비트 위치에 놓습니다.
```

버퍼를 `uint32_t *`로 강제 변환해 읽는 방식은 사용하지 않습니다. 시작 주소의 정렬 조건, 별칭 규칙, CPU 바이트 순서가 통신 계약에 섞이기 때문입니다. `memcpy`로 정수에 복사하더라도 통신 바이트 순서 변환까지 자동으로 해결되는 것은 아닙니다.

첫 샘플 `34 12`를 올바르게 읽으면 4,660입니다. 반대로 읽으면 `0x3412`, 즉 13,330이 됩니다. 두 값 모두 16비트 범위에 들어가므로 길이 검사가 이 오류를 잡아 주지 못합니다. 따라서 알려진 패턴을 넣는 검사와 길이 경계 검사를 별도로 둡니다. 같은 이유로 CRC가 맞더라도 수신 후의 정수 해석이 옳다는 보장은 없습니다.

## 확인 문제

1. 4바이트 헤더에 원소 수 3이 있고 전체 길이가 9바이트면 왜 거부합니까?
2. `count`를 먼저 `size_t`로 바꾸는 것과 나눗셈으로 상한을 확인하는 것의 차이는 무엇입니까?
3. 길이와 CRC가 맞는데 샘플의 숫자가 이상하면 무엇을 비교해야 합니까?

답: 1. 필요한 길이는 10바이트이므로 샘플 1바이트가 부족합니다. 2. 형 변환은 표현 범위만 바꾸며 그 범위 안이라는 근거를 만들지 않습니다. 상한 검사는 실제 버퍼 안에 들어감을 먼저 확인합니다. 3. 알려진 바이트 패턴, 필드 폭, 부호 해석, 바이트 순서와 단위를 비교합니다.

## English

This deliberately faulty C fixture narrows a calculated frame length to 32 bits and accepts a four-byte header advertising 2,147,483,648 samples. The corrected parser checks header availability, divides remaining storage by item width, applies the application limit, and finally requires an exact frame length. An independent known-pattern check catches the reversed interpretation of `34 12`. The host run covers 16,496 count/length combinations; it does not establish device timing, transport integrity, or exhaustive protocol correctness.
