# Verilog·SystemVerilog·아날로그 모델의 연결 / RTL, verification and mixed-signal models

칩의 동작을 설명하는 코드와 그 동작을 검사하는 코드는 목적이 다릅니다. 같은 `.sv` 확장자를 사용해도 하나는 회로로 합성할 설계이고, 다른 하나는 컴퓨터에서 실행하는 시험 환경일 수 있습니다. 이 글은 그 경계와 디지털·아날로그 블록 사이에 전달하는 모델을 설명합니다. 공개 문서 확인일은 2026-10-26입니다. 아래 코드와 계산은 학습용으로 구성했으며 상용 도구 실행이나 칩 제작 결과가 아닙니다.

## 1. RTL은 시간에 따라 상태가 바뀌는 회로 설명입니다

RTL(register-transfer level)은 레지스터에 저장한 상태와 그 사이의 논리 연산으로 회로를 설명하는 수준입니다. 레지스터는 클록 사건에 맞춰 값을 저장하고, 조합논리는 현재 입력에서 출력을 계산합니다. 프로그램 문장이 위에서 아래로 실행된다는 설명만으로는 여러 회로가 동시에 동작하는 관계를 이해하기 어렵습니다.

Verilog는 회로의 구조와 동작을 기술하는 언어입니다. SystemVerilog는 여기에 설계 표현과 검증 기능을 더한 언어입니다. `logic`, `always_comb`, `always_ff` 같은 설계 표현과 클래스·무작위 시험·시간적 속성 검사를 함께 제공하지만, 모든 문법이 물리 회로가 되는 것은 아닙니다. 합성 가능 여부는 대상 하드웨어와 합성 도구의 지원 범위까지 확인합니다. 예를 들어 [Yosys 0.49의 `read_verilog` 설명](https://yosyshq.readthedocs.io/projects/yosys/en/v0.49/cmd/read_verilog.html)은 자체 프런트엔드의 SystemVerilog 지원을 일부 기능으로 한정합니다. 이 판본의 설명을 모든 도구와 후속 판본의 지원표로 사용하지 않습니다.

| 구분 | 하는 일 | 결과의 의미 |
|---|---|---|
| 합성 대상 RTL | 상태·연산·연결을 표현합니다. | 합성기가 이를 해석해 논리 셀로 구현합니다. |
| 테스트벤치 | 입력·클록·리셋을 만들고 결과를 검사합니다. | 지정한 시험에서의 동작을 관찰합니다. |
| Assertion | 유지해야 할 조건과 시간 관계를 표현합니다. | 시뮬레이션이나 형식 검증에서 조건을 검사합니다. |
| UVM 환경 | 시험 생성·구동·관찰·비교를 재사용 가능한 구성으로 묶습니다. | 큰 검증 환경을 조직하는 방법입니다. |

`#10`으로 시뮬레이션 시간을 기다리는 문장, 파일을 읽어 시험값을 만드는 코드, UVM 클래스 객체를 생성하는 코드를 그대로 표준 셀 회로의 구현으로 보면 안 됩니다. 반대로 `for`문처럼 프로그램에서 익숙한 문법도 정해진 반복 범위의 회로 전개에 쓰일 수 있습니다. 문법 이름보다 하드웨어로 무엇이 남는지 확인합니다.

## 2. 값을 저장하는 회로와 유지 조건을 함께 읽습니다

다음은 클록 상승 에지에서 `en=1`이면 `d`를 저장하는 자체 SystemVerilog 예입니다. 공식 제품의 코드 발췌가 아니며, 문법과 상태 변화의 대응을 보이기 위해 작성했습니다.

```systemverilog
module hold_bit (                         // module로 한 회로 블록의 경계를 정의합니다.
    input  logic clk, rst_n, en, d,        // input은 외부 입력이며 logic은 4상태 값을 표현합니다.
    output logic q                        // output q는 이 블록이 내보내는 저장값입니다.
);                                        // 포트 목록을 닫습니다.
    always_ff @(posedge clk or negedge rst_n) // 상승 클록과 비동기 리셋 하강에 반응합니다.
        if (!rst_n) q <= 1'b0;            // 리셋이 0이면 1비트 0을 비차단 대입으로 예약합니다.
        else if (en) q <= d;              // en이 1인 클록 사건에서 d를 다음 q로 저장합니다.
endmodule                                 // 블록 정의를 끝냅니다.
```

`<=`는 비차단 대입입니다. 같은 클록 사건에서 여러 레지스터가 이전 상태를 기준으로 다음 상태를 계산하는 표현에 사용합니다. `en=0`인 경우 대입이 없으므로 이 순차 회로는 값을 유지합니다. 조합논리에서 필요한 대입을 빠뜨려 의도하지 않은 래치를 만드는 문제와 구분합니다. `always_ff`를 썼다는 사실만으로 리셋 해제·클록 품질·타이밍까지 검증된 것은 아닙니다.

| 자체 입력 순서 | 클록 직전 조건 | 사건 뒤 기대하는 q |
|---|---|---|
| 리셋 | `rst_n=0` | 0입니다. |
| 저장 | `rst_n=1, en=1, d=1` | 1입니다. |
| 유지 | `rst_n=1, en=0, d=0` | 이전 값 1입니다. |

이 표는 예상 동작이며 실행 로그가 아닙니다. 실제 테스트벤치에서는 에지와 같은 순간에 입력을 바꾸는 경쟁을 피하고, 출력 관찰 시점과 시뮬레이터 시간 단위를 정합니다. 비동기 리셋을 해제하는 회로에는 별도의 리셋 도메인·타이밍 검토가 필요합니다.

다음 속성은 같은 `clk`, `rst_n`, `en`, `q`가 보이는 검증 범위에 두는 자체 예입니다. 앞 에지에서 `en=0`이었다면 다음 에지에서 관찰하는 `q`가 유지되는지를 검사합니다.

```systemverilog
property p_hold;                           // property로 시간적 조건에 이름을 붙입니다.
    @(posedge clk) disable iff (!rst_n)    // 클록 에지에서 샘플링하며 리셋 중에는 검사를 중단합니다.
    !en |=> $stable(q);                    // 다음 샘플의 q가 앞 샘플과 같은지 검사합니다.
endproperty                               // 속성 정의를 닫습니다.
assert property (p_hold);                  // 해당 속성을 실제 검사 항목으로 연결합니다.
```

Assertion의 샘플링 시점은 비차단 대입의 갱신 시점과 구분합니다. 이 속성 하나는 `en=1`일 때 올바른 값을 저장하는지, 모든 리셋 순서가 안전한지까지 검사하지 않습니다. 속성이 성공했어도 선행 조건이 한 번도 발생하지 않았을 수 있으므로 조건이 실제로 발생한 시험과 커버리지를 함께 읽습니다. 검증의 기초는 [Assertion·커버리지·형식 검증](../전자컴퓨터공학_ece/14-하드웨어검증_hardware-verification/해설_notes/검증에서무엇을확인했는가_assertions-coverage-formal.md)으로 이어집니다.

## 3. UVM의 시험 객체와 칩 안의 신호를 구분합니다

UVM은 SystemVerilog 클래스 라이브러리와 검증 방법론입니다. 예를 들어 ‘주소 3에 17을 씁니다’라는 트랜잭션을 생성하고, driver가 이를 버스 핀의 변화로 바꿉니다. Monitor는 핀에서 실제 수행된 거래를 읽고, scoreboard는 관측한 결과와 기대 결과를 비교합니다. Driver가 보낸 값만 확인하면 DUT가 무시하거나 잘못 응답한 거래를 놓칠 수 있습니다.

Reference model은 기대 결과를 계산하는 기준 모델입니다. RTL의 조건문을 그대로 복사하면 같은 오류를 둘 다 가질 수 있습니다. 버퍼에서는 들어간 값의 순서와 나간 값의 순서를 비교하는 별도 자료구조가 기준 모델이 될 수 있습니다. DUT의 내부 구현과 검사하려는 외부 계약을 분리하는 이유입니다. [Accellera UVM 1.1 User’s Guide의 3장](https://www.accellera.org/images/downloads/standards/uvm/uvm_users_guide_1.1.pdf)은 driver·sequencer·monitor·agent·환경과 검사 구성을 설명합니다. 이 연결은 방법을 읽는 자료이며 최신 UVM의 모든 API가 같은 판본이라는 뜻은 아닙니다.

SystemVerilog `interface`는 관련 신호와 연결 규칙을 한곳에 묶는 언어 구성입니다. 클래스 기반 시험에서는 virtual interface로 실제 신호 묶음에 접근할 수 있습니다. interface가 존재한다는 것과 아날로그 전압·전류를 연속시간으로 푼다는 것은 다른 문제입니다.

## 4. 메모리와 아날로그 블록에는 서로 다른 모델이 필요합니다

| 모델·파일 | 표현하는 정보 | 그 모델만으로 판단할 수 없는 것 |
|---|---|---|
| 메모리 기능 모델 | 주소·데이터·쓰기 허용·읽기 지연·동시 접근 규칙을 표현합니다. | 비트셀의 읽기 여유·누설·실제 접근 시간을 입증하지 않습니다. |
| 메모리 black box | 블록의 포트와 존재를 남기고 내부 구현을 생략합니다. | 내부 기능·연결이 검사되었다는 뜻이 아닙니다. |
| Liberty `.lib` | 셀의 논리 기능, 타이밍 아크, 전력 등의 특성 정보를 제공합니다. | 트랜지스터 회로 전체나 배치·배선 형상 자체가 아닙니다. |
| LEF·GDS/OASIS | 물리 추상 정보 또는 레이아웃 형상을 제공합니다. | 올바른 읽기·쓰기 프로토콜을 자동으로 보장하지 않습니다. |
| SPICE 모델·넷리스트 | 소자 모델과 연결을 이용해 전압·전류를 계산합니다. | 모든 칩의 긴 소프트웨어 실행을 효율적으로 검사하는 모델은 아닙니다. |
| `real` 기반 RNM | 실수값을 사용해 아날로그 의도를 이산 사건 수준으로 근사합니다. | 실수형이라는 이유만으로 연속시간 회로 해석이 되지는 않습니다. |
| Verilog-A·Verilog-AMS | 아날로그 동작과 혼합 신호 연결을 기술합니다. | 해당 모델이 실제 소자의 모든 잡음·비선형성을 포함한다는 보장은 없습니다. |

타이밍 아크는 입력에서 출력으로의 지연이나 입력과 클록 사이의 setup·hold처럼 분석할 시간 관계를 뜻합니다.

메모리 기능 모델은 특히 read-during-write에서 이전 값·새 값·미정 값 중 무엇을 내는지 명시해야 합니다. 같은 포트 이름이라도 한 사이클 읽기와 조합 읽기는 회로의 동작이 다릅니다. 기능 모델과 `.lib`, LEF, GDS의 모델 이름·핀 이름·비트 폭·전원 핀·판본을 맞춰 전달합니다.

[Accellera UVM-MS 1.0의 용어와 bridge 설명](https://www.accellera.org/images/downloads/standards/uvm-ms/UVM-MS_1.0.pdf)은 RNM/DMS의 `real`·사용자 정의 net type과 클래스·구조 환경의 연결을 구별합니다. 예를 들어 ADC 모델에는 아날로그 입력 범위, 기준 전압, 샘플링 사건, 양자화·포화 규칙과 출력 지연을 정할 수 있습니다. 외부 입력 전압을 정수 코드로 바꾸는 규칙과 트랜지스터 수준의 정착 시간은 별도 비교 대상입니다. AMS 경계에서는 discipline, 연결 모듈, 임계 전압·히스테리시스·전원 꺼짐 상태 등 선택한 도구와 모델의 연결 규칙도 확인합니다.

SDF는 지연·타이밍 검사 값을 시뮬레이션 설계에 주석으로 연결하는 형식입니다. 라이브러리의 특성 모델인 `.lib`, 배선의 저항·정전용량인 SPEF와 역할이 다릅니다. [OpenSTA의 입력 형식 목록](https://openroad.readthedocs.io/en/latest/main/src/sta/README.html)은 Verilog·Liberty·SDC·SDF·SPEF를 나누어 제시합니다. 파일 하나를 다른 역할의 대체물로 넘기면 분석 경계가 사라집니다.

## 5. 다음 단계로 넘기는 파일과 오류 진단

전달 묶음에는 RTL 목록·top module·파라미터·매크로 정의·include 경로, 사용한 메모리·아날로그 모델과 판본, 클록·리셋·전원 조건을 둡니다. 검증 결과에는 시험명·seed·도구 판본·검사 항목·관측 로그를 연결합니다. 파형 파일만 있으면 어떤 기대 조건으로 성공을 판단했는지 알기 어렵습니다.

| 증상 | 먼저 확인할 내용 |
|---|---|
| 시뮬레이션은 되지만 합성이 실패합니다. | 테스트벤치가 설계 파일 목록에 섞였는지, 지원하지 않는 문법·추상 모델인지 확인합니다. |
| 메모리 결과가 한 사이클 어긋납니다. | 기능 모델의 읽기 지연·enable·충돌 규칙과 scoreboard의 비교 시점을 맞춥니다. |
| 출력이 X로 번집니다. | 초기 상태·리셋·미연결 포트·다중 구동·전원 꺼짐 모델을 구분합니다. |
| Assertion이 항상 성공합니다. | 선행 조건의 발생 여부, 비활성화 조건과 샘플링 에지를 확인합니다. |
| RNM은 통과하지만 SPICE에서는 실패합니다. | 모델이 생략한 정착·부하·포화·전원·비선형 조건을 비교합니다. |

도구 이름은 확인된 기능의 예로 읽습니다. [Cadence Xcelium 공개 설명](https://www.cadence.com/en_US/home/tools/system-design-and-verification/simulation-and-testbench-verification/xcelium-simulator.html)은 SystemVerilog·UVM·혼합 신호 기능을 안내합니다. 특정 판본·라이선스의 모든 언어 기능이 제공된다는 보증이나 이 저장소에서 실행한 기록으로 사용하지 않습니다.
