공식 자료 확인일: 2026-10-19입니다. 아래 내용은 특정 배포물의 자료 분석이며, 가중치 추론이나 유료 API 실험 결과는 아닙니다.

## 구조와 용도

Air라는 이름이어도 전체 가중치는 106B입니다. BF16의 단순 payload는 약 212GB가 되므로 활성 12B만 보고 소형 GPU에 모두 들어간다고 판단하면 안 됩니다. 실제 배포에는 양자화·분산·전송량의 조건이 추가됩니다.

## 재현 방법과 비교 항목

공식 배포 지침에서 runtime·모델 revision·FP8 여부를 고정합니다. 도구 선택이 맞는지, 인자 형식이 맞는지, 도구 결과를 반영했는지를 분리해 셉니다. Thinking 모드의 출력 토큰도 예산에 포함합니다.

## 결과를 해석할 때

활성 파라미터 수는 모델 전체 저장량이 아닙니다. 공개 가중치와 서비스 API의 처리 속도를 직접 비교하려면 장치·동시 요청·네트워크 조건이 필요합니다.

## hybrid reasoning은 구조 혼합과 다른 표현입니다

여기서 hybrid reasoning은 thinking과 non-thinking 모드를 선택하는 동작을 가리킵니다. Mamba와 attention을 섞은 네트워크라는 뜻으로 바꾸어 읽지 않습니다. Air의 MoE 구조, 출력 사고 모드, 도구 호출 형식은 서로 다른 구분입니다. [GLM-4.5-Air 개별 카드](https://huggingface.co/zai-org/GLM-4.5-Air#model-introduction)

공식 GitHub 저장소는 현재 4.5뿐 아니라 4.6·4.7도 함께 설명합니다. 4.7의 Preserved Thinking·전용 parser 안내를 제목이 같은 저장소라는 이유만으로 4.5-Air에 적용하지 않습니다. 설치한 runtime과 해당 모델의 parser가 맞아야 사고 텍스트·함수 요청·최종 답을 올바르게 구분할 수 있습니다. [버전별 설명](https://github.com/zai-org/GLM-4.5#model-introduction)

## 직접 만든 조회와 예약의 구분 예

자체 입력은 “내일 오후 2시에 비어 있는 회의실을 알려 주세요. 예약은 하지 마세요.”입니다. 시험지의 기준 날짜를 2026년 11월 2일로 제공하고, 평가용 도구는 조회 함수 `check_rooms`와 예약 함수 `reserve_room`으로 나눕니다. 가정 자료로 다음 날 그 시각의 A실은 사용 중, B실은 비어 있다고 정합니다. 실제 도구 응답·예약·모델 출력을 얻은 예가 아닙니다.

| 단계 | 정답 기준 | 실패 사례 |
| --- | --- | --- |
| 날짜·시간 | 2026년 11월 3일 오후 2시를 사용해야 합니다. | 기준 날짜나 오전·오후를 바꾸면 안 됩니다. |
| 함수 선택 | 조회는 과제에 맞고 예약은 요청 범위를 벗어납니다. | 이름이 비슷한 예약 함수를 골라도 의미상 오답입니다. |
| 자료형 | 조회 인자는 도구 계약의 날짜·시간 형식에 맞아야 합니다. | 자연어 문장을 JSON으로 감싼 것만으로 유효 인자가 되지는 않습니다. |
| 최종 답 | 주어진 자료에서는 B실이 비어 있다고 알려야 합니다. | A실을 추천하거나 예약 완료라고 말하면 오답입니다. |

기준 날짜를 뺀 변형에서는 구체적인 날짜를 정하는 정보가 부족합니다. 이때는 기준 날짜를 확인해야 하며, 모든 필드를 임의로 채운 호출을 성공으로 세지 않습니다. 날짜가 주어진 변형과 주어지지 않은 변형을 나누어 볼 수 있습니다.

이 과제는 유효한 JSON을 생성하는 능력만으로는 충분하지 않음을 보여 줍니다. 도구가 실제로 조회했는지, 결과가 어떤 요청에 해당하는지, 답이 그 결과를 반영하는지까지 분리합니다. 사고 모드에서 더 긴 글이 나와도 이런 조건을 지키지 않으면 정답이 아닙니다. 실제 실행 없이 위 판정표만으로 모델의 성공률을 보고하지 않습니다.
