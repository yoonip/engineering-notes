# DeepSeek-V3.2: 희소 어텐션과 도구 사용 중 추론의 연결

DeepSeek-AI와 공동저자들의 「DeepSeek-V3.2: Pushing the Frontier of Open Large Language Models」는 2025년 12월 2일 제출된 기술 보고서입니다. [arXiv 기록](https://arxiv.org/abs/2512.02556), [공식 저장소](https://github.com/deepseek-ai/DeepSeek-V3.2)를 기준으로 읽습니다. 저자 집단과 소속은 DeepSeek-AI입니다. 여기서는 학회 채택을 추정하지 않으며, 일반 V3.2와 높은 추론 계산을 사용하는 Speciale의 결과를 구분합니다.

## 원문 구조와 세 가지 축

1절은 개요, 2절은 DeepSeek Sparse Attention과 연속 사전학습·비용, 3절은 강화학습·도구 사용·합성 과제, 4절은 평가, 5절은 한계와 향후 연구입니다. 부록은 MLA 모드, 템플릿, 평가 절차와 저자 목록입니다. 긴 입력에서 참조할 토큰을 고르는 계산과, 도구 호출 중 추론 문맥을 유지하는 규칙, 검증 가능한 과제 생성이 함께 제시됩니다. [원문 2–4절](https://arxiv.org/pdf/2512.02556)

핵심 어텐션은 선택한 k개를 사용하지만, 인덱서의 복잡도는 여전히 길이의 제곱이라고 원문이 밝힙니다. 전체 구조를 아무 조건 없이 선형 시간이라고 적으면 정확하지 않습니다.

## 희소성과 인덱서의 뜻

희소는 가능한 모든 관계를 같은 방식으로 계산하지 않고 일부를 선택한다는 뜻입니다. 인덱서는 현재 질의가 과거 어떤 항목을 참조할지 점수를 매기는 부분입니다. 검색에서 문서를 고르는 것과 비슷한 직관을 주지만, 인터넷 검색을 호출하는 외부 도구와 같은 것은 아닙니다.

상위 k 선택은 점수가 큰 k개를 남기는 절차입니다. 선택 단계가 어떤 정보를 놓치면 뒤의 본 어텐션도 그 항목을 사용할 수 없습니다. 따라서 비용을 줄이는 정도와 선택의 품질을 함께 평가해야 합니다. 후보 선택 비용이 사라진다는 뜻도 아닙니다.

## 직접 계산하는 긴 입력의 두 비용

설명용으로 입력 길이 L=10000, 선택 수 k=100이라고 두겠습니다. 모든 쌍은 1억 개이고, 선택 후 본 어텐션의 관계 수는 약 100만 개입니다. 이 두 수만 보면 100배 차이입니다. 그러나 인덱서가 모든 후보를 비교한다면 그 앞 계산의 제곱 항은 남습니다.

```math
L^2=10^8,\qquad Lk=10^6
```

| 부분 | 단순 관계 수 | 해석 |
| --- | --- | --- |
| 전체 쌍 | 100000000 | 선택 없는 비교 기준입니다 |
| 선택 후 본 계산 | 1000000 | 인덱서 비용은 포함하지 않았습니다 |

작은 인덱서의 한 관계 계산이 본 어텐션보다 가벼울 수 있으므로 실제로 빨라질 수 있습니다. 하지만 이것은 전체 점근적 차수와 같은 말은 아닙니다. 실제 배포 비용은 길이, GPU, 커널, 배치와 함께 측정해야 합니다. 이 표는 원문의 서비스 가격이나 실측 시간이 아닌 자체 계산입니다.

## 도구 호출의 문맥을 따라가기

사용자가 “자료에서 합계를 구하고 틀린 행을 설명해 주세요”라고 요청했다고 가정하겠습니다. 모델은 자료 읽기 도구를 호출하고, 도구 결과를 받은 뒤 계산 도구를 부를 수 있습니다. 요청, 도구 호출, 도구 결과는 서로 다른 메시지 역할입니다.

원문은 새 사용자 메시지가 들어오면 과거 추론 내용을 제거하되 도구 호출과 결과는 남기고, 도구 관련 메시지만 추가되면 추론을 유지하는 규칙을 설명합니다. 도구 결과를 사용자 메시지로 흉내 내는 프레임워크에서는 같은 효과를 얻기 어렵다고 밝힙니다. [원문 3.2.1절](https://arxiv.org/pdf/2512.02556)

따라서 모델이 좋은 성능을 보였다는 표만 옮기고 메시지 역할을 임의로 바꾸면 같은 조건을 재현한 것이 아닙니다. 기억한 추론을 유지하는 정책과, 사용자에게 추론 전문을 공개하는 정책도 서로 다른 문제입니다.

## 합성 과제와 검증 가능한 보상

합성 과제는 프로그램이나 모델로 만들어 학습 자료를 늘리는 문제입니다. 자동 검사할 수 있는 답이나 실행 결과가 있으면 강화학습 신호를 만들기 쉽습니다. 그러나 검사가 통과되었다고 현실에서 의도한 작업을 모두 올바르게 수행했다는 뜻은 아닙니다. 검사 규칙의 빈틈을 이용할 수도 있습니다.

직접 만든 예로 합계가 100이면 통과하는 검사만 있다면 모델이 실제 행을 읽지 않고 100을 출력해도 지나갈 수 있습니다. 행별 근거와 입력 변화에 따른 정답 변화도 확인해야 합니다. 훈련용 검증기와 최종 평가기를 분리하는 이유를 보여 주는 사례입니다.

## 결과와 변형을 구분하기

원문은 일반 모델과 Speciale를 나누어 여러 추론·코딩·도구 과제에서 평가합니다. 대회 문제의 점수가 금메달 기준에 해당한다는 주장과, 인간 참가자와 같은 규칙으로 현장에서 수상했다는 주장은 다릅니다. 부록의 평가 방법과 계산 예산을 함께 봐야 합니다. [원문 4절과 부록 D](https://arxiv.org/pdf/2512.02556)

보고서는 지식 범위와 토큰 효율, 복잡한 에이전트 과제를 한계로 설명합니다. 긴 출력으로 얻은 점수와 빠르게 응답해야 하는 서비스의 효율은 다른 평가입니다. 모든 벤치마크에서 다른 모델을 이겼다는 식으로 초록을 과장해 옮기지 않습니다.

확인된 공개 연결은 공식 코드·가중치와 보고서의 배포입니다. 그 이후 모든 독립 재현과 제품 영향이 확인되었다고 주장하지 않습니다. 이 글은 구조와 자체 예제만 분석했으며 모델 호출, 올림피아드 재평가, 비용 측정을 수행하지 않았습니다.

## 도구의 성공과 과제의 성공

자체 과제에서 파일 읽기 도구가 정상 종료되었다고 하겠습니다. 반환 상태가 성공이어도 잘못된 파일을 읽었거나 필요한 행이 빠졌다면 사용자 요청은 해결되지 않습니다. 도구 실행 성공, 내용 추출의 정확성, 최종 답의 근거 일치를 따로 확인해야 합니다.

예를 들어 합계 계산기가 100을 정확히 계산했더라도 입력에서 제외해야 할 취소 행을 포함했다면 최종 정답은 틀릴 수 있습니다. 계산 도구의 산술 정확도와 입력 선택의 정확성은 다른 항목입니다. 에이전트 과제의 자동 검증에서도 무엇을 성공으로 세는지 명확해야 합니다.

이 구분은 모델을 비난하기 위한 가상의 실패 보고가 아니라 평가 단위를 정의하는 자체 사례입니다. 원문의 도구 사용 점수를 읽을 때도 환경, 허용 호출, 종료 조건을 확인해야 합니다. 이 글은 실제 도구 작업을 실행하거나 보고서의 에이전트 점수를 재현하지 않았습니다.
