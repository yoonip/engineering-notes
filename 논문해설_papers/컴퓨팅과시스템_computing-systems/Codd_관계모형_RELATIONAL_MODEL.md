# Codd: 저장 경로 대신 데이터의 관계를 묻기 | The relational model

E. F. Codd의 「A Relational Model of Data for Large Shared Data Banks」는 Communications of the ACM 13(6), pp.377–387, 1970년 6월에 실렸습니다. [원문](https://cs.uwaterloo.ca/~david/cs848s14/codd-relational.pdf) 마지막 쪽에는 1969년 9월 접수, 1970년 2월 수정으로 표시되어 있습니다. 해설의 주요 위치는 §1.2의 데이터 의존성, §§1.3–1.4의 관계·정규형, §2.1의 관계 연산입니다.

## 저장 구조와 독립적인 질의

학교가 학생 자료를 반별 파일에서 학번별 파일로 옮겼다고 생각해 보겠습니다. ‘어느 수업을 듣는 학생의 이름은 무엇입니까’라는 질문의 뜻은 그대로입니다. 그런데 질문 프로그램이 저장된 순서와 경로를 직접 따라가도록 작성되었다면, 보관 방식을 바꿀 때 프로그램도 고쳐야 합니다.

논문은 사용자가 물리적 표현에 과도하게 의존하지 않도록 데이터를 관계로 다루는 방향을 제안합니다. 관계의 값과 연산을 통해 질문을 표현하고, 내부 표현의 변경과 사용자의 질문을 분리하려는 구상입니다. 표 모양 자체보다 데이터 독립성이 중요한 이유입니다. [원문 §§1.1–1.3](https://cs.uwaterloo.ca/~david/cs848s14/codd-relational.pdf)

| 용어 | 쉬운 뜻 | 구별할 부분 |
| --- | --- | --- |
| 관계 | 정해진 자리의 값들을 묶은 튜플의 집합입니다. | 단순히 두 표 사이의 연결선만 뜻하지 않습니다. |
| 튜플 | 한 개의 사실을 이루는 값 묶음입니다. | 화면에서 보이는 행 순서가 사실의 의미를 정하지는 않습니다. |
| 속성·도메인 | 값의 역할과 그 자리에 허용되는 값의 범위입니다. | 숫자로 저장했다는 이유만으로 학번과 점수를 더할 수는 없습니다. |
| 키 | 각 튜플을 구별하는 값의 조합입니다. | 한 번 관측한 값이 우연히 달랐다는 사실만으로 키가 되지는 않습니다. |
| 조인 | 공통되는 값을 기준으로 관련 사실을 결합하는 연산입니다. | 화면에서 옆에 놓인 두 행을 임의로 붙이는 일이 아닙니다. |

여기서는 설명을 위해 현대적인 이름 붙은 표를 사용합니다. 이것을 원문의 모든 표기 관례나 현재 SQL의 모든 규칙과 동일시하지 않습니다.

## 직접 만든 학생·수강 관계

학생 관계는 `(1, 가)`, `(2, 나)`이고, 수강 관계는 `(1, 회로)`, `(1, 통계)`, `(2, 통계)`라고 정하겠습니다. 앞의 숫자는 같은 의미의 학번입니다. 학생 관계에서는 학번이 한 학생을 구별하고, 수강 관계에서는 한 학생에게 여러 수업이 연결됩니다.

‘통계를 듣는 학생의 이름’을 구하는 과정을 세 단계로 나눌 수 있습니다.

| 단계 | 판단하는 일 | 결과 |
| --- | --- | --- |
| 선택 | 수강 관계에서 수업이 통계인 튜플을 남깁니다. | `(1, 통계)`, `(2, 통계)` |
| 조인 | 남은 학번과 학생 관계의 학번이 같은 사실을 결합합니다. | `(1, 가, 통계)`, `(2, 나, 통계)` |
| 투영 | 질문에 필요한 이름만 남깁니다. | `{가, 나}` |

전체 수강 관계를 먼저 조인하면 세 튜플이고, 그 뒤 통계만 남겨도 두 튜플입니다. 이 작은 사례에서는 같은 답을 얻지만 중간 결과의 크기는 다릅니다. 질문의 뜻을 유지하면서 계산 순서를 정하는 문제와, 데이터가 어디에 저장되어 있는지는 서로 구별됩니다.

학번이 같은 학생 튜플을 두 개 허용하면 조인 결과가 어떻게 달라질지도 생각해 보셔야 합니다. 키에 관한 제약은 보기 좋은 표를 만드는 장식이 아니라, 어떤 결합과 갱신을 올바른 것으로 볼지 정하는 조건입니다.

## 중복 저장과 한 번만 바꾸는 일

학생 이름을 모든 수강 튜플에 반복 저장한다면 가의 이름이 바뀔 때 여러 곳을 수정해야 합니다. 한 곳만 바꾸면 같은 학번에 다른 이름이 남을 수 있습니다. 학생 사실과 수강 사실을 나누고 학번으로 연결하면 이름 변경의 위치를 줄일 수 있습니다.

그렇다고 어떤 표든 무조건 잘게 쪼개면 좋은 것은 아닙니다. 나눈 뒤 원래 사실을 정확히 복원할 수 있는지, 원하는 제약을 어떻게 검사하는지 확인해야 합니다. 이 예의 결합이 의미를 보존하는 이유는 학생 관계의 학번과 수강 관계의 학번이 같은 식별 역할을 하고, 학생 쪽 학번의 유일성을 지킨다고 정했기 때문입니다.

‘정규형’은 모양이 단정하다는 뜻이 아니라 데이터 표현에 관한 특정 조건을 가리킵니다. 1970년 글의 정규형 설명을 오늘날 배우는 여러 정규형 단계 전체로 곧바로 확장하지도 않습니다. 원문 §2의 중복·일관성 논의와 무엇을 연결하는지 먼저 확인합니다. [원문 §1.4·§2](https://cs.uwaterloo.ca/~david/cs848s14/codd-relational.pdf)

## 나눈 두 표를 다시 붙이면 없는 사실이 생길 수 있습니다

다음은 직접 만든 수강·담당 관계입니다. 값 세 개가 함께 하나의 사실을 나타냅니다.

| 학번 | 수업 | 담당자 |
|---|---|---|
| 1 | 통계 | 가 |
| 1 | 회로 | 나 |

이것을 ‘학번·수업’과 ‘학번·담당자’로 나누면 앞 표에는 `(1,통계)·(1,회로)`, 뒤 표에는 `(1,가)·(1,나)`가 남습니다. 학번으로 자연 조인하면 첫 표의 각 행에 뒤 표의 두 행이 모두 맞습니다. 결과는 `2×2=4`개이며 원래 없던 `(1,통계,나)`와 `(1,회로,가)`가 생깁니다. 어떤 수업과 어떤 담당자가 짝이었는지 분해 과정에서 잃었기 때문입니다.

행을 더 얻었으니 정보를 더 알아냈다는 뜻이 아닙니다. 두 표 각각과 모순되지 않는 조합이라도 원래 세 값이 함께 이루던 사실은 아닐 수 있습니다. 원문 §2.1.3의 결합 모호성과 §2.1.4의 connection trap이 연결되는 지점입니다. 연결 경로가 있다는 사실만으로 실제 업무 관계가 모두 성립하지는 않습니다. [원문 인쇄 383–385쪽](https://cs.uwaterloo.ca/~david/cs848s14/codd-relational.pdf)

이번에는 ‘한 수업의 담당자는 반드시 하나입니다’라는 제약을 정하고 ‘학번·수업’과 ‘수업·담당자’로 나누겠습니다. 수업이 같으면 담당자가 하나로 정해지므로 두 행을 정확하게 복원할 수 있습니다. 이런 제약을 함수적 종속이라고 부릅니다. 여기서 함수는 수업이라는 입력에 담당자 값이 하나 대응한다는 뜻이며, 프로그래밍 언어의 함수 호출이라는 뜻만은 아닙니다.

제약은 지금 두 행을 보니 우연히 맞는 규칙과도 다릅니다. 이후 같은 수업에 담당자를 여러 명 허용하는 업무로 바뀌면 이 분해를 다시 검토해야 합니다. 원문에 있는 결합 논의를 현대적인 이름 붙은 관계로 풀어 쓴 자체 예이며, 이 두 행으로 모든 정규형의 판정법을 대신하지는 않습니다.

## 논문의 근거와 구현에서 남는 일

원문은 모형과 연산, 표현의 중복과 일관성을 분석합니다. 이 글의 두 학생 예는 실제 DB 서버에서 측정한 속도 자료가 아닙니다. 결과가 논리적으로 같다는 사실만으로 어느 실행 계획이 모든 환경에서 빠르다고 말할 수는 없습니다. 인덱스, 저장장치와 데이터 분포를 고려하는 구현이 별도로 필요합니다.

관계 모형의 집합과 현재 SQL 결과도 구분해야 합니다. 예를 들어 [PostgreSQL의 SELECT 설명](https://www.postgresql.org/docs/current/sql-select.html)은 기본 중복 유지와 DISTINCT에 의한 제거를 구분합니다. 이름만 투영했을 때의 집합 연산과 SQL의 기본 결과를 같은 것으로 가정하면 중복 수가 달라질 수 있습니다.

확인 가능한 후속 구현은 [IBM의 System R 논문(1976)](https://research.ibm.com/publications/system-r-relational-approach-to-database-management)입니다. 관계형 인터페이스와 데이터 독립성을 구현·평가하는 연구 시스템을 설명합니다. Codd의 개념 제안과 후속 시스템이 처리해야 하는 권한·복구·동시 갱신 문제를 나누어 읽으시면 이론과 구현의 거리가 보입니다.

## 자가 점검

1. 위의 학생·수강 관계를 전체 조인하면 왜 두 행이 아니라 세 튜플입니까?
2. 행의 순서가 바뀌면 같은 관계가 다른 사실이 됩니까?
3. 이름이 같은 학생 두 명의 이름만 집합으로 투영하면 원소는 몇 개입니까?
