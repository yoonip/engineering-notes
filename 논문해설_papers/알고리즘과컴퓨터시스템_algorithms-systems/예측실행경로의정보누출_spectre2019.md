# 예측한 경로에서 새는 정보 / Spectre and speculative execution

배열 범위를 검사한 소스 코드가 정상 결과에서는 잘못된 값을 반환하지 않더라도, CPU가 예측으로 잠깐 진행한 경로의 흔적은 남을 수 있습니다. Spectre는 제어 흐름의 검사와 데이터의 관측 가능성을 함께 분석해야 하는 이유를 보여 줍니다.

## 예측과 실제 분기 결과

원문은 조건 분기와 간접 분기의 잘못된 예측을 이용하여 피해 문맥의 데이터를 내부 흔적으로 전달하는 방식을 설명합니다. 네이티브 코드·당시 브라우저·커널 인터페이스 등의 실증과 대응 방안을 제시합니다. 일부 추가 변형은 실험한 공격이 아닌 가능한 방향으로 구분됩니다. 다음 인덱스와 확률은 자체 예제이며 공격 프로그램을 실행한 결과가 아닙니다.

분기 예측기는 다음에 어느 경로를 실행할지 과거 정보 등을 바탕으로 예상합니다. 직접 분기는 목적지가 명령에 정해져 있고, 간접 분기는 레지스터나 메모리 값 등으로 목적지를 구합니다. 조건이 맞을지 예측하는 문제와, 다음 목적지가 어디인지 예측하는 문제는 서로 다른 형태입니다.

자체 예로 공개 배열의 유효 인덱스를 0–7이라고 하겠습니다. 프로그램은 범위 안이면 값을 읽고, 아니면 거절하도록 작성되어 있습니다.

| 실제 범위 판정 | CPU가 먼저 예측한 경로 | 정상 결과와 내부 실행의 관계 |
| --- | --- | --- |
| 허용 | 허용 | 읽기를 진행하고 결과를 채택합니다. |
| 허용 | 거절 | 예측 오류를 되돌리고 허용 경로를 수행합니다. |
| 거절 | 거절 | 읽지 않고 거절합니다. |
| 거절 | 허용 | 일시적으로 읽는 경로에 들어갔다가 결과를 취소할 수 있습니다. |

마지막 행에서는 최종 응답이 거절이어도, 일시적으로 읽은 데이터가 관측 가능한 흔적에 영향을 주었는지 따로 봐야 합니다. 예상과 실제가 다르다는 사실만으로 누출이 완성되는 것은 아닙니다. 비밀에 도달하는 경로와 외부로 정보를 전달하는 경로가 이어져야 합니다.

## 범위 밖과 권한 밖은 같은 말이 아닙니다

배열 8칸의 범위를 벗어났다고 반드시 하드웨어 페이지 접근 권한도 위반하는 것은 아닙니다. 같은 프로세스 안에서 배열 뒤의 데이터가 정상적으로 매핑되어 있고 피해 프로그램에는 읽기 권한이 있을 수 있습니다. 언어·샌드박스가 부여한 논리적 범위와 CPU 페이지 권한은 다른 경계입니다.

Spectre의 피해 코드는 자기 권한으로 읽을 수 있는 정보를, 정상 의미상 실행하지 않아야 할 경로에서 사용할 수 있습니다. [Meltdown](취소된실행과캐시정보누출_meltdown2018.md)의 권한 없는 매핑 접근과 관련되지만, 같은 조건의 공격으로 합쳐서는 안 됩니다. 커널 매핑을 줄이는 대응이 피해 프로세스 안의 잘못된 추측 경로까지 자동으로 없애지는 않습니다.

가젯 gadget은 작은 코드 조각입니다. 여기서는 일시적으로 실행되어 비밀과 관측 흔적을 연결할 수 있는 조각을 뜻합니다. 디스크의 실행 파일을 공격자가 새로 고쳐야만 존재하는 것은 아닙니다. 이미 있는 코드와 공격자가 영향을 주는 입력·예측 상태의 조합을 살핍니다.

```mermaid
flowchart LR
    A[입력 또는 예측 상태에 대한 영향] --> B[피해 코드가 잘못 예측한 경로]
    B --> C[피해 권한의 비밀을 일시적으로 사용]
    C --> D[캐시 등 관측 가능한 흔적]
    D --> E[반복 관측으로 정보 추정]
    B --> F[나중에 정상 결과는 취소]
```

## 비밀이 흔적까지 도달하는 연결을 봅니다

자체 추상 예에서 숨긴 숫자 6에 따라 관측 버퍼의 6번 구역이 빠른 상태가 된다면, 관측자는 그 구역의 반응을 보고 숫자를 추정할 수 있습니다. 하지만 숨긴 숫자를 읽기만 하고 이후 어떤 관측 가능 상태에도 영향을 주지 못했다면 이 경로의 누출은 완성되지 않습니다.

따라서 검토는 “범위 검사문이 있나요?”에서 끝나지 않습니다. 무엇을 일시적으로 읽을 수 있는지, 그 값이 주소·계산 시간·공유 자원에 영향을 주는지, 관측자는 그 차이를 어느 문맥에서 볼 수 있는지를 연결해 적어야 합니다. 분기를 제거했다는 한 사실만으로 모든 데이터 의존적 흔적을 없앴다고 판단할 수도 없습니다.

반복 관측은 작은 차이를 더 분명하게 만들 수 있습니다. 자체 독립 오류 모형에서 한 번 비트 판정이 90% 맞고 세 번의 다수결을 사용하면, 정답 확률은 0.9³+3×0.9²×0.1=97.2%입니다. 실제 오류가 독립이고 같은 정확도를 가진다는 가정은 별도 검증 사항입니다. 타이머를 거칠게 만들어 한 번의 측정을 어렵게 하는 것과 정보 통로를 없애는 것은 다르다는 점을 보여 주는 계산입니다.

## 방어를 어디에 두나요

방어는 공격의 서로 다른 연결을 끊을 수 있습니다.

| 방어 위치 | 검토할 질문 |
| --- | --- |
| 경로의 일시적 실행 제한 | 검사 결과가 확정되기 전에 민감한 다음 연산이 실행될 수 있나요? |
| 사용할 데이터 제한 | 일시적 경로에서 비밀이나 잘못된 포인터에 도달하지 못하게 했나요? |
| 예측 상태의 문맥 분리 | 덜 신뢰하는 코드의 예측 정보가 다른 문맥에 영향을 주나요? |
| 관측 통로 제한 | 캐시·시간·다른 공유 자원에 구별 가능한 차이가 남나요? |

인덱스 마스킹의 경우에도 값을 안전한 범위로 만드는 일과 잘못된 요청을 거절하는 API 의미는 다릅니다. 길이 8에서 14에 비트 마스크 7을 적용하면 6이 됩니다. 주소 범위는 맞지만 “14를 거절한다”는 원래 요구를 그대로 구현한 것은 아닙니다. 길이가 2의 거듭제곱이 아니면 `길이−1`과의 비트 AND는 나머지 연산과 같지도 않습니다. 예를 들어 7 AND 5는 5지만 7 mod 6은 1입니다.

추측 차단 명령, 데이터 의존성, 컴파일러 변환과 실행 CPU의 의미까지 확인해야 실제 방어가 됩니다. 원문의 제안된 대응을 읽고 소스 코드 어느 줄에 이름만 붙이면 모든 CPU에서 안전하다고 단정하지 않습니다. 간접 분기 대응인 retpoline도 조건 분기 우회의 모든 형태를 해결하는 동일한 조치가 아닙니다.

## 당시 실증과 현재 상태를 구분합니다

원문 브라우저의 버전·타이머·공유 메모리 기능·JIT 동작, CPU의 예측기 공유 조건은 실험 설정입니다. 그 설정의 속도를 현재 브라우저에서 그대로 재현되는 결과로 옮기지 않습니다. 피해 데이터가 같은 프로세스에 있는지 다른 프로세스에 있는지, 공격자에게 VM 내부 관리자 권한을 준 실험인지도 구분해야 합니다.

후속 구현 근거는 [Linux의 Spectre 공식 문서](https://docs.kernel.org/admin-guide/hw-vuln/spectre.html)에서 볼 수 있습니다. 조건 분기와 간접 분기 유형, CPU·소프트웨어 지원과 대응 구성을 따로 설명합니다. 같은 “대응됨”이라는 문구도 적용한 유형과 문맥이 다르므로 시스템 상태를 판단할 때에는 해당 조합을 확인해야 합니다.

이 글의 검토는 논문과 공식 문서의 정보 흐름 분석입니다. 제공된 공격 코드를 실행하거나 현재 하드웨어를 측정하지 않았습니다. [seL4](운영체제커널의구현정확성증명_sel42009.md)의 기능적 정확성 증명과 함께 읽으면, 소프트웨어 명세에 맞는 계산이라는 보장과 시간·마이크로아키텍처 관측까지 포함한 비밀성의 보장이 왜 다른지 생각해 볼 수 있습니다.

## 자기 점검

1. 배열 범위 밖의 주소는 반드시 페이지 접근 권한도 없는 주소인가요?
2. 최종적으로 분기 결과를 취소했으면 그전에 남긴 정보도 자동으로 취소되나요?
3. 길이 8의 인덱스 14를 7로 마스킹하면 원래의 거절 의미도 보존하나요?
