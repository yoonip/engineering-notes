# KPerfIR: GPU의 어느 구간이 시간을 쓰는지 컴파일러로 추적하기

원문은 「KPerfIR: Towards an Open and Compiler-centric Ecosystem for GPU Kernel Performance Tooling on Modern AI Workloads」입니다. Yue Guan, Yuanwei Fang, Keren Zhou, Corbin Robeck, Manman Ren, Zhongkai Yu, Yufei Ding, Adnan Aziz의 연구로 UC San Diego·Meta·George Mason University·OpenAI가 참여했습니다. OSDI 2025 발표 논문입니다. [공식 발표와 자료](https://www.usenix.org/conference/osdi25/presentation/guan), [전체 논문](https://www.usenix.org/system/files/osdi25-guan.pdf)을 참고하실 수 있습니다.

## 전체 시간만 재면 놓치는 것

GPU 커널은 GPU에서 실행하는 계산 단위입니다. 운영체제 커널과 같은 뜻으로 쓰인 말이 아닙니다. 한 커널 안에서도 메모리 읽기, 행렬 곱, 다른 계산이 겹칠 수 있습니다. 전체 시간이 길다는 사실만으로 어느 구간이 병목인지 알기 어렵습니다.

프로파일링은 프로그램이 실행되며 어디에 자원을 쓰는지 관찰하는 일입니다. 이 연구는 성능 도구를 컴파일러와 연결해, 실행 시간과 프로그램의 반복문·계산 영역을 대응시킵니다. IR은 중간 표현으로, 소스와 기계어 사이에서 컴파일러가 프로그램을 다루는 형태입니다.

## 본문의 전개

배경과 동기 절은 기존 도구의 집계값만으로 세밀한 겹침을 해석하기 어려운 상황을 설명합니다. 소프트웨어 파이프라이닝은 한 반복의 계산과 다음 반복의 데이터 준비를 겹칩니다. 워프 특화는 일부 실행 묶음에 생산자, 다른 묶음에 소비자 역할을 맡기는 방식입니다.

설계 절은 Triton의 여러 IR 단계에 기록 연산을 넣고 하위 코드로 변환하는 과정을 제시합니다. 높은 단계에서는 반복문과 텐서의 의미를 알기 쉽지만, 실제 실행 순서는 뒤의 변환에서 달라질 수 있습니다. 낮은 단계에서는 하드웨어에 가깝지만 원래 프로그램 구조와 연결하기 어렵습니다.

시간 측정 도구 절은 기록 버퍼와 추적 재구성을 다룹니다. 측정용 명령을 넣으면 원래 실행도 변합니다. 특히 비동기 작업에서는 대기 시간이 측정 명령 때문에 짧아 보이거나 새 유휴 시간이 생길 수 있어 단순히 타임스탬프를 빼는 것만으로 충분하지 않습니다.

평가 절은 H100과 MI300X 환경에서 GEMM·attention 계열 커널, 기록 비용과 컴파일러 변환의 영향을 살핍니다. 논문이 보고한 평균 오버헤드나 개별 최적화 효과를 모든 커널의 고정 비용으로 일반화하지 않습니다. 논의 절은 공급사 전용 성능 카운터 접근과 다른 작업으로의 확장에 남은 한계를 설명합니다.

## 겹치는 작업을 손으로 계산하기

아래는 원문의 실행 결과가 아니라 설명용 일정입니다. 데이터 준비 8단위, 계산 12단위가 필요한 반복을 세 번 수행한다고 하겠습니다. 겹치지 않으면 `3×(8+12)=60`단위입니다.

이상적으로 다음 데이터를 준비하면서 현재 계산을 할 수 있고 자원 충돌이 없다면, 처음 준비에 8, 세 번의 계산에 36이 필요해 총 44단위가 됩니다. 마지막 계산 이후의 저장이나 다른 준비 비용은 이 예에서 제외했습니다.

| 반복 | 데이터 준비 구간 | 계산 구간 |
|---|---|---|
| 0 | 0–8 | 8–20 |
| 1 | 8–16 | 20–32 |
| 2 | 16–24 | 32–44 |

각 구간 길이의 합이 실제 벽시계 시간과 같지 않은 이유가 겹침입니다. 반대로 준비와 계산이 같은 자원을 두고 경쟁하거나 의존 관계가 있으면 이렇게 겹치지 못합니다. 임계 경로는 최종 완료를 늦추는 의존 경로입니다. 모든 구간을 조금씩 빠르게 만드는 일보다 임계 경로의 대기를 줄이는 일이 중요할 수 있습니다.

## 측정 기록에도 메모리가 필요합니다

기록 하나가 8바이트이고 영역마다 시작·끝 두 개를 저장하는 가상의 형식을 생각해 보겠습니다. 한 반복에 영역이 4개라면 8기록, 즉 64바이트입니다. 4 KiB 버퍼에는 64반복의 기록을 저장할 수 있습니다.

순환 버퍼는 끝에 도달하면 앞부분부터 덮어씁니다. 최근 동작을 볼 수 있지만 전체 실행 이력이 모두 남는 것은 아닙니다. 매번 큰 메모리로 내보내면 이력을 더 보존할 수 있는 대신 기록 자체의 비용이 늘어납니다. 저장 전략이 관찰 가능한 결과의 범위를 바꿉니다.

가상의 원래 실행이 100 μs, 계측 후 110 μs라면 오버헤드는 10%입니다. 계측 실행이 110 μs였다는 이유로 원래 커널의 실행도 110 μs라고 기록하면 안 됩니다. 상대 오차와 오버헤드는 또 다른 값이며, 무엇을 기준으로 나누었는지 확인해야 합니다.

## 이 연구가 주는 읽기 기준

컴파일러와 성능 도구를 연결하면 프로그램의 의도를 잃지 않고 하드웨어 동작을 해석할 가능성이 커집니다. 그러나 하드웨어 고유 카운터를 전부 사용할 수 있다는 뜻이나 공급사 도구가 모두 필요 없다는 뜻은 아닙니다. 공개 논문에서 제시한 프레임워크와 현재 배포된 라이브러리의 API도 버전을 구분해야 합니다.

이 저장소에서는 해당 GPU 실험을 재실행하지 않았습니다. 직접 구성한 일정과 버퍼 계산으로 원리를 설명하며, 논문의 성능 결과는 명시된 하드웨어·작업·컴파일러 조건에서 얻은 보고로 다룹니다.

## 확인 문제

1. 전체 시간 44에 포함된 구간 길이를 더해 60이 나오는 것은 모순인가요?
2. 위의 기록 형식에서 2 KiB 버퍼는 몇 반복을 저장하나요?
3. 측정 명령을 넣은 실행이 원래 실행과 완전히 같다고 가정해도 되나요?

1. 아닙니다. 동시에 진행한 시간을 중복해서 더했기 때문입니다.

3. 안 됩니다. 실행 시간·배치·메모리 사용·명령 순서에 영향을 줄 수 있어 계측의 교란을 확인해야 합니다.
