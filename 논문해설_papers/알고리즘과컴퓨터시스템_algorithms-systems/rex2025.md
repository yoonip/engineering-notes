# Rex: 커널 확장의 안전성을 언어와 실행 환경에 나누어 맡기기

Jinghao Jia, Ruowen Qin, Milo Craun, Egor Lukiyanov, Ayush Bansal, Minh Phan, Michael V. Le, Hubertus Franke, Hani Jamjoom, Tianyin Xu, Dan Williams의 「Rex: Closing the language-verifier gap with safe and usable kernel extensions」는 USENIX ATC 2025 논문입니다. 소속은 University of Illinois Urbana-Champaign, Virginia Tech, IBM T.J. Watson Research Center입니다. [학회 서지](https://www.usenix.org/conference/atc25/presentation/jia), [원문 PDF](https://www.usenix.org/system/files/atc25-jia.pdf), [저자 프로젝트](https://github.com/rex-rs)를 기준으로 읽습니다.

## 원문이 제기하는 문제

1–2절은 커널 확장과 안전성, 3절은 언어와 검증기의 간극, 4절은 안전성 모델, 5절은 설계, 6절은 구현, 7절은 평가, 8–10절은 논의·관련 연구·결론입니다. 인쇄 325–337쪽이 본문이며 학회 표지를 포함한 PDF 쪽수와 다릅니다. eBPF 코드가 언어 규칙에는 맞아도 별도의 바이트코드 검증에서 거절되는 문제를 다룹니다. Rex는 제한된 safe Rust와 안전한 커널 인터페이스, 런타임 검사를 결합합니다. [원문 3–5절](https://www.usenix.org/system/files/atc25-jia.pdf)

이 연구의 안전성 모델은 신뢰한 관리자가 설치한 확장의 프로그래밍 오류를 막는 데 초점이 있습니다. 악의적인 모든 코드를 무권한으로 실행해도 안전하다는 격리 보장을 뜻하지 않습니다.

## 먼저 구분할 용어

커널은 운영체제에서 장치와 메모리, 실행을 관리하는 핵심 부분입니다. 확장은 전체 커널을 다시 만들지 않고 특정 동작에 코드를 덧붙이는 방식입니다. 그 코드가 잘못된 메모리를 바꾸면 다른 프로그램까지 영향을 받을 수 있습니다.

검증기는 코드를 실행하기 전에 특정 조건을 만족하는지 확인하는 장치입니다. 컴파일러는 소스 언어를 다른 실행 형식으로 바꾸며 언어의 규칙도 검사합니다. 언어에서 보장하는 것과 커널 확장이 요구하는 조건이 모두 같은 것은 아닙니다. 메모리 범위를 지키는 프로그램도 무한히 반복할 수 있습니다.

신뢰 컴퓨팅 기반 TCB는 시스템의 보장이 성립하려면 올바르다고 믿어야 하는 구성 요소입니다. 검증기를 없앴다고 신뢰할 대상이 0이 되는 것은 아닙니다. Rex에서는 컴파일러와 커널 래퍼, 런타임의 정확성이 중요해집니다.

## 직접 만드는 배열 접근 사례

길이 8의 자료에 입력 인덱스로 접근하는 코드를 생각해 보겠습니다. 올바른 인덱스는 0부터 7까지입니다. 인덱스가 9일 때 오류 없이 아무 위치나 읽으면 메모리 안전성을 위반할 수 있습니다. 반면 경계 검사가 실패해 패닉을 발생시키는 언어 동작도 커널 전체를 그대로 중단하게 해서는 곤란합니다.

| 확인할 조건 | 필요한 질문 |
| --- | --- |
| 메모리 범위 | 길이 8에서 9번 위치를 읽지 않나요? |
| 오류 처리 | 범위 위반 때 커널이 안전하게 제어를 회복하나요? |
| 자원 정리 | 오류 이전에 얻은 잠금을 해제하나요? |
| 실행 시간 | 끝나지 않는 계산이 다른 일을 막지 않나요? |

이 사례는 실제 Rex나 eBPF 검증기를 실행한 결과가 아닙니다. 한 가지 안전성 조건만으로 나머지를 증명할 수 없다는 자체 분석입니다. 문법적으로 올바르다는 사실과 커널에서 원하는 모든 동작이 안전하다는 사실을 나누어 보실 수 있습니다.

## RAII가 해결하는 것과 남는 것

RAII는 자원 획득과 객체의 수명을 연결하고, 객체가 정리될 때 자원을 반납하도록 만드는 방식입니다. 잠금 보호 객체를 얻은 뒤 작업하다 오류가 나도 적절한 정리 경로를 따라 잠금이 해제되어야 합니다. 정상 반환 경로에서만 해제 코드를 적는 방식보다 예외 경로를 체계적으로 다룰 수 있습니다.

그러나 일반 safe Rust에 속하는 모든 기능이 이 자원 규칙까지 보장하는 것은 아닙니다. 원문 5.1절은 객체의 자동 정리를 피할 수 있는 일부 기능을 Rex에서 제한합니다. 확장 코드의 unsafe 금지와, 커널과 연결하는 신뢰 래퍼 내부의 unsafe 사용도 구분합니다. [원문 5.1–5.5절 및 8절](https://www.usenix.org/system/files/atc25-jia.pdf)

직접 만든 상태표에서 잠금 획득 후 정상 반환, 경계 오류, 시간 제한 종료의 세 경로를 적어 보시면 좋습니다. 각 경로 끝에 잠금이 남는지 확인하면 자원 안전성이 단순히 문법 검사보다 넓은 문제임을 이해할 수 있습니다. 서로 다른 자원 사이의 순환 대기까지 검토하려면 추가 조건도 필요합니다.

## 시간 제한과 종료의 차이

어떤 반복문이 결국 종료한다는 수학적 성질과, 정해진 시간 안에 끝난다는 운영 조건은 다릅니다. 10억 번 반복한 뒤 끝나는 코드라도 시스템에서는 너무 오래 걸릴 수 있습니다. Rex는 런타임의 감시 타이머를 이용해 실행 시간이 긴 확장을 중단하는 쪽을 택합니다.

설명용으로 타이머가 1ms마다 확인하고 허용 시간을 5ms로 정했다고 가정하겠습니다. 시작 시점과 확인 시점이 어긋나면 정확히 5.000ms에 중단된다고 단정할 수 없습니다. 주기적인 검사, 인터럽트가 가능한 실행 문맥, 정리 경로의 비용까지 보아야 합니다. 이 수치는 원문의 타이머 설정이나 측정 지연이 아닌 자체 예제입니다.

검사 빈도를 늘리면 더 자주 제한을 확인하지만 검사 비용이 생깁니다. 한 번의 확인이 0.2µs이고 1ms마다 수행된다는 가정에서는 코어 시간의 단순 비율이 0.02%입니다. 이것만으로 전체 Rex 오버헤드를 계산한 것은 아닙니다. 확장 진입·종료와 자원 처리 등 다른 비용도 남습니다.

## 평가 결과를 읽는 범위

논문은 검증기 우회 수정 사례, 복잡한 BMC 확장의 구현 경험, 매크로·마이크로 벤치마크를 나누어 평가합니다. 해당 8코어 BMC 설정에서 Rex 1.98M RPS와 eBPF 1.92M RPS를 보고합니다. 모든 확장에서 항상 더 빠르다는 결과는 아닙니다. 미시적인 최악 조건의 비용도 따로 분석합니다. [원문 7절](https://www.usenix.org/system/files/atc25-jia.pdf)

두 보고 수치의 비율은 약 1.03125입니다. 이 산술을 곧바로 통계적으로 확정된 3.125% 우위라고 부르려면 변동과 실험 조건이 더 필요합니다. 본문의 결론은 사용성을 높이는 설계가 해당 평가에서 비슷한 수준의 성능을 보인다는 범위로 읽는 편이 적절합니다.

원문 구현은 Linux v6.11과 일부 훅 유형을 대상으로 합니다. 현재 배포되는 모든 Linux 기능을 지원한다는 뜻은 아닙니다. 동적 할당의 당시 제한과 신뢰한 래퍼의 유지보수도 논의합니다. 공개 프로젝트는 확인되지만 이후 제품 전체에 대한 적용률이나 독립 재현 성능은 이 글에서 주장하지 않습니다.
