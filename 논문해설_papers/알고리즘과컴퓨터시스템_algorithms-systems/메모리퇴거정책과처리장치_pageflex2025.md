# PageFlex: 메모리를 내보낼 정책과 페이지 처리 장치를 분리하기

Anil Yelam, Kan Wu, Zhiyuan Guo, Suli Yang, Rajath Shashidhara, Wei Xu, Stanko Novaković, Alex C. Snoeren, Kimberly Keeton의 「PageFlex: Flexible and Efficient User-space Delegation of Linux Paging Policies with eBPF」는 USENIX ATC 2025 논문입니다. 소속은 Google, UC San Diego, University of Washington입니다. [학회 페이지](https://www.usenix.org/conference/atc25/presentation/yelam), [원문 PDF](https://www.usenix.org/system/files/atc25-yelam.pdf)를 기준으로 설명합니다.

## 원문 구조와 문제

1절은 개요, 2절은 페이징의 배경과 기존 방식, 3절은 설계, 4절은 정책 사례, 5절은 구현, 6절은 평가, 7절은 결론입니다. 인쇄 291쪽에서 본문이 시작하며 PDF 첫 장은 학회 표지입니다. 비용이 작은 계층으로 덜 쓰는 메모리를 옮기되, 다시 필요해졌을 때의 지연을 줄이려는 문제입니다. PageFlex는 정책을 빠르게 바꾸면서 Linux의 기존 스왑 장치를 재사용하는 틀입니다. [원문 2–3절](https://www.usenix.org/system/files/atc25-yelam.pdf)

제목에 사용자 공간이 있어도 모든 정책 코드와 페이지 오류 처리가 사용자 프로세스로 옮겨지는 것은 아닙니다. eBPF 이벤트 처리기는 커널 안에서 필요한 정보를 다루고, 사용자 에이전트가 설정과 비동기적인 조치를 연결합니다.

## 페이지와 스왑, 차가운 자료

페이지는 운영체제가 메모리를 관리하는 일정한 크기의 단위입니다. 스왑은 덜 필요한 페이지를 다른 저장 계층으로 내보내 주 메모리를 확보하는 방식입니다. 저장장치로만 내보내는 경우 외에 압축 메모리 같은 계층도 있을 수 있습니다.

차가운 페이지는 최근 접근이 적어 가까운 미래에도 덜 필요할 것으로 추정한 페이지입니다. 실제 온도가 낮다는 뜻은 아닙니다. 다시 접근해 가져와야 하는 사건을 refault라고 부릅니다. 내보내는 양만 최대화하면 앱이 필요한 페이지를 계속 되가져오느라 느려질 수 있습니다.

정책은 무엇을 언제 내보낼지 결정하는 규칙이고, 메커니즘은 실제 이동·매핑·회수 등을 수행하는 장치입니다. 정책을 바꾸고 싶은 사람이 메모리 처리 전체를 새로 구현해야 한다면 개발과 배포가 어려워집니다.

## 직접 만드는 메모리 장부

한 앱이 100페이지를 쓰며, 30페이지를 내보내고 나머지 70페이지를 주 메모리에 남겼다고 가정하겠습니다. 그 뒤 내보낸 것 중 6페이지가 다시 필요해졌다면, 내보낸 페이지 기준 복귀 비율은 6/30=20%입니다. 전체 100페이지 기준으로는 6%입니다.

| 분모 | 계산 | 묻는 질문 |
| --- | --- | --- |
| 내보낸 30페이지 | 6/30=20% | 내보낸 것 중 얼마나 되가져왔나요? |
| 전체 100페이지 | 6/100=6% | 전체 대비 되가져온 양은 얼마인가요? |

어느 쪽이 논문의 평가 비율인지 확인하지 않고 숫자를 비교하면 다른 질문을 섞게 됩니다. 원문은 정해진 작업 집합으로 정규화한 비율 등의 정의를 사용합니다. 위 표는 분모의 차이를 보여 주기 위한 자체 예제이며 실제 PageFlex 워크로드의 결과가 아닙니다.

내보낸 30페이지 중 끝까지 쓰지 않은 24페이지는 주 메모리를 절약하는 데 도움이 될 수 있습니다. 그러나 다시 쓴 6페이지의 지연이 민감한 요청에 몰리면 평균보다 꼬리 지연이 크게 나빠질 수 있습니다. 공간 절약과 응답 시간의 교환을 같이 봐야 합니다.

## 커널과 사용자 에이전트의 역할

PageFlex의 커널 이벤트는 할당·해제·스왑·접근 스캔 등과 관련됩니다. eBPF 처리기가 해당 시점의 정보를 낮은 비용으로 읽고, 맵을 통해 사용자 측과 상태를 공유합니다. 사용자 에이전트는 설정과 복잡한 정책 작업을 수행하며 process_madvise 같은 인터페이스로 페이지 반입·반출을 요청합니다. [원문 3.2절](https://www.usenix.org/system/files/atc25-yelam.pdf)

이 분담은 모든 페이지 오류마다 사용자 프로세스의 동기 응답을 기다리는 구조와 다릅니다. 같은 정책을 구현하더라도 중요한 요청 경로에 어떤 왕복이 들어가는지에 따라 앱의 지연이 달라질 수 있습니다. 정책의 정답률만 보면 이런 실행 비용을 놓칩니다.

또한 원문 구현에는 새 tracepoint와 페이지 구조의 예약 필드 등 커널 수정이 있습니다. 앱 소스를 바꾸지 않는다는 장점과, 아무 수정 없는 모든 Linux에 바로 같은 기능이 있다는 주장은 구별해야 합니다. 시스템 수준의 배포 조건이 남습니다.

## 페이지당 작은 상태의 실제 크기

설명용으로 페이지 크기를 4096바이트, 추가 상태를 4바이트로 정하면 단순 비율은 다음과 같습니다.

```math
\frac{4}{4096}\times100\%=0.09765625\%
```

페이지가 백만 개라면 상태만 400만 바이트입니다. 비율은 작아도 페이지 수가 많으면 전체 저장량을 따로 보아야 합니다. 이 산술에는 맵과 에이전트, 인덱스의 메모리 등은 없습니다. 원문의 페이지당 상태 설명을 이해하는 계산이며 전체 구현 메모리를 측정한 것이 아닙니다.

빈도와 최근성도 다른 정보입니다. 페이지 A를 어제 100번 읽고 오늘은 한 번도 안 읽었으며, B를 방금 한 번 읽었다고 하겠습니다. 빈도만 보면 A가 높고 최근성만 보면 B가 높습니다. 어느 정책이 적합한지는 앞으로의 접근 패턴에 달렸습니다. 미래를 모두 아는 MIN을 비교 기준으로 사용할 수 있어도, 실제 배포 정책이 미래 정답을 미리 읽는 것은 아닙니다.

## 실험과 오버헤드를 분리하기

논문은 기존 정책 위임, 새로운 회수·미리 읽기 정책, 영역·실행 단계별 특화, 스캔과 시스템 호출 비용을 나누어 평가합니다. 기존 커널 정책과 비슷한 앱 성능을 얻었다고 관리 CPU와 호출 비용이 없다는 뜻은 아닙니다. 비동기 경로의 자원 사용은 별도로 분석합니다. [원문 6.2–6.5절](https://www.usenix.org/system/files/atc25-yelam.pdf)

직접 만든 비용 모델에서 페이지 한 장마다 고정 호출 비용 2µs와 처리 비용 4µs가 든다고 하겠습니다. 한 장씩 처리하면 장당 6µs입니다. 64장을 한 번에 요청하고 같은 고정 비용이 한 번만 든다면 장당 4+2/64=4.03125µs입니다. 실제로는 묶음 크기와 지연의 교환도 있으므로 이를 무조건적인 최선 설정으로 읽지 않습니다.

어떤 페이지를 내보내도 앱이 결국 맞는 답을 계산한다는 기능적 호환성과, 정해진 응답 시간 안에 서비스한다는 성능 목표도 다른 조건입니다. 영역과 실행 단계를 구분할 수 있다는 유연성은 좋은 정책을 자동으로 제공한다는 보장이 아닙니다.

확인한 논문은 프레임워크와 여러 정책 사례의 근거를 제공합니다. 이후 대규모 생산 환경의 보편적 절약률이나 현재 Linux 채택 상태를 임의로 추가하지 않습니다. 이 글은 페이지 장부와 비용 예제만 계산했으며 커널을 설치하거나 메모리 벤치마크를 실행하지 않았습니다.
