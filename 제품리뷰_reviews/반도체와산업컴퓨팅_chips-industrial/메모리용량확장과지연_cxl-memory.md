# Samsung CMM-D와 CXL 메모리: 용량 확장과 접근 지연 / Memory expansion over CXL

2026년 10월 20일 기준의 CMM-D 제품 목록과 2026년 3월 백서, 별도 연구진의 CXL 원측정을 읽습니다. 공개 목록의 MD220·MD310과 백서의 시험 샘플을 같은 제품으로 단정하지 않습니다. 실제 장비나 운영체제 설정을 이 글에서 실행하지는 않았습니다.

## SSD처럼 꽂아도 같은 저장 장치는 아닙니다

일반적인 CPU 메모리는 DIMM과 메모리 채널을 사용합니다. CXL 메모리 확장은 PCIe 계열 물리 연결을 활용하면서 CPU의 메모리 접근에 맞는 프로토콜을 제공합니다. 호환되는 하드웨어·펌웨어·운영체제에서는 추가 메모리를 주소 공간에 포함할 수 있습니다.

SSD는 대체로 블록 단위 입출력 요청으로 접근하고, CXL DRAM은 메모리 의미를 갖는 접근을 제공합니다. 연결 모양이 비슷하다는 사실만으로 SSD를 DRAM과 같은 지연으로 사용할 수는 없습니다. DRAM 기반 CMM-D와 NAND를 결합한 다른 제품도 구분해야 합니다.

Type-3는 주로 호스트에 메모리를 제공하는 CXL 장치 유형입니다. 캐시 일관성은 여러 위치가 같은 자료를 서로 모순되게 보지 않도록 관리하는 성질입니다. 그러나 일관성이 있다는 말이 전원 차단에도 데이터가 보존된다는 뜻은 아닙니다. DRAM의 휘발성은 별개의 속성입니다.

## 프로그램의 읽기 한 번은 어디를 지나가나요?

일반 메모리로 배정된 CXL 영역을 읽는 상황을 순서대로 보겠습니다. 먼저 운영체제가 프로그램의 가상 주소에 실제 메모리 페이지를 연결합니다. CPU는 주소 변환 결과와 캐시를 이용해 자료를 찾습니다. 해당 자료가 캐시에 있으면 매번 CXL 장치까지 갈 필요가 없습니다. 캐시에도 없어 외부 메모리 접근이 필요할 때 호스트가 물리 주소에 맞는 경로를 선택합니다.

CXL 경로에 배정된 주소라면 요청이 호스트 브리지와 링크를 지나 메모리 장치에 도착합니다. 장치 쪽 주소로 변환한 뒤 DRAM에서 자료를 읽고 응답을 돌려줍니다. [Linux의 CXL 드라이버 문서](https://kernel.org/doc/html/next/driver-api/cxl/linux/cxl-driver.html)는 이때 접근을 안내하는 HDM decoder와 호스트 물리 주소·장치 물리 주소의 관계를 설명합니다. decoder는 이 문맥에서 압축 파일을 푸는 장치가 아니라 주소에 맞는 목적지를 정하는 구성 요소입니다.

자료를 CPU 캐시에 담은 뒤 같은 내용을 다시 읽을 수 있습니다. 이 때문에 CXL DRAM의 지연과 프로그램의 모든 load 명령 지연은 같지 않습니다. load는 메모리 내용을 읽는 CPU 명령입니다. Type-3 장치의 CXL.mem 접근과, 가속기가 호스트 메모리를 캐시하는 CXL.cache 기능도 같은 것으로 묶지 않습니다.

자체 가상 예로 읽기 1000번 중 캐시 적중 900번은 1ns, 나머지 100번은 250ns가 걸린다고 놓으면 평균은 `(900×1+100×250)/1000=25.9ns`입니다. 외부 접근만 100ns인 대안에서는 같은 가정으로 10.9ns입니다. 실제 CPU는 여러 캐시 단계와 요청 중첩을 갖추므로 이 모형은 경로를 구별하는 계산일 뿐입니다. 운영체제가 매번 읽을 때마다 장치를 다시 골라 준다는 뜻도 아닙니다.

이 흐름은 도입 선택과 연결됩니다. 로컬 DIMM 증설은 슬롯·채널·용량 한도 안에서 가까운 메모리를 늘립니다. CXL은 추가 경로와 관리 비용을 받아들이며 용량을 확장합니다. 자료를 여러 서버로 나누는 방식은 노드 간 통신과 응용 변경이 필요합니다. 프로그램을 거의 그대로 유지할 가치, 필요한 용량, 재사용 빈도에 따라 적합한 방법이 달라집니다.

## 공개 제품과 시험 샘플

| 근거 | 확인한 구성 | 확인 범위 |
| --- | --- | --- |
| 현재 CMM-D 제품 목록 MD220 | CXL 2.0·PCIe 5.0, 128/256GB, DDR5입니다. | 지원 호스트와 플랫폼 인증을 별도로 확인해야 합니다. |
| 현재 목록 MD310 | CXL 3.2·PCIe 6.0, 256GB, 최대 72GB/s를 제시합니다. | 제품 페이지 사양이며 이 글의 독립 실측값이 아닙니다. |
| 2026-03 CMM-D 백서 | 2소켓 Emerald Rapids, 256GB 시험 샘플 4개를 사용합니다. | 모델명이 같다고 전제하지 않으며 해당 시험 구성에 한정합니다. |

제품 목록은 [Samsung CMM-D](https://semiconductor.samsung.com/cxl-memory/cmm-d/), 구성은 [백서 p.5–6](https://download.semiconductor.samsung.com/resources/white-paper/Samsung_CMM-D_Utilization_in_IMDB_Applications.pdf)에 있습니다. 기존 PCIe 슬롯이 있다는 이유만으로 모든 PC에 바로 꽂아 사용할 수 있는 것은 아닙니다. 프로토콜·CPU·BIOS·메모리 매핑·OS 지원이 함께 필요합니다.

## 제조사 백서의 숫자를 읽는 법

백서는 로컬 RDIMM 144ns, 로컬 CMM-D 254ns를 보고합니다. 원격 경로에서는 각각 239ns와 353ns입니다. 이 차이는 해당 플랫폼의 접근 조건에서 얻은 값입니다. DIMM 전체의 읽기 대역폭과 CXL 경로의 수치를 비교할 때에는 장치·채널 수가 같은지 확인해야 합니다. 이 수치로 모든 CXL 장치의 고정 지연을 정하지 않습니다. [시험 구성과 표 2](https://download.semiconductor.samsung.com/resources/white-paper/Samsung_CMM-D_Utilization_in_IMDB_Applications.pdf)를 함께 읽으셔야 합니다.

로컬·원격은 주로 어느 CPU 소켓에서 요청했는지에 관계됩니다. 같은 CXL 장치도 가까운 CPU와 다른 소켓의 CPU가 접근하면 경로가 달라질 수 있습니다. 원격 메모리처럼 보이는 OS 표기만으로 실제 CXL 장치의 특성을 전부 모사했다고 생각하지 않는 것이 중요합니다.

백서의 SAP HANA 배치는 주 저장 영역과 실행 중 작업 영역을 따로 다룹니다. 자료의 양이 같아도 연속 읽기와 많은 동시 요청을 만드는 작업 영역은 병목이 다를 수 있습니다. 따라서 ‘메모리를 확장했더니 몇 %’라는 한 숫자보다 어느 자료를 어디에 놓았는지 확인하는 것이 먼저입니다.

## 독립 연구의 원측정과 다른 점

Liu 등의 2024년 SupMario 원고는 실장치 4종·여러 CPU와 지연 조건·265개 작업을 다룹니다. 본문의 장치 표와 분석은 CXL의 대역폭·꼬리 지연·요청 병렬성이 다름을 보여 줍니다. 이 연구는 공개 제품 MD310의 독립 인증 시험이 아니며 익명화된 장치를 임의로 특정 회사 모델에 연결하지 않습니다. [연구 원문 §3–6](https://arxiv.org/abs/2409.14317)을 확인하실 수 있습니다.

2025년의 [Melody 논문 목록](https://www.microsoft.com/en-us/research/publication/systematic-cxl-memory-characterization-and-performance-analysis-at-scale/)은 저자·시험 플랫폼 수가 달라진 후속 판입니다. 이 글의 구체적인 설명은 2024년 원고의 조건을 기준으로 합니다. 서로 다른 판의 표본 수와 결과를 섞지 않습니다. 연구진에 공급·인프라 이해관계가 전혀 없다고도 단정하지 않습니다.

## 평균 지연과 전체 실행 시간은 다릅니다

자체 모형으로 로컬 접근 100ns, 확장 메모리 250ns, 요청의 20%가 확장 쪽으로 간다고 놓겠습니다. 단순 가중 평균은 0.8×100+0.2×250=130ns입니다. 이는 모든 요청이 같은 비용 구조이고 주소 배치가 정해진 가정의 계산입니다.

그렇다고 전체 프로그램이 30% 느려지는 것은 아닙니다. 메모리를 기다리는 비율이 원래 40%이고 그 부분만 1.3배가 된다면 전체 시간은 0.6+0.4×1.3=1.12배입니다. 반면 많은 요청을 겹칠 수 있거나 캐시 적중이 늘면 이 식과도 다릅니다. 다음 주소를 이전 자료에서 알아내는 포인터 추적은 요청을 겹치기 어려운 사례입니다.

요청 병렬성의 의미를 다른 자체 계산으로 보겠습니다. 64바이트를 250ns마다 한 번 받으면 약 0.256GB/s입니다. 서로 독립적인 요청 32개가 항상 겹친다는 이상화에서는 8.192GB/s까지 가능하지만 링크 상한·컨트롤러·CPU 제한을 넘지는 못합니다. 지연만 측정한 시험과 여러 스레드의 대역폭 시험이 다른 결과를 내는 이유입니다.

## 용량 부족을 피하는 이익과 페이지 이동 비용

로컬 용량이 256GB인데 작업이 300GB라면 64GB의 추가 메모리가 느린 저장소로의 페이지 교체를 피하게 할 수 있습니다. 이 경우 모든 자료를 로컬에 둘 수 있는 작은 작업보다 확장의 가치가 큽니다. 그러나 가격·전력·추가 경로의 지연을 합쳐 보아야 합니다. 이는 특정 CMM-D의 가성비 측정이 아니라 사용 조건 예시입니다.

자주 쓰는 페이지를 빠른 쪽으로 옮기는 계층화도 공짜는 아닙니다. 4KiB 페이지를 옮길 때에는 복사·매핑 갱신·잠금·캐시 영향이 발생합니다. 자체 모형에서 이동 비용이 10µs이고 이후 한 접근마다 100ns를 절약한다면 적어도 100번 넘게 재사용해야 단순 비용을 회수합니다. 곧 다시 차가워질 페이지를 반복해서 옮기면 오히려 느려질 수 있습니다.

메모리 풀링은 여러 호스트가 필요에 맞게 용량을 배정하는 구성입니다. 장치 한 개를 지원 슬롯에 꽂았다는 사실만으로 다중 호스트 풀링이 완성되지 않습니다. 스위치·패브릭 관리·보호와 장애 복구 정책도 필요합니다. 용량 확장, 공유, 풀링을 하나의 기능처럼 적으면 시스템 요구 사항이 가려집니다.
