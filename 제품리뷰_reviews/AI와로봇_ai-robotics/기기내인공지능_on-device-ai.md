# 기기 내 AI: 작은 모델의 계산량보다 메모리와 열이 중요한 이유 / Memory and thermal limits of on-device AI

기준일: 2026년 10월 20일. Apple·Android 개발 문서와 공개 추론 실험을 조사했습니다. 이 글에서 휴대전화 모델을 내려받거나 배터리 시험을 직접 실행하지 않았습니다.

## ‘AI 기능’과 ‘기기 내 실행’은 다릅니다

기기 내 AI는 사용자의 휴대전화나 PC에서 모델 계산을 수행하는 방식입니다. 네트워크가 끊겨도 동작할 수 있고, 원문을 서버로 보내지 않는 기능을 만들 수 있습니다. 반면 AI라고 표시된 모든 기능이 로컬에서 처리되는 것은 아닙니다. 같은 앱도 간단한 요청은 로컬, 어려운 요청은 클라우드로 보낼 수 있습니다.

[Apple의 Foundation Models framework](https://developer.apple.com/foundation-models-framework/)는 Swift 앱에서 모델을 호출하는 통로를 제공합니다. 현재 안내는 기기 내 모델뿐 아니라 Private Cloud Compute와 다른 모델을 연결하는 경로도 구분합니다. 따라서 ‘이 프레임워크를 사용합니다’만으로 해당 기능의 모든 계산이 로컬이라고 판단하면 안 됩니다. 모델 가용성, 이용자 설정, 장치·운영체제 지원을 확인해야 합니다.

[Android의 Gemini Nano 안내](https://developer.android.com/ai/gemini-nano?hl=en)는 AICore라는 시스템 서비스가 기기 내 모델 실행과 갱신을 관리한다고 설명합니다. 앱이 직접 큰 모델을 각각 설치하는 방식과 다릅니다. [2026년 7월 개발 안내](https://developer.android.com/blog/posts/build-intelligent-android-apps-on-device-inference)는 Gemini Nano 4를 AICore 개발자 미리보기의 예로 제시합니다. 이 안내를 모든 Android 장치의 일반 제공 보장으로 바꾸지 않습니다.

## 모델을 휴대전화에 넣는 기술

가중치는 모델이 학습한 숫자들입니다. 양자화는 이 숫자를 적은 비트로 표현해 저장량과 데이터 이동을 줄이는 기술입니다. 16비트 숫자를 4비트로 바꾸면 가중치 본체는 이론상 4분의 1이 됩니다. 그러나 범위를 나타내는 추가 숫자, 계산 중간값, 실행 프로그램이 필요하므로 앱 전체의 메모리도 정확히 4분의 1이 되는 것은 아닙니다. 압축에 따른 출력 품질 변화도 확인해야 합니다.

희소 모델은 매번 전체 계산 블록을 사용하지 않습니다. 다만 적게 계산하는 것과 적게 저장하는 것은 다릅니다. 저장 장치에서 필요한 가중치를 가져오는 속도가 느리면 연산기를 늘려도 답변이 빨라지지 않습니다. NPU는 신경망 연산에 맞춘 전용 처리 장치이지만, 지원하지 않는 연산이나 데이터 형식이 있으면 CPU·GPU와 주고받는 비용이 생깁니다.

[Apple의 2026년 6월 AFM 3 설명](https://machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models)은 Core를 약 30억 매개변수의 밀집 모델, Core Advanced를 전체 200억 중 요청에 따라 약 10억~40억을 활성화하는 모델로 소개합니다. Advanced는 플래시에 전체 가중치를 두고 선택한 전문가를 메모리에 올리며, 요청과 생성 과정의 적절한 시점에 선택을 갱신합니다. 매 토큰마다 전체 전문가를 플래시에서 바꾸는 설명과 다릅니다.

이는 제조사가 공개한 구조 설명이며, 모든 기기에서 같은 모델이 같은 속도로 제공된다는 뜻은 아닙니다. 2025년 약 30억 모델의 시험 결과와 AFM 3 Advanced의 성능을 섞어서 비교하지 않습니다. 공식 발표 당시의 개발 단계와 개별 기능의 배포 상태도 따로 읽어야 합니다.

## 입력 처리와 출력 생성의 병목

입력을 한꺼번에 읽는 단계는 prefill, 다음 토큰을 반복해서 만드는 단계는 decode라고 합니다. 긴 파일을 넣으면 첫 답변이 나오기 전 시간이 길어질 수 있습니다. 답변이 시작된 후 토큰 생성 속도가 빠르더라도 첫 응답까지 기다리는 시간이 길면 짧은 대화에는 불편합니다.

decode에서는 매번 필요한 가중치와 이전 문맥의 중간 정보를 읽습니다. 이때 연산 수보다 메모리에서 숫자를 꺼내는 속도가 제한이 될 수 있습니다. 이전 토큰에서 계산한 key·value를 보관한 공간을 KV 캐시라고 합니다. 모델 가중치를 작게 만들었어도 문맥이 길어지면 캐시가 커집니다. ‘작은 모델이므로 메모리는 걱정하지 않아도 됩니다’라는 결론은 맞지 않습니다.

전력과 열도 함께 봐야 합니다. 초당 처리량이 높으면 빨리 끝나 에너지가 적게 들 수도 있지만, 큰 전력을 계속 쓰면 온도가 올라갑니다. 장치는 온도를 낮추려고 동작 주파수를 줄이는 열 제한을 적용합니다. 첫 요청 한 번의 속도와 수십 분 연속 처리 속도를 따로 재야 하는 이유입니다.

## 토큰 하나가 늘 때 다시 계산하는 것과 보관하는 것

이 흐름은 앞에서 설명한 자기회귀 언어 모델에 해당합니다. 먼저 입력 토큰들을 모델에 통과시켜 각 층의 key와 value를 보관합니다. 생성 중에는 새 토큰의 query로 이전 key들을 비교하고 value들을 섞어 다음 표현을 만듭니다. 이전 토큰의 key·value를 다시 만드는 일을 줄이는 것이 KV 캐시의 역할입니다. 캐시에 문장 원문이나 완성된 답변만 저장한다는 뜻은 아닙니다. [Transformers의 캐시 설명](https://huggingface.co/docs/transformers/main/en/cache_explanation)의 Attention matrices·Cache class 절에서 이 연결을 확인하실 수 있습니다.

자체 작은 모델의 층 수를 12, KV 헤드 수를 4, 헤드당 차원을 64, 숫자당 저장량을 2바이트로 정하겠습니다. 헤드는 attention의 여러 계산 갈래이고 차원은 각 벡터의 숫자 개수입니다. 토큰당 KV 저장량은 `2×12×4×64×2=12,288바이트`, 즉 12KiB입니다. 처음의 2는 key와 value 두 묶음을 셉니다. 배치 하나에서 1024토큰이면 12MiB, 4096토큰이면 48MiB입니다. 실제 AFM·Nano의 구조가 아닌 모형이며 query 헤드와 KV 헤드 수가 다르면 KV 쪽 수를 써야 합니다.

가중치 이동도 별도로 생각할 수 있습니다. 한 토큰을 만들 때 1.5GB를 외부 메모리에서 한 번 읽어야 하고 유효 대역폭이 60GB/s라는 자체 가정에서는 읽기만 최소 `1.5/60=0.025초`가 듭니다. 다른 비용을 생략해도 초당 40토큰에 해당합니다. 캐시에 남는 가중치, 여러 요청이 함께 재사용하는 효과, 연산과 이동의 중첩을 바꾸면 이 모형도 바뀝니다. TOPS가 두 배여도 이 읽기가 병목이면 토큰 속도는 두 배가 되지 않습니다.

따라서 긴 문서 요약과 짧은 명령을 같은 ‘기기 내 AI’ 점수로 묶기 어렵습니다. 긴 문서는 처음 처리와 KV 용량을, 긴 답변은 반복 읽기와 지속 발열을 더 압박할 수 있습니다. 단순 분류기는 이 토큰 생성 흐름을 쓰지 않을 수 있으므로 해당 구조를 모든 NPU 작업에 적용하지 않습니다.

## 외부 실험에서 읽을 수 있는 것

[Conscious Engines 연구진의 2026년 사전논문](https://arxiv.org/html/2603.23640v1)은 Qwen 2.5 1.5B의 명목상 4비트 모델을 휴대전화·노트북·NPU 장치에서 비교합니다. 고정된 258토큰 입력으로 반복 실행하며, 휴대전화의 열 제한을 관찰했습니다. 제조사 모델의 평가가 아니라 별도 공개 모델의 배치 실험입니다.

중요한 한계가 있습니다. 장치마다 MLX·MLC-LLM·vLLM 등 실행기가 다르고 양자화 형식과 출력 길이도 다릅니다. Android는 유효한 반복이 5회뿐이며 전력 자료도 제외했습니다. 전력의 측정 범위도 장치마다 일치하지 않습니다. 따라서 이 자료로 Apple과 Samsung 전체의 에너지 효율 순위를 만들 수 없습니다. AFM이나 Gemini Nano의 직접 성능표도 아닙니다.

이 연구는 제작사와 별도의 실측이지만 연구진도 기기 내 AI 사업을 하는 조직 소속입니다. 단일 장치와 단일 모델·입력의 결과입니다. 관찰된 열 제한이 문제를 제기하는 근거는 되지만, 모든 휴대전화와 모든 앱에서 같은 정도의 속도 저하가 난다고 단정할 근거는 아닙니다. 이 글에서는 논문의 방법과 한계를 읽었으며 같은 시험을 재현하지 않았습니다.

## 메모리와 배터리를 직접 계산해 봅니다

다음은 제품의 실제 압축률과 무관한 자체 계산입니다. 30억 가중치를 각각 4비트로 저장한다고 가정합니다.

```math
M=3\times10^9\times\frac{4}{8}
 =1.5\times10^9\ \mathrm{byte}=1.5\ \mathrm{GB}
```

약 1.40GiB이며, GB와 GiB의 기준이 다르기 때문에 표시가 달라집니다. 캐시·양자화 부가정보·운영체제 메모리는 포함하지 않았습니다. 활성 가중치가 30억인 희소 모델의 전체 저장량을 이 식만으로 계산할 수도 없습니다.

추가 전력이 3W인 기능을 10분 사용하면 0.5Wh를 씁니다. 사용 가능한 에너지가 15Wh인 가상 배터리에서는 약 3.3%입니다. 화면·통신·대기 전력은 제외한 예제입니다. 실제 배터리 표시의 1% 변화만 보고 특정 연산의 에너지를 정밀하게 역산해서는 안 됩니다.

## 기능을 확인하는 현실적인 방법

먼저 네트워크 연결 없이 실행 가능한지와 모델을 처음 준비할 때 다운로드가 필요한지를 나눕니다. 비행기 모드에서 작동하더라도 앱의 로그나 나중 동기화까지 모두 로컬이라는 뜻은 아닙니다. 개인정보의 수집·저장·전송은 계산 위치와 별도로 확인해야 합니다.

시험할 때는 장치·운영체제·실행기·모델 파일의 버전과 양자화 형식을 남깁니다. 같은 입력과 출력 상한을 사용하고, 차가운 상태의 첫 요청과 예열 후 연속 요청을 분리합니다. 초당 토큰 외에도 응답 정확도, 첫 토큰까지 시간, 최고 메모리, 온도, 배터리 측정 범위가 필요합니다. NPU의 TOPS라는 최고 연산 수치만으로 이 항목을 대신할 수는 없습니다.
