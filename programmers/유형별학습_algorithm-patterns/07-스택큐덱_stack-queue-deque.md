# 스택·큐·덱

[학습목차](README.md) · [연습문제](연습문제_problem-index.md)

## 꺼내는 순서로 정하는 자료구조

스택은 마지막에 넣은 원소를 먼저 꺼내고, 큐는 먼저 넣은 원소를 먼저 꺼냅니다.
덱은 양 끝에서 넣고 꺼낼 수 있습니다.
세 구조의 핵심은 저장 모양보다 허용 연산과 꺼내는 순서입니다.
MIT 6.006도 시퀀스 인터페이스에서 스택과 큐를 끝 삽입·삭제의 조합으로 구분합니다. [MIT 강의 2, Sequence Interface](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/79a07dc1cb47d76dae2ffedc701e3d2b_MIT6_006S20_lec2.pdf)

최근 작업의 취소, 괄호의 대응, 대기 요청의 순차 처리처럼 순서 자체가 정답 조건일 때 중요합니다.
반면 가장 작은 값부터 꺼내야 한다면 입력 순서를 유지하는 큐가 아니라 우선순위 큐가 필요합니다.

## 인식 단서와 불변식 후보

“가장 최근”, “되돌리기”, “아직 닫히지 않은 중첩”은 스택의 단서입니다.
“도착 순서”, “현재 단계 뒤의 다음 단계”는 큐의 단서입니다.
“양쪽 끝 제거”, “창 밖의 오래된 원소와 뒤의 불필요한 후보 제거”는 덱의 단서입니다.
어떤 원소를 남기고 어떤 원소를 버려도 되는지 먼저 설명해야 구조 선택이 근거를 갖습니다.

빈 구조에서 꺼낼 때의 동작과 처리할 원소가 새로 들어오는 시점을 명시합니다.
들어온 순서만 유지하면 되는지, 같은 단계에서 새로 들어온 원소도 바로 처리하는지도 구분합니다.

## 직접 구성한 예제: 괄호의 대응

문자열 `([])`가 올바르게 중첩되었는지 검사한다고 가정합니다.
스택에는 아직 닫히지 않은 여는 괄호를 입력 순서대로 저장합니다.

| 읽은 문자 | 처리 전 스택 | 처리 | 처리 후 스택 |
|---|---|---|---|
| ( | 빈 스택 | 여는 괄호 추가 | ( |
| [ | ( | 여는 괄호 추가 | (, [ |
| ] | (, [ | 맨 위 [와 대응 확인 후 제거 | ( |
| ) | ( | 맨 위 (와 대응 확인 후 제거 | 빈 스택 |

닫는 괄호는 가장 최근에 열렸으나 아직 닫히지 않은 괄호와 맞아야 합니다.
`([)]`는 여는 괄호 개수와 닫는 괄호 개수가 맞아도 중첩 순서가 틀린 반례입니다.

```python
def balanced(text):  # 함수로 괄호 중첩 검사 묶기
    stack = []  # 리스트의 뒤쪽을 스택의 맨 위로 사용
    opening = {')': '(', ']': '['}  # 닫는 괄호별 필요한 여는 괄호 저장
    for character in text:  # 문자열을 왼쪽부터 한 번 순회
        if character in '([':  # 여는 괄호인지 검사
            stack.append(character)  # 아직 닫히지 않은 괄호를 맨 위에 추가
        elif character in opening:  # 지원하는 닫는 괄호인지 검사
            if not stack or stack.pop() != opening[character]:  # 빈 스택 또는 잘못된 최근 괄호를 거부
                return False  # 대응 관계가 이미 깨졌으므로 실패 확정
    return not stack  # 끝까지 닫히지 않은 괄호가 없을 때만 성공
```

이 코드는 괄호가 아닌 문자는 무시하는 규칙입니다.
모든 문자가 괄호여야 하는 문제라면 지원하지 않는 문자도 따로 거부해야 합니다.

## 정당성과 총비용

각 접두 구간을 읽은 뒤 스택은 그 구간의 아직 닫히지 않은 여는 괄호 목록입니다.
여는 괄호는 추가하고 닫는 괄호는 가장 최근 항목과만 대응시키므로 이 의미가 유지됩니다.
잘못된 대응을 발견하면 이후 문자가 앞선 잘못된 중첩을 고칠 수 없습니다.
입력 끝에서 스택이 비었을 때만 모든 여는 괄호가 정확한 순서로 닫혔다고 결론냅니다.

문자 수 L에서 각 괄호는 최대 한 번 들어가고 한 번 나옵니다.
끝 추가·삭제를 분할 상환 O(1)로 처리하는 구현에서는 총 O(L) 시간, 최악 O(L) 공간입니다.
한 번의 반복에서 여러 원소를 꺼내더라도 원소별 전체 삽입·삭제 횟수를 세는 방식이 유용합니다.

## 큐와 덱의 구현 선택

배열의 맨 앞 원소를 매번 삭제하고 나머지를 당기는 큐는 N개 처리에 O(N²)이 될 수 있습니다.
배열과 읽기 인덱스를 함께 쓰거나 원형 버퍼, 연결 큐, 덱을 검토합니다.
읽기 인덱스만 늘리는 큐는 앞의 처리된 항목이 계속 메모리에 남는다는 점도 함께 봅니다.
Python `deque`는 양 끝 추가·삭제를 대략 O(1)로 지원하지만 중간 임의 접근을 배열처럼 취급하면 안 됩니다. [Python collections.deque](https://docs.python.org/3/library/collections.html#collections.deque)

C의 원형 큐에서는 머리·꼬리가 같을 때 빈 큐인지 가득 찬 큐인지 구별하는 규칙이 필요합니다.
C++에서는 `stack`, `queue`, `deque`가 공개하는 연산의 차이를 확인합니다.
Python `list`는 뒤쪽 스택 연산에는 자연스럽지만 큐의 `pop(0)` 반복에는 적절하지 않을 수 있습니다.

## 단조 덱과 실전 조건

길이 K인 이동 구간의 최댓값에는 오래된 인덱스를 앞에서 제거하고 약한 후보를 뒤에서 제거하는 단조 덱을 사용할 수 있습니다.
새 값이 더 크고 더 늦게 들어왔다면 앞선 작은 값은 앞으로 어떤 창에서도 새 값보다 유리하지 않다는 지배 관계가 근거입니다.
이는 일반 덱의 성질이 아니라 창의 이동 규칙과 최댓값이라는 질의가 결합된 성질입니다.

작업 대기열에서 FIFO가 적절하려면 도착 순서대로 처리한다는 정책이 먼저 있어야 합니다.
취소나 우선순위 변경이 필요하면 단순 큐만으로 충분하지 않을 수 있습니다.
이 예시는 정책과 구조의 대응이며 실제 운영체제나 서비스가 단일 FIFO만 사용한다는 주장은 아닙니다.

## 실수와 연계 유형

- 괄호 문제에서 전체 개수만 세면 `)(` 같은 순서 오류를 놓칩니다.
- 큐를 순회하면서 새 원소를 넣을 때 현재 단계와 다음 단계를 섞으면 거리나 턴 수가 달라질 수 있습니다.
- 값만 덱에 저장하면 같은 값의 중복과 창 밖으로 나갈 원소를 구별하기 어려울 수 있습니다.

[문자열 파싱](04-문자열과파싱_strings-parsing.md)은 중첩 괄호와 연결됩니다.
[슬라이딩 윈도](10-투포인터와슬라이딩윈도_two-pointers-window.md)는 단조 덱의 대표 연결이며 [힙](08-힙과우선순위큐_heap-priority-queue.md)은 다른 추출 정책입니다.
