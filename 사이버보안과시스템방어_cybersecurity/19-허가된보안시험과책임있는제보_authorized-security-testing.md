# 허가된 보안 시험과 책임 있는 제보 | Authorized security testing and disclosure

[분야 목차](README.md) · [용어](용어_glossary.md) · [출처와 판본](출처_sources.md)

## 해킹이라는 이름보다 먼저 시험 범위를 정합니다

보안 시험은 제품의 약점을 찾아 위험을 줄이는 활동입니다. 모의침투는 합의한 범위 안에서 실제 공격 경로가 성립하는지 확인하는 평가의 한 형태이고, 취약점 연구는 원인·영향·수정 방법을 분석하는 활동입니다. 화이트햇·블랙햇·그레이햇은 사람이나 행위의 성격을 부르는 관용적 표현입니다. 그 이름만으로 소유자 허가, 개인정보 처리 권한, 제3자 시스템 접근 권한이 생기지는 않습니다.

NIST SP 800-115는 기술 보안 시험을 계획·수행하고 결과를 분석해 완화 방안을 만드는 안내서입니다. 2008년 자료이므로 지금의 클라우드·AI·공급망 세부사항을 모두 다루는 최신 체크리스트로 보지 않습니다. OWASP WSTG는 웹 시험 절차의 출발점이며, ASVS는 구현과 검증에서 사용할 보안 요구사항의 기준입니다. 두 자료 모두 특정 사이트를 시험할 허가를 제공하지 않습니다.

## 시험 전에 서면으로 합의할 항목

| 항목 | 기록할 내용 | 빠졌을 때의 문제 |
| --- | --- | --- |
| 소유자와 연락 담당 | 승인 권한이 있는 시스템 소유자, 긴급 중단 연락처입니다. | 제3자·운영팀의 동의 범위를 알 수 없습니다. |
| 대상 범위 | 도메인·앱·API·장치·계정·환경의 정확한 식별자입니다. | 비슷한 이름의 운영·외부 시스템을 잘못 건드릴 수 있습니다. |
| 허용 기법 | 수동 검토, 테스트 계정, 자동 스캔, 부하 시험 등 허용·금지 항목입니다. | 승인되지 않은 시험이 범위에 섞입니다. |
| 시간·속도 제한 | 시험 창, 요청 속도, 동시성, 최대 자료 크기입니다. | 서비스 장애나 다른 사용자의 피해가 커질 수 있습니다. |
| 데이터 처리 | 조회 가능한 자료, 저장·전달 금지 항목, 마스킹·삭제 시점입니다. | 민감정보가 불필요하게 복제되거나 보고서에 남습니다. |
| 중단 조건 | 서비스 이상, 안전 영향, 범위 불확실, 제3자 경로 발견 때의 중지 방법입니다. | 위험을 발견하고도 시험을 계속하게 됩니다. |
| 보고·공개 일정 | 담당자, 접수 경로, 재현 증거, 수정 확인, 공개 시점의 합의입니다. | 수정 전 세부 정보가 노출되거나 제보가 전달되지 않습니다. |

보안 시험은 승인된 테스트 환경에서 먼저 수행하고, 운영 환경은 명시적으로 포함된 경우에만 다룹니다. 자동 도구가 예상보다 넓은 범위를 발견해도 범위를 임의 확장하지 않습니다. 외부 서비스·클라우드 공급자·고객 계정이 연결되면 해당 소유자의 승인 여부를 다시 확인합니다.

## 재현보다 안전한 증거가 우선입니다

허용된 범위에서 최소한의 입력과 권한으로 문제를 확인합니다. 다른 사용자의 자료가 노출될 수 있다면 추가 자료를 열람하지 말고 메타데이터만으로 영향이 확인되는지 검토한 뒤 중단·보고합니다. 지속성 설치, 자격증명 재사용, 대량 반출, 서비스 거부, 악성코드 배포는 별도 명시적 승인 없이는 수행하지 않습니다. 취약점이 보인다는 이유로 다른 환경으로 이동하거나 접근 범위를 넓히지 않습니다.

시험 기록에는 다음 항목을 남깁니다.

1. 대상·승인 문서·시험 시각·도구와 판본
2. 영향을 받는 제품·버전·설정과 필요한 권한
3. 최소 재현 단계와 기대 결과·실제 결과
4. 기밀성·무결성·가용성에 미치는 구체적 영향
5. 원인과 수정 방향, 수정 후 합격 조건
6. 증거의 출처·수집 시각·무결성·민감정보 마스킹
7. 수행하지 않은 항목과 결과의 한계

비밀번호 관련 시험에서는 온라인 추측, password spraying, 유출 자격증명 재사용, 탈취된 해시의 오프라인 추측을 구분합니다. 온라인 시도는 인증 경로와 계정 잠금에 영향을 줄 수 있고, 오프라인 추측은 비밀번호 해시를 획득한 상황을 가정합니다. 허가되지 않은 계정에 후보를 대입하거나 공개된 해시를 무단으로 내려받아 대조하지 않습니다. 정의와 방어는 [암호·비밀번호 해싱](03-암호와키의신뢰_cryptography-keys.md)과 [인증·계정 방어](04-인증과권한검사_identity-access.md)를 참고합니다.

## 취약점 보고서의 공통 형식

```text
제목:
요약:
대상 제품·버전·환경:
승인된 시험 범위:
필요한 사전 조건과 권한:
최소 재현 절차:
기대 결과와 실제 결과:
영향받는 자산·사용자·업무:
원인 분석:
완화·수정 제안:
수정 후 확인할 합격 조건:
증거 링크와 민감정보 처리:
수행하지 않은 시험·남은 불확실성:
제보 담당자·접수일·후속 일정:
```

심각도는 점수 하나로 단정하지 않습니다. CVSS 판본·벡터, 실제 노출 경로, 영향받는 자산, 악용 가능성, 보완 통제를 따로 적습니다. 제보가 접수됐거나 수정됐다는 사실은 제3자 확인이 끝났다는 뜻이 아닙니다. 공개된 제보 정책이 있으면 그 절차를 따르고, 정책이 없으면 소유자의 공식 보안 연락처나 [KISA 보호나라·KrCERT/CC](https://www.krcert.or.kr/)의 공식 안내를 확인합니다.

## 사례: 다른 조직의 문서 ID가 반환되는지 확인합니다

이 저장소의 객체 권한 실습은 메모리 안에 합성 문서 두 개를 만듭니다. Alice는 `org1`의 `d1`을 읽을 수 있고 Bob의 `org2` 문서는 읽을 수 없어야 합니다. 시험 입력은 Alice의 검증된 주체로 `d2`를 요청하는 경우입니다. 기대 결과는 본문을 내보내지 않는 거부이며, 정상 소유자·같은 조직의 다른 소유자·없는 ID·읽기 scope 없음도 별도로 확인합니다.

원인은 문서 ID 자체를 권한으로 오해하는 데 있습니다. 수정은 사용자 입력의 `tenant`나 `owner`를 신뢰하는 것이 아니라 인증 계층이 만든 주체의 조직·사용자·scope와 저장된 문서 속성을 서버에서 대조하는 것입니다. 구현 예시는 [access_control.py](실습_labs/access_control.py), 검사 입력은 [test_security.py](실습_labs/test_security.py)에 있습니다. 검사 기록에는 2026-11-04 실행한 Python 단위 검사 38개가 기재되어 있습니다. 이 결과는 합성 함수의 회귀 근거이며 실제 웹 서비스의 침투 시험이나 전체 시스템 인증 결과는 아닙니다.

## 권장 학습 순서

1. 웹의 요청·응답과 인증·인가를 익힙니다.
2. [OWASP WSTG 4.2](https://owasp.org/www-project-web-security-testing-guide/v42/)에서 검사 목표와 방법을 읽습니다.
3. [ASVS 5.0.0](https://asvs.owasp.org/)의 요구사항을 제품 기능에 맞게 선택합니다.
4. [PortSwigger Web Security Academy](https://portswigger.net/web-security)나 [picoCTF](https://picoctf.org/)에서 제공한 연습 환경만 사용합니다.
5. 한 문제를 원인·영향·수정·회귀 시험까지 보고서로 작성합니다.

이 장은 보안 평가와 책임 있는 제보를 위한 기록 기준입니다. 실제 법적 판단이나 특정 대상 시험의 승인을 대신하지 않으며 외부 호스트·계정·서비스에 시험을 실행한 기록도 아닙니다.

## 원문에서 이어 읽기

- [NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final): 2008년 기술 보안 시험 계획·수행·분석 안내입니다.
- [OWASP WSTG 4.2](https://owasp.org/www-project-web-security-testing-guide/v42/): 버전이 고정된 웹 보안 시험 가이드입니다.
- [OWASP ASVS 5.0.0](https://asvs.owasp.org/): 2025-05-30 공개된 애플리케이션 보안 검증 요구사항입니다.
- [KISA 보호나라·KrCERT/CC](https://www.krcert.or.kr/): 국내 보안공지·취약점 안내·사고 대응의 공식 진입 경로입니다.

## English

Security testing begins with written authorization, a bounded scope, safe evidence handling and a stop condition. WSTG provides testing guidance; ASVS provides verifiable requirements. Neither grants permission to test a system. Findings should include a minimal reproduction, impact, remediation and retest criteria.
