# Linux와 네트워크 경계 | Linux and network boundaries

[분야 목차](README.md) · [용어](용어_glossary.md) · [출처와 판본](출처_sources.md)

## 패킷이 도착하는 것과 작업이 허용되는 것은 다릅니다

IP는 통신 상대의 주소, TCP·UDP 포트는 수신 프로그램의 접점을 구분합니다. 방화벽은 주소·포트·연결 상태 등에 따라 통신을 제한합니다. 접근 가능한 API가 무엇을 해도 되는지는 애플리케이션 권한의 문제입니다. 사내 IP에서 왔다는 이유로 관리자 기능을 허용하면 침해된 내부 장비가 통로가 될 수 있습니다.

DNS는 이름을 주소로 연결합니다. URL 검사 직후 DNS 결과·리디렉션이 바뀌는 경우에는 최초 문자열 확인만으로 최종 목적지를 보장할 수 없습니다. 서버가 외부 URL을 받아 요청하는 기능은 DNS·리디렉션·실제 연결 목적지와 출구 방화벽까지 연결해서 설계합니다. 클라우드 메타데이터와 내부 관리망을 일반 외부 URL 수집기의 권한에 포함하지 않습니다.

## TLS가 제공하는 범위를 이해합니다

TLS 1.3은 연결 상대 인증과 암호화된 통신을 구성하는 프로토콜입니다. 일반적인 웹 연결에서는 서버 인증서를 검증합니다. mTLS는 클라이언트도 인증서를 제시하지만 어느 API를 허용할지는 추가 정책입니다. 인증서 검증을 끄거나 연결 이름과 인증서 이름을 대조하지 않으면 암호화만 있고 의도한 상대의 확인은 약해집니다.

TLS는 복호화한 뒤의 SQL injection·잘못된 객체 권한·악성 서버를 자동으로 막지 않습니다. 또 TLS 1.3의 0-RTT 데이터에는 재전송 위험이 있어 상태 변경 작업을 무조건 허용하면 안 됩니다. [RFC 8446 §2·§8](https://www.rfc-editor.org/rfc/rfc8446.html)

## Linux에서 확인할 경계

| 경계 | 확인 대상 | 실패하기 쉬운 가정 |
| --- | --- | --- |
| 사용자·그룹 | 서비스 계정·파일 소유권·접근 권한입니다. | 서비스 하나가 root여야 모든 기능이 된다고 가정합니다. |
| 프로세스 | capability·시스템 호출·기기·마운트 권한입니다. | 컨테이너라는 이유만으로 모든 격리가 끝났다고 봅니다. |
| 비밀값 | 서비스 자격증명·환경·core dump·로그입니다. | 환경변수면 어떤 경우에도 유출되지 않는다고 봅니다. |
| 네트워크 | 수신 인터페이스·관리 포트·출구 목적지입니다. | 인바운드 차단만 있으면 반출도 막는다고 봅니다. |
| 파일 | 임시 경로·심볼릭 링크·검사와 열기 사이의 경쟁입니다. | 문자열 경로를 검사한 뒤 열면 항상 같은 파일이라고 봅니다. |

`127.0.0.1` 바인딩은 외부 인터페이스로 직접 노출하지 않는 설정이지만, 로컬의 다른 프로세스까지 인증한 것은 아닙니다. 같은 PC의 다른 사용자·확장 기능·브라우저에서 접근하는 경로도 고려합니다. 실습용 서비스도 실제 비밀을 넣기 전에 바인딩·인증·수명과 포트를 확인합니다.

## 네트워크 분석의 질문

자신이 관리하는 캡처에서 요청 시각·연결 실패·TLS 협상·응답 크기를 먼저 봅니다. 암호화된 패킷만으로 애플리케이션의 평문 내용을 전부 읽을 수 있는 것은 아닙니다. Wireshark의 캡처 필터와 표시 필터도 서로 다른 단계입니다. [공식 사용자 안내](https://www.wireshark.org/docs/wsug_html_chunked/)

Zero Trust는 네트워크 위치만으로 자원을 신뢰하지 않고 주체·자원·접근 결정을 중심에 놓는 접근입니다. 방화벽을 없애거나 모든 패킷에 비밀번호를 넣는다는 뜻이 아닙니다. [NIST SP 800-207 공식 개요](https://csrc.nist.gov/pubs/sp/800/207/final)

## 이름 확인과 실제 연결 대상을 함께 통제합니다

DNS는 이름을 주소로 변환하지만 애플리케이션이 실제로 연결하는 대상은 해석 시점, 프록시, 리디렉션에 따라 달라질 수 있습니다. 서버가 외부 URL을 가져오는 기능에서는 입력 URL의 문법 검사만으로 내부 관리 서비스 접근을 막을 수 없습니다. 허용 호스트·scheme을 정하고, DNS 해석 결과와 리디렉션 뒤의 목적지를 정책으로 검사하며, 출구 방화벽이나 전용 프록시에서 사설·관리망으로의 연결을 막습니다. 연결 시간과 응답 크기에도 제한을 둡니다.

TLS는 통신 중 도청·변조를 줄이고 인증서를 통해 연결 상대를 확인하지만, 상대 서비스가 허용된 기능만 수행한다는 뜻은 아닙니다. TLS 복호화 뒤에도 인증·인가·입력 검사·로그 정책이 필요합니다. TLS 1.3 0-RTT는 재전송 가능한 요청 데이터가 될 수 있으므로 중복 실행 시 금전·상태 변경이 발생하는 API에는 재생 방지나 0-RTT 거부 정책을 적용합니다. [RFC 8446 §2·§8](https://www.rfc-editor.org/rfc/rfc8446.html)

## 패킷 캡처가 보여 주는 것과 보여 주지 않는 것

| 관측 자료 | 알 수 있는 내용 | 단독으로 알 수 없는 내용 |
| --- | --- | --- |
| DNS·연결 메타데이터 | 질의·시각·주소·포트·일부 TLS 협상입니다. | 암호화된 애플리케이션 본문과 사용자 의도입니다. |
| 서버·프록시 로그 | 정책 판정·요청 ID·응답 상태입니다. | 로그가 수집되지 않은 내부 상태와 조작 여부입니다. |
| TLS 복호화 자료 | 복호화 지점에서 보이는 평문 요청입니다. | 복호화 지점 밖의 흐름과 이후 서비스의 권한 판단입니다. |
| 방화벽 규칙 | 정책에 적힌 허용·거부 조건입니다. | 런타임 경로에서 실제로 적용되는지 여부입니다. |

시험에서는 같은 요청 ID를 애플리케이션·프록시·네트워크 장비 로그에 연결하고 각 시계의 오차를 기록합니다. 캡처 화면만으로 취약점이나 침입을 확정하지 않고, 프로세스 권한·정책 적용·상대 서비스 기록과 대조합니다.

## English

Network reachability, TLS peer authentication and application authorization are separate boundaries. Linux privileges, outbound access and local interfaces require explicit policies.
