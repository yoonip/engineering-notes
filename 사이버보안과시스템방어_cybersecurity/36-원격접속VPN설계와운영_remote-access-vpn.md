# 원격 접속 VPN 설계와 운영 | Remote access VPN design and operations

자료 확인일: 2026-11-04

## 이 장에서 다루는 범위

가상 사설망(VPN)은 인터넷 같은 공용망 위에 암호화된 통신 경로를 만듭니다. 이 경로가 생겼다고 내부 서비스 전체에 접근할 권한이 자동으로 생기는 것은 아닙니다. 단말과 사용자를 확인하고, 필요한 목적지에만 경로를 열고, VPN 이후에도 각 서비스가 권한을 확인해야 합니다.

이 장은 재택·외근 사용자가 사내 업무망에 접속하는 원격 접속 VPN과 서로 다른 사업장 네트워크를 잇는 site-to-site VPN을 구분합니다. IPsec/IKEv2와 WireGuard의 구조, 분할 터널과 전체 터널의 경로 차이, DNS·IPv6·MTU 장애, 키 수명 주기와 운영 점검을 연결합니다. 제품별 화면이나 성능 수치를 비교하는 자료가 아니라 표준과 공식 프로토콜 설명을 바탕으로 설계 경계를 정리합니다.

## VPN이 만드는 경로와 만들지 않는 권한

VPN은 패킷을 터널 종단점까지 암호화해 전달합니다. 터널 종단점에서 패킷이 복호화된 뒤에는 일반 네트워크 경로로 전달되므로, 내부 방화벽·애플리케이션 인증·서버 권한 검사가 계속 필요합니다. VPN에 연결됐다는 신호만으로 관리자 권한이나 모든 내부망 접근을 허용하면, 감염된 단말이 암호화된 터널을 통해 내부로 들어올 수 있습니다.

```text
관리되는 단말                    VPN 경계                         업무 서비스
사용자·기기 확인 → 암호화 터널 → VPN 종단점·방화벽 → 필요한 서브넷만 허용 → 서비스별 인증·인가
       │                                  │                                  │
단말 보안 상태                   경로·계정 정책                  사용자·작업별 권한
```

| 연결 유형 | 연결하는 대상 | 흔한 사용 목적 | 운영에서 확인할 점 |
| --- | --- | --- | --- |
| 원격 접속 VPN | 사용자·기기와 VPN 게이트웨이 | 외부에서 사내 업무 서비스에 접속합니다. | 사용자별 인증, 단말 관리 상태, 기기별 키 회수, 접근 서브넷 제한이 필요합니다. |
| site-to-site VPN | 네트워크 게이트웨이와 게이트웨이 | 사무실·데이터센터·클라우드 네트워크를 연결합니다. | 각 방향의 네트워크·서비스 선택자, 중복 주소, 라우팅, 장애 전환을 조정합니다. |
| 애플리케이션 단위 접근 | 사용자·단말과 개별 서비스 | 특정 업무 서비스만 외부에 제공하거나 프록시를 통해 연결합니다. | VPN 터널과 별도 접근 모델이며 서비스 단위 신원·정책을 적용합니다. |

VPN은 전송 구간을 보호하는 수단입니다. 접속 단말에 악성코드가 실행 중이거나, VPN 계정이 탈취되었거나, 내부 서비스에 과도한 권한이 있으면 터널의 암호화만으로 피해를 막지 못합니다.

## IPsec과 IKEv2의 역할

IPsec은 IP 계층에서 패킷을 보호하는 표준 체계입니다. IKEv2는 두 종단점이 서로를 인증하고, 사용할 암호 알고리즘과 키를 협상하며, 보호할 트래픽을 나타내는 Security Association(SA)을 설정·갱신하도록 돕습니다. IPsec의 보안 정책은 주소·프로토콜·포트 등 트래픽 선택자를 기준으로 어떤 패킷을 보호하거나 통과시키거나 버릴지 정합니다.

IKEv2의 첫 교환인 `IKE_SA_INIT`에서는 암호 알고리즘 제안·nonce·Diffie–Hellman 키 교환을 처리합니다. 뒤이어 `IKE_AUTH`에서 인증 자료를 확인하고 첫 Child SA를 설정합니다. 관리자는 연결이 성립했는지만 보지 말고 양쪽 장비의 IKE SA·Child SA 상태, 선택된 알고리즘, 양방향 트래픽 선택자, 재협상과 만료 시각을 대조해야 합니다.

| 구성 요소 | 역할 | 운영 점검 |
| --- | --- | --- |
| IKE SA | 피어 간 제어·협상 메시지를 보호합니다. | 인증 방식·알고리즘 제안·수명·재협상 상태를 확인합니다. |
| Child SA | 실제 데이터 패킷의 ESP 보호 조건과 키를 관리합니다. | 양방향 선택자·암호화·무결성·rekey 결과를 확인합니다. |
| SPD | 어떤 트래픽을 보호·통과·폐기할지 정하는 정책 데이터베이스입니다. | 의도한 업무 흐름만 선택하고 그 밖의 경로는 기본 정책에 맞게 처리하는지 확인합니다. |
| SAD | 성립한 SA별 키·알고리즘·상태를 기록합니다. | 양쪽 끝의 SA가 같은 방향·수명·선택자에 맞는지 확인합니다. |

게이트웨이가 종단점인 일반적인 site-to-site 구조에는 보통 터널 모드를 사용합니다. 이 모드에서는 원래 패킷을 내부 IP 헤더째 보호하고, 게이트웨이 사이에서 전달할 새 외부 IP 헤더를 붙입니다. 외부망에는 터널 종단점 주소가 보이고 내부 원래 주소는 보호되는 범위에 따라 가려집니다. RFC 4301은 터널 모드 SA의 외부·내부 IP 헤더와 gateway 동작을 설명합니다.

IPsec의 장점은 서로 다른 사업자 장비와 운영체제 사이에서 표준 기반 site-to-site 연결을 구성할 수 있고, 트래픽 선택자를 세밀하게 정할 수 있다는 점입니다. 반대로 양쪽의 알고리즘 제안, 인증서·PSK, NAT 통과, 선택자, 수명·재협상 설정이 맞지 않으면 협상은 성공해도 데이터가 흐르지 않거나 한 방향만 통신할 수 있습니다. 장비별 구성 명령과 기본값은 다르므로 공통 표준 개념과 각 제품 문서를 함께 확인합니다.

## WireGuard의 peer·키·경로

WireGuard는 UDP 위에 IP 패킷을 캡슐화하는 VPN입니다. 각 인터페이스는 자신의 개인키를 갖고 각 peer의 공개키와 허용 IP 범위를 설정합니다. WireGuard의 `AllowedIPs`는 송신 시 목적지에 맞는 peer를 고르는 경로표 역할을 하며, 수신 시에는 해당 peer가 터널 안에서 보낼 수 있는 출발지 주소를 제한합니다. 따라서 `AllowedIPs`는 단순한 “접속할 네트워크 목록”이 아니라 암호화 키와 IP 주소를 연결하는 경로·접근 경계입니다.

다음은 `wg-quick` 형식의 분할 터널 예시입니다. 실제 키가 아니라 자리표시자를 썼으므로 그대로 배포하지 않습니다. 예시는 사용자의 기기에서 사내 VPN 대역과 업무망만 터널로 보내고 일반 인터넷 경로는 기존 연결에 남기는 구성을 나타냅니다.

```ini
# 이 단말의 WireGuard 인터페이스 설정입니다.
[Interface]
# VPN 안에서 이 단말에 할당한 주소입니다.
Address = 10.77.0.11/32
# 실제 단말의 비밀키를 넣으며 저장소에 올리지 않습니다.
PrivateKey = <CLIENT_PRIVATE_KEY>

# 연결할 VPN 게이트웨이 peer를 정의합니다.
[Peer]
# 별도 신뢰 경로로 확인한 게이트웨이 공개키입니다.
PublicKey = <VPN_GATEWAY_PUBLIC_KEY>
# 게이트웨이의 공개 주소와 UDP 포트입니다.
Endpoint = vpn.example.net:51820
# 이 대역의 목적지만 터널로 보내고 peer 출발지도 제한합니다.
AllowedIPs = 10.77.0.0/24, 10.40.0.0/16
# NAT 뒤에서 유휴 수신이 필요할 때만 설정합니다.
PersistentKeepalive = 25
```

`PersistentKeepalive`는 기본적으로 꺼져 있습니다. 클라이언트가 NAT 뒤에 있고 조용한 상태에서도 서버가 먼저 클라이언트에 도달해야 할 때 필요성을 확인해 설정합니다. 모든 peer에 무조건 25초 주기로 켜면 불필요한 트래픽과 상태 유지가 늘어납니다.

WireGuard는 작은 프로토콜 표면과 단순한 peer 공개키 설정을 목표로 합니다. 공식 문서는 WireGuard가 키 배포와 설정 push 자체를 범위 밖에 두며, 이 기능을 다른 관리 계층에 맡긴다고 설명합니다. 따라서 규모가 큰 조직에서는 사용자의 퇴사·단말 분실·업무 변경을 peer 키 제거와 연결하는 등록·회수 시스템이 필요합니다. WireGuard 키 하나만으로 사내 인사 계정, 다중 인증, 단말 상태가 자동 확인되는 것은 아닙니다.

### 키 생성 예시

다음 명령은 Linux에서 WireGuard 도구로 새 단말 키 쌍을 만들 때 사용하는 형태입니다. 키가 생성되는 호스트의 파일 권한과 백업 정책을 먼저 정하고, 개인키는 허가된 비밀 저장 위치에만 보관합니다. 실제 운영 장비에서는 조직의 승인된 키 관리 절차를 따릅니다.

```sh
umask 077                                      # 이후 생성할 파일을 현재 사용자만 읽도록 제한합니다.
wg genkey | tee client-private.key | wg pubkey > client-public.key  # 개인키를 저장하고 공개키를 계산합니다.
```

첫 명령은 이후 파일 생성 권한을 제한합니다. 둘째 명령은 `wg genkey`로 개인키를 만들고 `tee`로 보호된 파일에 기록하면서 표준 출력을 `wg pubkey`에 전달해 공개키 파일을 생성합니다. 이 명령은 예시로 제시했으며 여기서 실행하지 않았습니다. 실제 파일 권한·소유자·운영체제 도구 설치는 각 배포판의 WireGuard 공식 설치 문서와 조직 정책에 따라 확인합니다.

## 분할 터널과 전체 터널의 차이

분할 터널(split tunnel)은 지정한 업무 목적지나 사내 서브넷만 VPN으로 보냅니다. 전체 터널(full tunnel)은 IPv4·IPv6의 기본 경로를 VPN으로 보내 웹 트래픽까지 기업 출구를 거치도록 설계합니다. 어느 쪽이 더 안전하다고 단정하기보다 보안 관제·개인정보·대역폭·업무 요구와 출구 정책을 함께 봅니다.

| 항목 | 분할 터널 | 전체 터널 |
| --- | --- | --- |
| 경로 | 선언한 내부 대역만 VPN으로 보냅니다. | 일반 인터넷 트래픽도 VPN 출구로 보냅니다. |
| 장점 | VPN 대역폭을 절약하고 외부 SaaS의 직접 경로를 유지할 수 있습니다. | 단말의 인터넷 출구를 한 곳에서 검사·기록할 수 있습니다. |
| 주된 위험 | 업무 대상이 빠지거나 DNS·IPv6만 로컬 경로로 빠지면 예상 밖의 직접 통신이 생깁니다. | 게이트웨이 장애·용량 부족·중앙 출구 정책 오류가 모든 외부 접속에 영향을 줄 수 있습니다. |
| 점검 | 업무망 prefix, DNS 서버 경로, IPv4·IPv6 우회를 확인합니다. | 양 주소 계열 기본 경로, DNS 전달, 차단 시 fail-open/close 동작을 확인합니다. |

전체 터널을 의도했는데 IPv4 기본 경로만 VPN으로 향하고 IPv6 기본 경로가 로컬 네트워크에 남으면 IPv6 트래픽이 직접 나갈 수 있습니다. DNS resolver 설정도 라우팅과 별개로 확인합니다. VPN이 연결된 상태에서 사용자가 기대하는 DNS 서버가 어느 경로로 질의를 받고, VPN 연결 해제·절전 복귀·네트워크 변경 때 이전 DNS 설정이 남지 않는지 점검합니다.

분할 터널에서는 허용 목록에 업무 서비스의 실제 IP 범위뿐 아니라 인증, DNS, 업데이트, 원격 관리에 필요한 목적지가 빠지지 않았는지 확인합니다. 전체 터널에서는 공용 화상회의나 대용량 다운로드까지 중앙 출구를 지나도록 했을 때 지연과 용량이 감당되는지 측정합니다. 어느 모델이든 VPN으로 라우팅되는 범위와 방화벽이 실제 허용하는 범위는 별도로 기록합니다.

## 보안 경계를 세우는 구성 원칙

1. 사람·자동화 작업·기기별로 고유한 자격 증명을 발급하고 공유 peer 키를 피합니다.
2. 사용자 인증, 기기 등록, MFA·단말 정책을 VPN 프로토콜의 키 확인과 구분해 설계합니다.
3. VPN 연결 후 네트워크 접근을 업무 역할별로 나누고 관리망·사용자망·서버망을 기본적으로 분리합니다.
4. 필요한 업무망만 route·traffic selector·방화벽 규칙으로 열고, `0.0.0.0/0`·`::/0` 전체 터널은 의도와 출구 통제를 확인한 경우에 적용합니다.
5. 단말 분실·퇴사·키 유출 때 계정, 인증서, peer 공개키, 게이트웨이·방화벽 정책을 함께 회수합니다.
6. 터널이 끊겼을 때 단말이 업무 경로를 공용 인터넷으로 계속 보내는지, 차단 상태를 유지하는지 정책으로 정하고 실제 시험합니다.
7. 접속 사용자·기기·피어 키 ID·할당 IP·연결 시각·정책 결과를 중앙에서 기록하되 비밀키와 민감한 평문은 로그에 남기지 않습니다.

VPN 연결은 내부망의 신뢰를 증명하지 않습니다. VPN 인증 뒤에도 서비스가 사용자 역할·기기 상태·작업 요청을 검사하도록 구성합니다. 연결된 단말에서 다른 사내 기기로 lateral movement가 가능한지, VPN 계정 하나로 관리면까지 도달할 수 있는지 별도 위협 모델로 검토합니다.

## 흔한 장애를 구분하는 진단 순서

### 1. 터널 협상 자체가 되지 않습니다

양쪽이 사용하는 peer 주소, DNS 해석 결과, UDP 포트, 방화벽·NAT 통과, 인증서 만료, 사전 공유 키 또는 공개키를 확인합니다. IPsec은 `IKE_SA_INIT`과 `IKE_AUTH` 중 어디에서 실패했는지, 제안 알고리즘·인증서 신뢰·피어 ID가 일치하는지 양쪽 로그로 비교합니다. WireGuard는 peer 공개키, endpoint, handshake 시각과 송수신 바이트 카운터를 확인합니다. 개인키나 사전 공유 키를 지원 티켓·채팅에 붙이지 않습니다.

### 2. 터널은 연결됐지만 내부 서버에 도달하지 못합니다

터널 인터페이스 주소, `AllowedIPs` 또는 IPsec traffic selector, 클라이언트·게이트웨이 라우팅, 서버의 반환 경로, VPN 이후 방화벽을 순서대로 봅니다. 패킷이 요청 방향으로만 가고 응답이 돌아오지 않으면 return route나 상태 방화벽을 확인합니다. 같은 사설 대역을 사용자의 집 네트워크와 회사 내부가 동시에 쓰면 클라이언트가 목적지를 잘못된 인터페이스로 보낼 수 있으므로 주소 계획을 살펴봅니다.

### 3. 일부 웹사이트나 큰 응답만 멈춥니다

터널 암호화와 새 IP 헤더로 인해 사용할 수 있는 최대 패킷 크기(MTU)가 줄어들 수 있습니다. 작은 요청은 되지만 큰 응답이나 특정 TLS 연결만 정체된다면 MTU·경로 MTU 탐색·ICMP 차단·단편화 문제를 조사합니다. MTU를 무작정 낮추기보다 터널 전후에서 패킷 크기와 재전송을 관측하고, 게이트웨이와 단말의 설정을 함께 조정합니다. RFC 4301은 IPsec의 Path MTU와 DF 처리 절을 별도로 둡니다.

### 4. VPN 연결 중에도 일부 트래픽이 직접 나갑니다

IPv4와 IPv6의 경로표, DNS resolver, 프록시 자동 설정, 로컬 앱의 예외 경로, 절전 복귀 후 터널 상태를 점검합니다. 분할 터널을 의도했다면 직접 나가는 목적지가 정책상 허용된 범위인지 확인합니다. 전체 터널을 의도했다면 로컬 출구를 통한 IPv4·IPv6와 DNS 통신이 발생하지 않는지 테스트하고, VPN이 끊겼을 때 어떤 동작을 해야 하는지도 확인합니다.

## IPsec과 WireGuard를 고르는 질문

| 질문 | IPsec/IKEv2가 맞을 수 있는 상황 | WireGuard가 맞을 수 있는 상황 |
| --- | --- | --- |
| 기존 네트워크 장비와 연결합니까? | 서로 다른 방화벽·라우터·클라우드 gateway 사이 표준 site-to-site 연결이 중요합니다. | 모든 종단이 WireGuard를 지원하고 peer 키와 경로를 별도 관리할 수 있습니다. |
| 접근 정책이 얼마나 세분화됩니까? | IKE 인증과 트래픽 선택자, 장비 정책을 조합해 gateway 수준으로 관리합니다. | peer별 `AllowedIPs`와 운영체제 방화벽·별도 관리 계층으로 관리합니다. |
| 어떤 관리 역량이 있습니까? | 인증서·알고리즘 협상·SA·라우팅과 장비별 상호운용성을 다룰 운영자가 있습니다. | 키 발급·회수, peer 상태·주소 할당, route 충돌을 처리할 중앙 관리 방법이 준비되어 있습니다. |
| 우선 확인할 실패 조건은 무엇입니까? | 제안 불일치, 인증 실패, selector·SPD 불일치, NAT·MTU 문제입니다. | 키·endpoint·`AllowedIPs` 오설정, 단말 키 회수 누락, route·DNS·IPv6 문제입니다. |

프로토콜 이름만으로 제품의 보안이나 성능을 결정할 수 없습니다. 실제 구현의 지원 버전, 알고리즘 정책, 취약점 대응, 로그·회수 자동화, 고가용성, 단말 운영체제 지원을 확인해야 합니다. WireGuard 공식 문서가 밝히듯 키 배포와 설정 push는 프로토콜 자체가 제공하는 기능이 아니므로, 그 빈자리를 어떤 관리 시스템이 담당하는지 설계가 답해야 합니다.

## 변경 전후 운영 확인표

- 연결 전: 승인된 사용자·기기와 peer 목록, 사내 주소·서비스 목록, DNS와 IPv6 정책을 확인합니다.
- 설정 변경 전: 사용 중인 인증 방식·키·인증서·암호 제안·라우트·MTU와 현재 허용 흐름을 보관합니다.
- 변경 중: 관리 콘솔이나 로컬 복구 경로를 유지하고, 한 번에 사용자·경로·암호 정책을 모두 바꾸지 않습니다.
- 변경 직후: 정상 단말·회수 대상 단말, 허용 서비스·차단 서비스, IPv4·IPv6·DNS, 터널 단절 상황을 각각 확인합니다.
- 운영 중: 인증 실패·반복 재협상·handshake 장기 미갱신·비정상 대역폭·허가되지 않은 내부 접근 시도를 감시합니다.
- 회수 시: 계정 비활성화뿐 아니라 peer·인증서·공개키·방화벽 규칙·중앙 접속 정책과 세션 수명을 확인합니다.

이 문서의 WireGuard 설정과 명령은 공식 프로토콜·도구 형식을 참고해 직접 작성한 교육 예시입니다. 실제 VPN gateway에 적용하거나 연결·차단 결과를 측정하지 않았습니다. 운영 설정은 현재 설치된 프로그램 버전, 조직의 주소계획, 인증 체계와 변경 승인 절차에 맞춰 검증해야 합니다.

## English summary

A VPN encrypts traffic between tunnel endpoints; it does not automatically authorize a user or device for every internal service. IPsec/IKEv2 establishes authenticated security associations and applies traffic selectors and policy databases. WireGuard associates peer public keys with allowed IPs, which affect both packet routing and source-address checks; key distribution and configuration management remain external responsibilities. Choose split or full tunneling deliberately, then test IPv4, IPv6, DNS, failure behavior, return routes, and MTU. Keep application authorization and network segmentation in place after the tunnel terminates.
