# HTTP 요청 경계와 프록시 간 해석 차이 | HTTP Request Framing and Desynchronization

자료 확인일: 2026-11-04

웹 요청이 WAF, CDN, 로드 밸런서, 리버스 프록시, 응용 서버를 차례로 지날 때 각 구성요소가 요청의 끝을 다르게 판단하면 보안 필터가 본 요청과 원본 서버가 처리한 요청이 달라질 수 있습니다. 이 차이를 이용하는 취약점 계열이 HTTP 요청 밀수(request smuggling)와 요청 역동기화(request desynchronization)입니다. 핵심은 특정 헤더 하나가 아니라 여러 HTTP 파서와 프로토콜 변환기가 메시지 경계를 같은 방식으로 해석하는지에 있습니다.

이 장은 정상적인 요청 처리와 방어 설계를 설명합니다. 임의 서버에 보낼 공격 요청이나 재현용 악성 페이로드는 싣지 않습니다. 아래 확인 항목은 자체 시스템을 승인된 시험 환경에서 검증할 때 사용할 기준이며, 실제 프록시나 서버에서 실행한 결과는 아닙니다.

## 요청 경계가 어긋나는 이유

HTTP/1.1은 TCP 연결 위에서 요청을 이어 보낼 수 있습니다. 수신자는 헤더를 읽은 다음 규칙에 따라 본문 길이를 정하고, 그 뒤의 바이트를 다음 요청으로 해석합니다. 프런트엔드가 본문을 짧게 읽고 백엔드가 더 길게 읽거나 그 반대라면, 뒤에 남은 바이트가 다음 요청의 시작으로 처리될 수 있습니다.

```text
클라이언트
   │ HTTP/2 또는 HTTP/1.1
   ▼
CDN·WAF ── 요청 검사·정책 판단
   │ 프로토콜 변환 또는 재직렬화
   ▼
로드 밸런서·리버스 프록시 ── 연결 재사용 가능
   │
   ▼
응용 서버 ── 실제 경계에 따라 요청 처리
```

여기서 `요청 경계`는 한 요청의 헤더와 본문이 끝나고 다음 요청이 시작되는 위치입니다. `역동기화`는 중간 장비와 원본 서버가 같은 바이트 흐름에서 서로 다른 요청 순서를 구성하는 상태를 말합니다. 결과는 WAF 규칙 우회, 요청과 응답의 짝이 어긋나는 현상, 캐시 오염, 내부 기능에 대한 의도치 않은 요청 등으로 이어질 수 있습니다. 실제 영향은 서비스의 연결 재사용, 캐시 정책, 인증 방식과 프록시 구조에 따라 달라집니다. [MITRE CWE-444](https://cwe.mitre.org/data/definitions/444)

## HTTP/1.1 본문 길이 규칙

RFC 9112 §6.3은 메시지 본문 길이를 정하는 순서와 오류 처리를 규정합니다. 아래는 보안 검토에서 특히 중요한 규칙입니다.

| 수신한 상태 | 표준이 정한 처리 방향 | 운영상 의미 |
| --- | --- | --- |
| `Transfer-Encoding`과 `Content-Length`가 함께 있습니다. | `Transfer-Encoding`이 우선하지만, 이런 메시지는 오류로 처리하는 것이 바람직합니다. 처리하더라도 응답 뒤 연결을 닫아야 합니다. 전달하는 중개자는 기존 `Content-Length`를 제거하고 전송 코딩을 처리한 뒤 전달해야 합니다. | 장비마다 한 필드만 선택하거나 서로 다르게 정규화하지 않도록 경계에서 거부하거나 한 가지 표현으로 다시 구성합니다. |
| 유효한 `Transfer-Encoding`의 마지막 코딩이 `chunked`입니다. | 청크 종료 규칙을 읽어 메시지 끝을 정합니다. | 청크를 읽고 변환하는 모든 프록시가 오류·끝 표시를 같은 기준으로 처리해야 합니다. |
| 요청의 `Transfer-Encoding`에서 마지막 코딩이 `chunked`가 아닙니다. | 길이를 신뢰성 있게 정할 수 없으므로 서버는 `400 Bad Request`를 보내고 연결을 닫아야 합니다. | 불완전한 상태를 다음 요청에 이어 붙이거나 연결을 재사용하지 않습니다. |
| `Transfer-Encoding` 없이 잘못된 `Content-Length`가 왔습니다. | 쉼표로 묶인 값 전부가 유효하고 서로 같다고 확인되는 좁은 경우 외에는 복구할 수 없는 오류입니다. 요청이면 `400` 응답 뒤 연결을 닫아야 합니다. | 중복 길이 값을 임의의 우선순위로 선택하지 않고 표준 규칙대로 판정합니다. |
| 유효한 `Content-Length`만 있습니다. | 지정한 십진 바이트 수가 본문 길이입니다. | 문자 수가 아니라 전송되는 옥텟 수를 기준으로 합니다. |
| 요청에 두 길이 표시가 모두 없습니다. | 요청 본문 길이는 0입니다. | 한 파서가 본문이 있다고 가정하는 관대한 처리를 두지 않습니다. |

RFC 9112는 `Transfer-Encoding`과 `Content-Length`의 공존을 단순히 “어느 쪽이 더 우선인가”의 문제로 끝내지 않습니다. 표준상 전송 코딩이 우선하더라도 해당 메시지는 오류로 다루는 것이 바람직하고 연결을 닫아야 합니다. 프록시가 전달하려면 `Content-Length`를 제거하고 본문을 올바르게 처리해야 합니다. 이 처리 과정이 프런트엔드와 백엔드 사이에 서로 다른 표현을 남기면 취약한 파서가 그 차이를 악용당할 수 있습니다. [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3) · [§11.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-11.2)

## WAF만 통과했는데 원본은 다른 요청을 보는 상황

1. 첫 번째 장비가 헤더와 본문의 끝을 해석하고 WAF 규칙을 적용합니다.
2. 중간 프록시가 요청을 버퍼링하거나 HTTP 버전을 바꾸면서 새 요청 표현을 만듭니다.
3. 다음 서버가 길이·헤더·본문을 다른 규칙으로 해석합니다.
4. 연결을 재사용하는 경우 한 요청에서 남은 데이터가 다음 요청의 일부로 해석될 수 있습니다.
5. 그 결과 WAF가 검사한 내용과 응용 서버가 수행한 작업의 대응 관계가 깨질 수 있습니다.

이 흐름은 `WAF가 모든 공격 문자열을 놓쳤다`는 설명과 다릅니다. 각 장비의 로그에는 개별적으로 정상적인 HTTP 요청처럼 보이더라도 전체 홉의 해석이 일치하지 않을 수 있습니다. 따라서 WAF의 탐지 로그만으로 원본 서버가 받은 요청을 확정하지 말고, 프록시 전후의 요청 식별자·프로토콜·길이·연결 상태를 대조해야 합니다. 본문 원문이나 인증 정보를 로그에 그대로 남기지 말고 필요한 필드만 마스킹해 보관합니다.

## HTTP/2 연결에서도 변환 경계를 확인합니다

HTTP/2는 요청을 TCP 바이트 스트림의 길이 헤더만으로 나누지 않고, 각 stream과 frame으로 구성합니다. RFC 9113 §8.1.1은 `Content-Length`가 있을 때 DATA 프레임 payload의 합과 값이 다르면 메시지가 잘못된 것으로 보고, 중개자는 이런 메시지를 전달하지 말아야 한다고 정합니다. 헤더 필드의 금지된 문자와 pseudo-header 규칙도 검증해야 합니다. [RFC 9113 §8.1.1, §8.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.1.1)

다만 브라우저와 CDN 사이에서 HTTP/2를 사용한다는 사실만으로 모든 구간이 HTTP/2인 것은 아닙니다. 중간 게이트웨이가 HTTP/2 요청을 HTTP/1.1로 바꾸면 변환기가 필드와 본문 길이를 어떻게 검증하고 다시 직렬화하는지가 새 신뢰 경계가 됩니다. 가능한 경우 홉 간 프로토콜을 일관되게 유지하는 방법을 검토하되, 변환을 피할 수 없다면 불량 메시지 거부, 필드 정규화, 연결 종료 규칙을 각 구현에서 확인합니다. HTTP/2 종단간 사용은 특정 HTTP/1.1 framing 불일치를 줄이는 선택이지, 경로·권한·캐시·다른 파서 차이까지 해결하는 만능 조치는 아닙니다. [PortSwigger Web Security Academy](https://portswigger.net/web-security/request-smuggling)

## 방어 설계 순서

1. 인터넷 진입점부터 원본까지 HTTP 버전과 프록시 홉을 그립니다. TLS 종료 지점, 재직렬화 지점, 연결 풀과 캐시 위치를 표시합니다.
2. 모든 경계에서 RFC에 맞지 않는 요청을 거부합니다. 특히 길이가 모호한 메시지, 잘못된 `Content-Length`, 허용되지 않은 필드 값과 HTTP/2의 잘못된 frame·field 조합을 다음 홉으로 넘기지 않습니다.
3. 한 지점에서 입력을 파싱한 뒤 정규화된 메시지를 새로 직렬화합니다. 전달받은 원문 필드를 그대로 붙여서 다음 서버에 넘기는 식의 혼합 처리는 피합니다.
4. 표준이 오류 뒤 연결 종료를 요구하는 경우 그 연결을 재사용하지 않습니다. HTTP/1.1에서 `Transfer-Encoding`과 `Content-Length`가 함께 온 요청은 RFC의 연결 종료 요구를 따릅니다.
5. WAF 규칙과 응용 서버가 검사하는 경로·host·본문·메서드가 같은 의미를 갖는지 확인합니다. 사용자 인증과 객체별 인가는 원본 응용 서버에서도 수행합니다.
6. HTTP/2→HTTP/1.1 변환이 있다면 변환 전후의 헤더, 본문 길이, 연결 종료와 오류 응답을 별도 검토합니다. 지원하는 제품·버전·설정에 대한 제조사 보안 권고와 패치 상태도 관리합니다.
7. 백엔드 연결 재사용을 끄는 방안은 영향 완화책으로 평가하되 단독 해결책으로 보지 않습니다. 파서 불일치와 다른 연결 없는 변형을 모두 제거한다는 보장은 없습니다.

RFC 규칙과 제품별 동작은 구분해야 합니다. 예를 들어 특정 프록시가 모호한 요청을 자동 정규화하는지는 제품·버전·설정에 따라 다릅니다. 공급사 문서나 실제 승인된 시험 결과가 없으면 특정 제품이 안전하게 정규화한다고 단정하지 않습니다.

## 승인된 시험 환경에서 확인할 항목

공개 서비스나 다른 조직의 시스템에 요청을 보내지 말고, 소유자 승인과 범위를 기록한 스테이징 환경에서 버전 조합별로 확인합니다. 시험은 요청을 악용하는 문자열보다 파서의 결정과 연결 상태가 일치하는지에 초점을 둡니다.

| 시험군 | 확인할 관찰값 | 통과 기준 |
| --- | --- | --- |
| 정상 요청 | 각 홉의 HTTP 버전, method·target·본문 길이, 응답 상관관계 | 앞단과 원본이 동일한 요청 하나를 처리하고 요청·응답이 올바르게 짝지어집니다. |
| 잘못된 길이·전송 코딩 조합 | 최초 거부 지점, 오류 코드, 버퍼와 upstream 연결 상태 | 모호한 요청이 원본에 도달하지 않고, 표준상 연결을 닫아야 하는 오류에서 해당 연결을 재사용하지 않습니다. |
| 중복 또는 유효하지 않은 길이 필드 | 프록시별 파싱 결과와 변환 후 필드 | 앞단과 백엔드가 서로 다른 값으로 처리하지 않으며, 허용되지 않는 메시지는 오류로 종결합니다. |
| HTTP/2 요청 | stream 종료, DATA 길이 합, field 검증 결과 | malformed 메시지는 RFC 9113의 오류 처리에 따라 전달되지 않습니다. |
| HTTP/2→HTTP/1 변환 | 변환 전·후의 field와 framing, 백엔드 연결 풀 | 변환된 요청이 하나의 유효한 HTTP/1.1 메시지로만 표현되고 경계가 보존됩니다. |
| 요청 연속 처리와 오류 직후 요청 | 연결 식별자, 파서 상태, 응답 순서 | 한 요청의 잔여 바이트가 다음 요청이나 다른 사용자 응답에 섞이지 않습니다. |

이 표는 시험 설계 기준입니다. 이 문서 작성 과정에서 특정 제품이나 스테이징 서버에 시험을 실행하지 않았으므로 통과 결과로 읽으면 안 됩니다. 공급사 패치·버전 변경 뒤에는 같은 조합을 회귀 점검하고 결과에 제품 버전, 프록시 경로, 일시, 로그 출처를 남깁니다.

## 이상 징후 조사와 로그

- WAF의 요청 수와 원본 애플리케이션의 요청 수가 특정 경로에서 달라지는지 확인합니다.
- 프런트엔드의 요청 ID와 백엔드의 요청 ID가 같은 요청을 가리키는지 비교합니다. 프록시가 생성한 ID는 클라이언트가 보낸 값을 무조건 신뢰하지 말고 신뢰 경계에서 새로 만들거나 검증합니다.
- 정상 요청 직후 다른 사용자의 응답처럼 보이는 데이터, 캐시 키와 원본 URL 불일치, 설명되지 않는 400·502·연결 재설정을 조사합니다. 단일 증상만으로 request smuggling이라고 결론 내리지는 않습니다.
- 로그에는 프로토콜 버전, 파서 오류 종류, 요청 크기, 연결 재사용 여부, upstream 상태를 기록하되 Authorization·Cookie·비밀번호·민감한 본문은 수집하거나 마스킹합니다.
- 장애 대응 중에는 의심되는 upstream 연결 풀을 격리·재생성하고, 영향을 받은 캐시 항목과 응답 상관관계를 조사합니다. 증거 보존과 운영 영향은 사고 대응 절차에 따릅니다.

## English summary

HTTP request smuggling and desynchronization arise when intermediaries and origin servers disagree about HTTP message boundaries. RFC 9112 defines HTTP/1.1 body-length precedence and requires connection closure for several framing errors; RFC 9113 forbids intermediaries from forwarding malformed HTTP/2 messages. Audit every proxy and protocol-conversion hop, reject ambiguous input, normalize before forwarding, and verify connection-pool behavior in an authorized staging environment. The checklist is a test plan, not an executed result.

## 출처와 확인 범위

- [RFC 9112: HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112.html), IETF Standards Track, 2022년 6월. §6.1–§6.3에서 Transfer-Encoding·Content-Length와 메시지 본문 길이, 잘못된 요청의 연결 종료를 확인했습니다. §11.2에서 파서 불일치와 request smuggling의 정의를 확인했습니다.
- [RFC 9113: HTTP/2](https://www.rfc-editor.org/rfc/rfc9113.html), IETF Standards Track, 2022년 6월. §8.1.1·§8.2에서 malformed 메시지와 DATA payload 길이 검증, 필드 검증, 중개자의 전달 금지 요구를 확인했습니다.
- [MITRE CWE-444: Inconsistent Interpretation of HTTP Requests](https://cwe.mitre.org/data/definitions/444), MITRE CWE 온라인 항목, 2026년 11월 4일 확인. 프록시·방화벽과 최종 서버의 요청 해석 차이, 보안 필터 우회·캐시 영향의 분류를 확인했습니다. 공격 예시는 본문에 옮기지 않았습니다.
- [OWASP Web Security Testing Guide: Testing for HTTP Request Smuggling](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/16-HTTP_Request_Smuggling/), OWASP WSTG 온라인 문서, 2026년 11월 4일 확인. 프런트엔드와 백엔드 파서 차이 및 프로토콜 변환 경계를 확인했습니다. 시험 절차와 페이로드는 본문에 옮기지 않았습니다.
- [PortSwigger Web Security Academy: HTTP request smuggling](https://portswigger.net/web-security/request-smuggling), 온라인 교육 문서, 2026년 11월 4일 확인. HTTP/2 다운그레이드와 연결 재사용에 대한 방어 설명을 대조했습니다. RFC의 규범 요구와 구분해 보조 설명으로만 사용했습니다.

표준의 `MUST`·`SHOULD` 요구는 RFC 9112·9113의 해당 조항을 기준으로 요약했습니다. 시험표와 운영 체크리스트는 이 자료의 교육용 제안이며 실제 장비에서 실행한 결과가 아닙니다.
