# 평가 입력과 판정 기준 | Evaluation inputs and scoring rules

아래 질문·정답표·채점 산술은 모델·도구의 동작을 평가하기 위한 자체 설계입니다. 해당 입력으로 모델을 호출하거나 가중치 추론을 실행하지 않았습니다. 공식 벤치마크나 모델의 응답 관측값과 구분해서 읽으실 수 있습니다.

각 절의 숫자는 직접 정한 문제의 답이나 판정 기준입니다. 공식 벤치마크·실제 정확도·공급사의 학습 결과로 해석하지 않습니다. MLX 배열 예도 실행 관측값이 아닌 산술 기대값입니다. [직접 실행한 CPU 계산과 기록](README.md)은 별도입니다.

## Amazon

Amazon Nova Micro v1의 [공식 모델·도구 설명](../models/amazon.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 공지 추출 예

다음은 호출 결과가 아니라 평가에 사용할 자체 입력입니다. “행사는 11월 4일이며 접수는 10월 30일까지입니다. 장소는 추후 공지합니다. 행사일·접수마감·장소를 JSON으로 적고 없는 값은 null로 적어 주세요.”라고 묻습니다.

| 확인할 값 | 이 입력에서의 판정 기준 |
| --- | --- |
| 행사일 | 11월 4일을 골라야 합니다. |
| 접수마감 | 10월 30일과 행사일을 바꾸면 오답입니다. |
| 장소 | 실제 장소를 만들어 쓰면 오답입니다. |
| 형식 | JSON 파싱 성공과 각 필드의 정답을 따로 셉니다. |

세 필드 중 두 개만 맞으면 필드 정확도는 2/3이지만 문서 전체 정답은 아닙니다. 반대로 값이 모두 맞아도 JSON 뒤에 설명이 붙으면 엄격한 단일 JSON 계약은 어긴 것입니다. 이는 직접 정한 채점 규칙이며 모델의 측정 점수가 아닙니다. 같은 공지를 이미지로만 제공하여 실패했다면 Micro의 텍스트 입력 범위를 먼저 확인해야 하며, 그 결과를 텍스트 독해 능력의 오답률로 합산하지 않습니다.

## Anthropic

Anthropic Claude Sonnet 5.5의 [공식 모델·도구 설명](../models/anthropic.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 표 추출과 도구 판정

자체 평가 입력을 “A안 12개, B안 8개, C안은 수량 미정입니다. 확정 수량 합계와 미정인 항목을 알려 주세요.”로 정하겠습니다. 실행한 응답은 없으며, 정답 기준은 합계 20과 미정 항목 C안입니다. 20이라는 합계만 맞히고 C안까지 0개로 확정하면 정보 상태를 바꾼 오답입니다. ‘미정’과 ‘없음’의 구별을 볼 수 있는 입력입니다.

| 구간 | 확인할 기준 |
| --- | --- |
| 최종 텍스트 | 12+8=20이며 C안 수량은 모른다고 남겨야 합니다. |
| 블록 처리 | 비텍스트 블록을 버리며 최종 답까지 누락하지 않아야 합니다. |
| 도구 요청 | 계산 요청을 제안한 것과 계산기가 실제 실행된 것을 구분합니다. |
| 종료 | 정상 완료인지 출력 예산으로 잘렸는지 기록합니다. |

이 작은 덧셈에는 도구가 필수라는 전제를 두지 않습니다. 도구 연동을 따로 시험한다면 애플리케이션이 돌려준 결과와 최종 답의 일치 여부를 추가로 봅니다. 모델이 ‘계산했습니다’라고 말한 문장만으로 실행 성공을 인정하지 않습니다. 따라서 내용 정답과 블록 처리 오류를 별도로 남길 수 있습니다. 이 구분은 특히 버전 이전 뒤 화면이 비는 문제를 곧바로 모델의 무응답으로 오해하지 않게 합니다.

## Apple

Apple MLX의 [공식 모델·도구 설명](../frameworks/apple-mlx.md)과 구분한 자체 평가 설계입니다.

자체 배열 예로 `a=[1,2,3]`, `b=2*a+1`을 생각하겠습니다. b의 기대값은 `[3,5,7]`이고 합은 15입니다. 이 글에서는 MLX를 실행하지 않았으며 이 값은 산술로 정한 비교 기준입니다. 식을 만드는 시간과 실제 b를 얻는 시간을 구분하려면 입력을 이미 준비했는지, 평가를 어디서 강제하는지 명확해야 합니다.

| 확인 구간 | 포함되는 일 |
| --- | --- |
| 입력 준비 | 배열 생성·자료형 변환 등입니다. |
| 식 구성 | b를 만드는 계산 관계를 기록합니다. |
| 평가 완료 | b를 실제로 계산하도록 요청하고 끝날 때까지의 범위를 봅니다. |
| 값 비교 | `[3,5,7]`인지 검사하며 성능 측정과 구분합니다. |

이미 평가한 같은 b에 다시 `mx.eval(b)`만 호출하면 새로운 곱셈을 다시 수행한 시간으로 해석할 수 없습니다. 반복 벤치마크에서는 새 입력이나 새 연산으로 같은 일을 반복하는지 확인해야 합니다. 반대로 매 사소한 연산마다 평가를 강제하면 그래프를 묶어 처리할 기회를 바꾸게 됩니다.

## Baidu

Baidu ERNIE 4.5 0.3B PT의 [공식 모델·도구 설명](../models/baidu.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 수량 독해 예

자체 입력을 “仓库原有12箱，运走5箱，又收到2箱。现在有多少箱？只回答数字。”로 정하겠습니다. 의미는 상자 12개에서 5개를 보내고 2개를 받았다는 것이므로 비교 기준은 12−5+2=9입니다. 실제 모델 응답을 얻은 예는 아닙니다. 같은 사실을 한국어와 영어로도 적어 숫자·연산의 의미를 같게 두면, 번역 과정에서 문제 자체가 달라지는 오류를 줄일 수 있습니다.

| 구분 | 이 입력의 실패 판정 |
| --- | --- |
| 수량 | 9가 아닌 답을 쓰면 계산·독해 오답입니다. |
| 지시 | 숫자만 요청했는데 긴 설명을 붙이면 형식 오류입니다. |
| 범위 | 질문을 포함한 decode 결과에서 9를 찾는 방식은 정답 판정에 쓰지 않습니다. |
| 언어 | 중국어 한 사례의 성공을 한국어 성능으로 옮기지 않습니다. |

0.36B는 가중치의 수를 나타내며 한 번에 다룰 수 있는 문맥 길이나 한국어 정답률을 뜻하지 않습니다. 긴 입력을 허용하는 설정과 짧은 셈을 안정적으로 푸는 능력도 별개입니다. 이처럼 배포 형식, 구조, 생성 구간, 업무 정답을 나누면 작은 모델에서 무엇이 실제로 부족한지 더 구체적으로 기록할 수 있습니다.

## Black Forest Labs

Black Forest Labs FLUX.1-schnell의 [공식 모델·도구 설명](../models/bfl.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 이미지 판정 예

자체 평가 문장을 “A blue square on the left and a yellow circle on the right, on a plain white background.”로 정하겠습니다. 생성하지 않은 평가 입력이며 아래 표도 관측 결과가 아닌 판정 기준입니다.

| 요소 | 확인할 내용 | 실패 사례 |
| --- | --- | --- |
| 대상 | 사각형과 원이 각각 있어야 합니다. | 둘 다 원으로 바뀌면 모양 오류입니다. |
| 색 | 사각형은 파랑, 원은 노랑이어야 합니다. | 색을 서로 바꾸면 속성 결합 오류입니다. |
| 관계 | 사각형이 원의 왼쪽에 있어야 합니다. | 대상은 맞아도 좌우가 바뀌면 관계 오류입니다. |
| 배경 | 단순한 흰색이어야 합니다. | 요구하지 않은 복잡한 장면을 넣으면 지시 이탈입니다. |

네 항목 중 세 개만 맞은 그림을 ‘prompt 전체 준수’라고 세지 않습니다. 예쁜 그림이라는 인상과 조건별 정답은 다르기 때문입니다. 같은 seed에서 step만 달리하여 비교할 수 있지만, 그 비교를 실제로 실행하기 전에는 어느 설정이 더 낫다고 기록하지 않습니다. 작은 글자나 로고를 추가하는 과제라면 모양과 별도로 철자까지 검사해야 합니다. 이 모델은 사실을 확인하는 시스템이 아니므로 그럴듯한 제품 그림을 실제 제품 사진의 증거로 취급하지 않습니다.

## Cohere

Cohere Aya Expanse 8B의 [공식 모델·도구 설명](../models/cohere.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 한국어·영어 조건 쌍

자체 한국어 입력은 “이 도서관은 화요일에 닫습니다. 다만 매달 첫째 화요일에는 엽니다. 첫째 화요일과 둘째 화요일의 운영 여부를 각각 한 문장으로 답해 주세요.”입니다. 영어 입력은 “The library is closed on Tuesdays, except the first Tuesday of each month. Is it open on the first and the second Tuesday? Answer each separately.”로 정합니다. 실제 추론 결과가 아닌 평가용 문장입니다.

| 판단 대상 | 두 입력에서 공통으로 맞아야 할 내용 |
| --- | --- |
| 첫째 화요일 | 예외가 적용되어 엽니다. |
| 둘째 화요일 | 일반 조건이 적용되어 닫습니다. |
| 범위 | 첫째 화요일의 예외를 모든 화요일로 넓히면 안 됩니다. |
| 한국어 표현 | 독자에게 요청한 존댓말을 유지하는지도 별도로 봅니다. |

내용 두 개 중 하나를 맞혔으면 1/2이며, 말투가 공손하다는 이유로 내용 점수를 올리지 않습니다. 반대로 두 사실이 같다면 영어와 한국어의 문장 길이 차이를 내용 오류로 세지 않습니다. 월의 실제 날짜를 묻지 않았으므로 달력을 임의로 만들어 붙이는 것도 불필요한 정보 추가입니다.

언어별 차이를 보고 싶다면 질문의 사실·예외 수를 유지하고 언어만 바꾸는 방식이 도움이 됩니다. 한 언어에만 어려운 관용구를 넣은 비교는 번역 난도까지 바뀝니다. 이 예의 기준은 문장 안에 닫혀 있어 외부 상식의 영향을 줄이지만, 두 짧은 질문의 결과만으로 23개 언어 전체의 성능을 대표하지는 않습니다.

## Google

Google Gemma 3 1B IT의 [공식 모델·도구 설명](../models/google.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 일정 요약 예

평가 입력을 “A 실험은 11월 4일 시작합니다. B 실험은 취소되었습니다. C 실험의 시작일은 정하지 않았습니다. 세 실험의 상태를 한 줄씩 요약해 주세요.”로 정하겠습니다. 모델을 실행한 응답은 없으며 다음 표가 자체 정답 기준입니다.

| 항목 | 남겨야 할 정보 | 구체적 실패 |
| --- | --- | --- |
| A | 시작일 11월 4일입니다. | 다른 실험에도 이 날짜를 붙이면 오답입니다. |
| B | 취소 상태입니다. | 예정·연기 상태로 바꾸면 원문과 다릅니다. |
| C | 시작일이 미정입니다. | 문맥에 없는 날짜를 쓰면 정보 추가입니다. |

원문의 세 항목 중 두 개만 요약하면 그럴듯한 문장이라도 누락이 있습니다. 원문을 전부 복사한 긴 답은 사실을 유지할 수 있지만 ‘한 줄씩 요약’이라는 요구를 얼마나 지켰는지는 별도입니다. 요약에서는 줄 수·사실 보존·추가 사실을 각각 봅니다.

장문으로 확장하려면 동일한 핵심 사실을 문서 앞·중간·뒤에 옮기고 다른 문장은 방해 자료로 고정할 수 있습니다. 다만 입력을 잘라낼 때 정답 문장 자체가 사라졌다면 모델의 회수 실패로 세지 않습니다. 32k 범위에 들어온 사실과 필요한 내용을 실제로 이용한 사실은 다르므로 길이만으로 요약 품질을 인정하지 않습니다.

### 문맥 예산 산술

문맥에는 문서뿐 아니라 대화 지시·템플릿·이전 대화·생성할 답의 공간도 관련됩니다. 자체 예산을 30,000토큰으로 정하고 문서 28,000, 나머지 입력 500, 답 공간 1,500을 배정하면 합은 30,000입니다. 이는 예산 산술 예이며 실제 문서를 tokenizer로 잰 결과나 이 모델의 최대 출력 설정이 아닙니다. 한국어 글자 수를 토큰 수로 대신하여 같은 예산을 계산하지 않습니다.

## Hugging Face

Hugging Face SmolLM2 135M Instruct의 [공식 모델·도구 설명](../models/huggingface.md)과 구분한 자체 평가 설계입니다.

### 직접 만든 짧은 영어 독해 예

자체 입력을 “Lena packed three red notebooks and two blue notebooks. She gave away one red notebook. How many notebooks remain? Answer with one integer.”로 정하겠습니다. 실제 생성 결과가 아니라 정답 기준을 설계한 예입니다. 남은 수는 3+2−1=4입니다.

| 확인할 부분 | 판정 기준 |
| --- | --- |
| 계산 | 빨강만 세거나 준 물건을 더하지 않고 4를 답해야 합니다. |
| 형식 | 정수 하나라는 요구를 따로 확인합니다. |
| 생성 구간 | 질문을 제외한 새 답변만 판정합니다. |
| 언어 확장 | 같은 문제의 한국어 결과는 별도 항목으로 기록합니다. |

135M에서 이런 짧은 입력의 형식·독해가 무너지는지 먼저 보면 장문 지식 질문의 오류를 더 분명히 해석할 수 있습니다. 그러나 한 사례가 맞았다고 수학 능력을 일반화하지 않습니다. 초소형 모델의 장점을 말하려면 실제 장치의 로딩 시간·생성 속도·정답 기준이 함께 필요합니다. [모델 설명의 약 270MB 가중치 계산](../models/huggingface.md#작은-가중치와-생성된-답을-나누어-보기)은 그 측정값을 대신하지 않습니다.

### 직접 만든 단일 턴·이어지는 대화 예

| 입력 형태 | 유지할 사실 | 실패 판정 |
| --- | --- | --- |
| 한 질문 | 처음 2시간과 추가 1시간이 함께 있습니다. | 1시간만 답하면 전체와 추가분을 혼동했습니다. |
| 두 차례 | 앞 대화의 2시간을 다음 질문에 이어받아야 합니다. | 새 질문만 읽어 원래 예약을 잊으면 문맥 오류입니다. |
| 형식 | 최종 답에 시간 단위가 있어야 합니다. | 숫자를 맞혀도 다른 단위를 붙이면 오답입니다. |

두 차례 변형에서는 중간 대답을 어떻게 고정했는지도 비교 조건입니다. 실제로 얻지 않은 첫 응답을 얻은 것처럼 기록하지 않습니다. 공식 카드가 이 버전을 단일 턴 중심이라고 한 이유로 다중 턴 실패 가능성을 별도로 살펴보되, 아직 실행하지 않은 오류가 실제 관측되었다고 쓰지도 않습니다.

단일 질문의 성공을 대화 전체의 기억 능력으로 일반화하거나, 두 입력 형식의 차이를 무시해 평균 점수 하나로 합치면 배포물의 용도를 판단하기 어렵습니다. Base와 Instruct의 사용 조건도 별도이므로 DUS 구조가 같다는 이유만으로 라이선스까지 같게 처리하지 않습니다.

### 가중치 공유와 별도 함수의 비교

파라미터 공유와의 차이를 위한 자체 수 예로, 서로 다른 두 함수 f₁(x)=2x+1·f₂(x)=3x+1을 쓰면 입력 1은 3을 거쳐 10이 됩니다. 하나의 f(x)=2x+1을 두 번 쓰면 3을 거쳐 7이 됩니다. 두 번 계산한다는 사실만 같고 저장한 함수와 바꿀 수 있는 매개변수는 다릅니다. 이는 실제 SOLAR 층의 식이 아닌 개념 비교이며, DUS를 같은 가중치의 반복 호출과 구분하기 위한 예입니다.

### 직접 만든 조회와 예약의 구분 예

자체 입력은 “내일 오후 2시에 비어 있는 회의실을 알려 주세요. 예약은 하지 마세요.”입니다. 시험지의 기준 날짜를 2026년 11월 2일로 제공하고, 평가용 도구는 조회 함수 `check_rooms`와 예약 함수 `reserve_room`으로 나눕니다. 가정 자료로 다음 날 그 시각의 A실은 사용 중, B실은 비어 있다고 정합니다. 실제 도구 응답·예약·모델 출력을 얻은 예가 아닙니다.

| 단계 | 정답 기준 | 실패 사례 |
| --- | --- | --- |
| 날짜·시간 | 2026년 11월 3일 오후 2시를 사용해야 합니다. | 기준 날짜나 오전·오후를 바꾸면 안 됩니다. |
| 함수 선택 | 조회는 과제에 맞고 예약은 요청 범위를 벗어납니다. | 이름이 비슷한 예약 함수를 골라도 의미상 오답입니다. |
| 자료형 | 조회 인자는 도구 계약의 날짜·시간 형식에 맞아야 합니다. | 자연어 문장을 JSON으로 감싼 것만으로 유효 인자가 되지는 않습니다. |
| 최종 답 | 주어진 자료에서는 B실이 비어 있다고 알려야 합니다. | A실을 추천하거나 예약 완료라고 말하면 오답입니다. |

기준 날짜를 뺀 변형에서는 구체적인 날짜를 정하는 정보가 부족합니다. 이때는 기준 날짜를 확인해야 하며, 모든 필드를 임의로 채운 호출을 성공으로 세지 않습니다. 날짜가 주어진 변형과 주어지지 않은 변형을 나누어 볼 수 있습니다.

이 과제는 유효한 JSON을 생성하는 능력만으로는 충분하지 않음을 보여 줍니다. 도구가 실제로 조회했는지, 결과가 어떤 요청에 해당하는지, 답이 그 결과를 반영하는지까지 분리합니다. 사고 모드에서 더 긴 글이 나와도 이런 조건을 지키지 않으면 정답이 아닙니다. 실제 실행 없이 위 판정표만으로 모델의 성공률을 보고하지 않습니다.
